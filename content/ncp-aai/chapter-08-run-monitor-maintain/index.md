새 모델을 붙인 뒤 응답이 빨라졌다. 그런데 검증 도우미가 기준 시험을 잘못 고르는 사례도 늘었다고 하자. 지연과 오류는 같은 대시보드에 보여도 확인해야 할 원인은 다르다. 요청이 얼마나 빨리 끝났는지, 사용자가 요청한 과업이 끝났는지, 버전을 바꾼 뒤 어떤 종류의 입력이 나빠졌는지를 각각 확인했다.

공식 학습 가이드 8.1–8.5는 대시보드와 신뢰성 지표, 로그·오류·이상 징후 진단, 버전별 벤치마크, 자동 튜닝과 버전 관리, 가용성과 운영 투명성을 다룬다. 비중은 공식 웹 출제표의 5%를 사용했다. [공식 출제표](https://www.nvidia.com/en-us/learn/certification/agentic-ai-professional/#exam-blueprint) · [공식 학습 가이드 8장](https://dam-cdn.nvd.orangelogic.com/AssetLink/64tei188l3tt132l265u1ipjoexdl1p5.pdf#page=11)

## 1. 운영 대시보드에서 요청 건강과 답변 품질 나누기

| 지표 | 질문 |
|---|---|
| 처리량과 실패 수 | 입력이 얼마나 들어오고 요청이 어디서 멈추는가 |
| 유효 응답까지의 지연 | 목표 시간 안에 필요한 결과를 얻었는가 |
| 모델 첫 응답과 생성 속도 | 입력 처리와 첫 출력, 이후 생성 중 어디가 느린가 |
| 큐와 도구 호출 | 대기가 늘었는가, 특정 자료나 서비스에서 타임아웃이 났는가 |
| 업무 성공과 올바른 보류 | 올바른 시험과 근거를 썼는가, 자료가 없을 때 적절히 종료했는가 |

HTTP 상태 200은 전송이 성공했다는 신호다. 기준 시험에 무엇을 썼는지와 수치가 맞았는지는 과업 지표로 확인한다. 반대로 입력을 기다리는 응답의 시간을 모델 서버가 느렸다고 해석하면 문제가 생긴 위치를 놓친다. 자동 처리 시간과 사람의 확인 대기 시간은 구간을 분리한다.

p95에는 분모가 필요하다. 성공한 요청만 집계하면 시간 초과와 거부가 늘어도 수치가 좋아질 수 있다. 모든 인스턴스의 p95를 단순 평균하면 전체 분포를 알기 어렵다. 집계할 수 있는 히스토그램으로 기준 버킷과 요청 조건을 맞춰 전체 지연을 본다. [Prometheus의 히스토그램과 분위수](https://prometheus.io/docs/practices/histograms/) · [4장의 대기열 시뮬레이션](/ncp-aai/chapter-04-deployment-and-scaling/)

## 2. 한 요청의 실행 기록으로 원인 좁히기

flowchart TD

    B --> C["대표 실행의 trace_id 찾기"]
    C --> D["큐, 모델, 도구, 결과 구간 대조"]
    D --> E["재현 입력과 도구 결과 확보"]
    E --> F["변경 지점과 회귀 결과 비교"]

트레이스에는 하나의 조사 실행과 그 아래에서 처리한 모델·도구 구간을 연결한다. 로그는 구간에서 일어난 사건과 원인을 설명할 수 있다. 메트릭에는 모델의 버전, 과업 유형, 결과 종류처럼 카디널리티가 제한된 값을 사용한다. 각 요청의 ID는 트레이스나 구조화 로그에서 건별로 확인한다. GenAI용 OpenTelemetry 규약의 상태와 지원 속성은 사용하는 버전에서 확인한다. [OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/) · [OpenTelemetry GenAI Semantic Conventions](https://github.com/open-telemetry/semantic-conventions-genai)

R42 비교가 300ms를 넘겼다면 먼저 그 실행의 대기 시간이 늘었는지, 모델이 추론에 오래 걸렸는지, 시험 자료를 기다렸는지 읽는다. 모델 지연만 늘었다면 입력 길이와 대상 모델이 바뀌었는지 살핀다. 자료 API의 오류가 함께 늘었다면 요청량, 재시도, 도구 시간 제한이 맞는지 본다. 구간 일부가 병렬이라면 가장 오래 걸린 경로와 결과 합치는 시간을 별도로 확인한다. [블로그의 서빙 지연 측정](/agentic-ai/serving/)

## 3. 빨라진 후보가 과업을 회귀시킨 경우

[operations_lab.py](operations_lab.py)는 같은 요청 열 건의 모의 실행 기록을 기준 버전과 후보 버전에 각각 둔다. 각 행의 큐·모델·도구 시간을 더했다. 300ms를 완료 기한으로 두고, 과업 성공 수와 개선 후에 새로 틀린 사례가 있는지를 비교했다. 가상 시간이며 운영 서버 부하를 측정한 실험은 아니다.

```bash
python3 operations_lab.py
```

| 설정 | 과업 성공 | p95 | 300ms 초과 | 모델 구간 중앙값 |
|---|---:|---:|---:|---:|
| 기준 버전 | 9/10 | 410ms | 5 | 165ms |
| 후보 버전 | 8/10 | 289ms | 0 | 105ms |

후보는 기한을 넘긴 사례가 없었지만, 기준 버전이 맞힌 4번 사례에서 새로 실패했다. 코드는 후보의 성공 수가 줄지 않고 새 회귀가 없으며 p95가 300ms 이하인 경우에만 진행한다. 이 입력에서는 `hold`였다. 표본이 열 건이라 여기서 쓴 최근접 순위 p95는 가장 큰 값과 같다. 운영에 적용할 때 표본이 큰 분포와 과업별 실패 유형을 추가로 본다.

## 4. 자동 개선과 버전 기록을 연결하기

반복되는 피드백이 있으면 실패 유형부터 모은다. 비교 대상이 뒤집힌 경우는 요청 분류·추출을, 다른 판본을 선택했다면 검색과 데이터 조건을 살핀다. 변경 후보에서 새 프롬프트나 모델 매개변수, 도구 설정을 평가하고 결과를 배포 버전에 연결한다. 모델 재학습이 필요하면 별도 학습 데이터와 검증셋, 사용한 모델 버전을 관리한다. 간단한 조회 필터 변경과 모델 학습은 서로 다른 변경 책임을 갖는다. [3장의 실패 분석과 튜닝](/ncp-aai/chapter-03-evaluation-and-tuning/)

버전 기록에는 모델, 프롬프트, 서비스 코드, 도구 스키마, 지식 인덱스 판본, 평가셋 판본을 포함할 수 있다. 운영 신호와 전체 평가의 통과 조건을 같이 보며 제한된 트래픽부터 적용한다. 롤백으로 코드가 바뀔 때는 이전 버전이 새 체크포인트나 도구 결과를 읽을 수 있는지도 확인한다.

## 5. 운영 중 보류와 복구를 설명하기

자료 서비스가 잠시 응답하지 않으면 이미 확인한 사실과 다시 확인해야 할 항목을 구분해 보여 준다. 이후 같은 조사를 재개할 수 있도록 조사 ID와 마지막 완료 단계를 남긴다. 쓰기 권한이 걸린 작업에서는 현재 요청이 이미 반영됐는지 확인할 수 있어야 한다.

사용자 화면에 내부 로그 전체를 표시할 필요는 없다. 반환한 값의 출처와 조회 시점, 현재 상태, 모호해서 확인이 필요한 항목을 설명한다. 운영자가 권한 범위 안에서 같은 실행을 찾아볼 때에는 추적 ID와 버전이 연결된다. 이런 상태를 검색·모델·도구의 모니터링과 함께 두면, 서비스가 접속 가능하더라도 업무 결과가 틀리거나 근거가 오래된 문제를 확인할 수 있다. [10장의 사용자 감독과 실행 기록](/ncp-aai/chapter-10-human-ai-oversight/)
