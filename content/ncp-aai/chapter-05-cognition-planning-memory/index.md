R42의 탐지율 하락을 조사하다가 기준 시험을 골라 달라는 답과 함께 멈췄다고 하자. 다음 날 돌아온 사용자는 R38을 기준으로 정한다. 앱은 어제 받은 설정 비교 데이터를 찾아 이어서 실행해야 한다. 사용자가 이번 보고서에서 R38을 골랐다는 사실은 현재 조사의 조건이다. 다른 조사에서도 퍼센트포인트로 표기하길 원한다는 선호는 적용 범위가 다르다.

공식 학습 가이드 5.1–5.5는 단기·장기 문맥 유지, 추론과 하위 과업 분해, 다단계 계획, 상태가 있는 실행, 경험과 피드백에 따른 조정을 다룬다. 공식 웹 출제 비중은 10%다. [공식 출제표](https://www.nvidia.com/en-us/learn/certification/agentic-ai-professional/#exam-blueprint) · [공식 학습 가이드 5장](https://dam-cdn.nvd.orangelogic.com/AssetLink/64tei188l3tt132l265u1ipjoexdl1p5.pdf#page=8)

## 1. 다음 요청에서 무엇이 다시 필요할까

모델 컨텍스트에는 이번 요청과 다음 판단에 필요한 근거를 넣는다. 실행기는 보다 자세한 진행 상태를 보관할 수 있다. 프로세스가 끝난 뒤에도 동일한 조사에서 작업을 이어 가려면 상태를 체크포인트에 보존한다. 사용자에게 확인한 단위 또는 표기 선호는 여러 작업에 적용할 수 있도록 사용자 범위에 둔다.

| 범위 | 검증 도우미가 보관하는 값 |
|---|---|
| 현재 모델 입력 | 질문, R42의 최근 관찰, 다음 행동 후보 |
| 실행 상태 | 완료한 작업, 비교 후보, 남은 호출 수 |
| 체크포인트 | 조사 버전, 단계, 중단 이유, 조사 근거 참조 |
| 장기 기억 | 사용자가 확인한 보고서 표기 단위 |
| 원본 지식 | 시험값, 펌웨어 변경 문서와 현재 유효한 기준 |

컨텍스트 창이 커도 중단 내용을 자동으로 재개할 수 있지는 않다. 앱이 작업 ID에 따라 상태를 다시 읽고, 필요한 부분을 현재 호출에 넣는다. 반대로 도구의 긴 로그를 매번 포함하면 토큰이 반복해서 들어간다. 다음 선택에 쓰는 값은 상태에 구조화하고, 원래 관찰은 출처 ID로 다시 읽을 수 있게 한다. [MemGPT 원 논문](https://arxiv.org/abs/2310.08560) · [LangGraph의 체크포인터와 장기 저장소](https://docs.langchain.com/oss/python/langgraph/persistence)

## 2. 추론, 분해, 재계획의 위치

탐지율 하락을 조사하려면 시험마다 바뀐 설정을 먼저 비교하고, 조건을 통제할 수 있는 자료를 찾고, 영향을 설명해야 한다. 하위 목표를 이렇게 나누면 각각 어떤 도구와 결과가 필요한지 적기 쉽다. 중간 판단을 사용하는 추론과, 환경에 질의를 보내 정보를 늘리는 행동이 연결된다. ReAct는 판단과 행동을 교차시키고 새 관찰을 다음 단계에 넣는 구조를 실험했다. [ReAct 원 논문](https://arxiv.org/abs/2210.03629)

    B --> C{"같은 조건의 기준 시험이 있는가"}
    C -->|후보 확보| D["부족한 조건을 확인하고 측정값 비교"]

    E -->|선택 수신| D
    D --> F["관찰과 결과를 연결"]
    F -->|추가 근거 필요| C

| 방법 | 계획을 갱신하는 시점 | 적합한 부분 |
|---|---|---|
| 미리 정한 로직 | 확인할 조건과 순서를 코드로 정한다. | 시험 ID와 기준 문서의 유효성 검사 |
| 계획 후 실행 | 하위 목표와 의존 관계를 먼저 적고 실행한다. | 필요한 시험이 이미 알려진 교차 비교 |
| 관찰 기반 재계획 | 도구 결과를 보고 다음 조사를 선택한다. | 원래 기준 시험이 없거나 새 변수가 발견된 조사 |

각 단계에 선행 조건과 끝낼 기준을 적어 두면 전체 계획을 처음부터 다시 세우지 않아도 된다. 펌웨어와 각도가 함께 바뀐 사실을 이미 확인했다면 그 관찰은 유지하고, 비교 시험 후보를 찾는 단계만 바꿀 수 있다. 운영 기록에는 도구 선택, 그 선택에 쓴 관찰, 결과와 종료 사유를 남긴다. 사용자에게도 이 자료로 설명할 수 있다. [1장의 상태 기반 설계](/ncp-aai/chapter-01-agent-architecture/)

## 3. 체크포인트를 다른 프로세스에서 다시 열기

[resume_lab.py](resume_lab.py)는 임시 SQLite 파일을 만들고 별도 Python 프로세스를 차례로 실행한다. 조사에는 이전 설정 비교 결과의 ID만 저장한다. 재개 요청에서는 버전 1의 `waiting` 상태에만 R38 선택을 적용한다. 표기 단위는 별도 표에 저장한다.

```bash
python3 resume_lab.py
```

| 단계 | 조사 버전과 상태 | 기준 시험 | 사용자 선호 |
|---|---|---|---|
| 저장 뒤 새 프로세스에서 읽음 | 1 · `waiting` | `null` | `null` |
| 기준 시험을 선택하고 재개 | 2 · `ready` | R38 | `null` |
| 같은 버전의 재개를 다시 시도 | `stale_or_duplicate` | 기존 상태 유지 | `null` |
| 퍼센트포인트 표기를 별도로 확인 | 2 · `ready` | R38 | `percentage_points` |

재개 뒤에도 설정 비교의 참조 `compare:R41:R42@2`가 남았다. SQLite 갱신은 현재 버전과 대기 상태가 맞을 때만 한 행을 바꿨다. 두 작업자가 같은 체크포인트를 읽은 상황에서도 이 조건을 어느 쪽이 먼저 적용했는지 확인할 수 있다. 실습은 체크포인트와 재개 조건을 검사한다. 별도 서비스에서 보낸 외부 효과를 복구할 때는 그 서비스의 요청 ID와 실제 반영 결과도 필요하다. [SQLite 격리와 트랜잭션](https://sqlite.org/isolation.html) · [외부 효과 중복을 다룬 사례](/agentic-ai/lab-assistant/)

## 4. 오래된 상태와 지식의 충돌 처리

사용자가 장기 기억에 남긴 표기 단위와 최근 요청에서 지정한 단위가 다르면, 지금 요청의 범위 안에서 어떤 값을 적용할지 정한다. 이 요청에만 백분율을 쓰라는 지시는 실행 상태에서 처리할 수 있고, 모든 보고서에 적용해 달라는 확인은 사용자 기억을 갱신한다. 운영 문서의 유효 버전이나 시험 원본을 조회한 결과도 사용자 선호와 별도로 읽는다.

장기 기억에 저장할 때에는 출처와 적용 시점, 소유자, 변경 여부를 둔다. 같은 사용자에게서 정정이 오면 어느 날짜부터 값이 바뀌었는지도 확인한다. 사용자의 한 번의 선택은 작업 재개에 유용하지만, 모든 후속 요청에 일반화할 정보인지는 따로 판단한다. [블로그의 사용자 선호와 두 시간 축](/agentic-ai/memory-writing/)

## 5. 피드백을 어디에 반영할까

한 사용자만 원하는 표기는 선호 저장소에서 반영한다. 여러 사용자가 비슷한 요청에서 기준 시험을 혼동했다면 프롬프트나 입력 양식을 바꾼다. 오래된 기준표가 계속 들어왔다면 검색이나 데이터 버전 조건을 확인한다. 동일한 증상이라도 실패 지점이 다를 수 있으므로 입력, 계획, 실행, 결과를 구분해 평가한다.

변경 뒤에는 오류가 났던 조건과 새로운 사례를 함께 비교한다. 예를 들어 R38 선택 이후 같은 상태를 반복해서 적용하지 않는지, 다른 조사를 열었을 때 R38이 임의의 기본값으로 들어가지 않는지 확인한다. 모델을 다시 학습시키는 흐름에서는 별도 데이터 승인과 평가, 모델·프롬프트 버전 관리가 필요하다. 이번 예제의 선호 변경은 SQLite에 새 값을 저장하는 앱 동작이다. [LongMemEval의 정보 갱신과 보류 평가](https://arxiv.org/abs/2410.10813)
