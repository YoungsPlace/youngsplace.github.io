레이더 시험 데이터를 정리하는 도우미에 “오늘 검증 결과를 요약해 줘”라는 요청과 “R42에서 탐지율이 떨어진 이유를 찾아줘”라는 요청을 넣었다고 가정한다. 정기 보고에는 시험 설정, 측정 결과, 합격 기준이 필요하다. 원인 조사에서는 첫 조회를 끝내야 다음에 읽을 자료를 알 수 있다. 펌웨어와 시험 조건이 동시에 바뀌었다면 한 가지를 고정하고 비교한 시험부터 찾는다.

두 경우 모두 마지막에는 모델이 보고서를 작성할 수 있다. 실행 구조를 나눌 때는 **어떤 자료를 확인할지 언제 결정할 수 있는지**부터 봤다. 아래 시험 ID, 수치, 실행 경로는 설계를 설명하기 위한 가정이다.

## 1. 실행 경로를 정하기

### 정기 보고는 읽을 자료를 먼저 정할 수 있다

보고서에 들어갈 세 자료의 시험 ID가 정해져 있다. 시험 설정과 측정 결과를 동시에 읽을 수 있고, 기준표도 별도로 가져올 수 있다. 실행기는 세 응답에 같은 시험 ID와 유효한 기준 버전이 들어 있는지 확인한다. 그 다음 모델이 각 수치와 단위를 유지하며 보고서 문장으로 정리한다.

고정 워크플로에도 분기가 있다. 측정 결과가 아직 없으면 수집 대기 상태를 반환하고, 기준표가 두 개면 시험 날짜에 유효했던 버전을 고른다. 어느 조건에서 어느 단계를 실행할지는 미리 정할 수 있다.

### 원인 조사는 관찰을 읽고 다음 단계로 넘어간다

R41과 R42의 설정을 비교했더니 펌웨어 버전과 안테나 각도가 바뀌었다고 하자. 변경 기록에서 비슷한 증상이 발견됐다면 펌웨어를 후보로 둘 수 있다. 다음에는 같은 각도에서 펌웨어만 다른 시험을 찾는다. 각도별 기록에 표본이 부족하면 환경 로그나 다른 기준 시험이 필요해질 수 있다. 이 경로에서는 앞 단계의 관찰이 다음 조회를 정한다.

| 구조 | 다음 단계가 정해지는 시점 | 적용한 상황 |
|---|---|---|
| 로직 트리 | 조건과 분기를 코드로 미리 정한다. | 입력에 시험 ID가 없으면 다시 요청한다. |
| 프롬프트 체인 | 단계와 순서는 미리 정하고 앞 단계의 값을 다음 단계에 넘긴다. | 기준표 추출, 단위 확인, 보고서 작성 순서로 처리한다. |
| 라우팅 | 입력을 분류해 준비된 경로에 보낸다. | 정기 보고와 원인 조사를 갈라서 처리한다. |
| 고정 병렬 실행 | 이미 아는 독립 작업을 함께 시작한다. | 설정, 측정값, 기준표를 읽는다. |
| 감독자–작업자 | 감독자가 이번 요청에 필요한 하위 작업을 골라 배정한다. | 영향 가능성이 있는 시험이나 부서를 찾아 조사를 나눈다. |
| 관찰 기반 루프 | 도구 응답을 받은 뒤 다음 행동을 정한다. | 비교 후보를 검색하고 근거가 부족하면 조사 경로를 바꾼다. |

라우터를 모델로 구현해도 분류 결과가 들어갈 실행 경로는 코드로 정할 수 있다. 감독자가 하위 작업 대상을 고르고, 각 작업자가 정해진 절차대로 조회하는 구성도 가능하다. 하위 작업의 **선택**과 실제 **실행**을 나눠 보면, 모델을 어느 단계에 써야 하는지 판단하기 쉽다. [Anthropic의 워크플로와 에이전트 설계 패턴](https://www.anthropic.com/research/building-effective-agents) · [독립 조회의 순차·병렬 실습](/agentic-ai/orchestration/)

## 2. 모델의 제안에서 도구 실행까지

모델이 `compare_runs(R41, R42)`를 제안하면 실행기는 도구와 인자를 읽고 사용자의 접근 범위, 이번 조사 단계, 이미 확인한 결과를 검사한다. 실행기는 도구의 응답을 관찰로 남긴 뒤 필요한 경우 다시 모델을 호출한다.

| 검사 위치 | 이 예제에서 확인하는 것 |
|---|---|
| 도구 입력 형식 | 이름이 등록돼 있고 두 인자 모두 유효한 시험 ID인가 |
| 접근 범위 | 요청자가 R41과 R42의 결과를 읽을 수 있는가 |
| 실행 선행 조건 | 이번 조사에서 비교하기로 한 대상인가, 아직 확인이 필요한 조회인가 |
| 종료 조건 | 최종 주장과 비교 조건을 뒷받침하는 근거를 확보했는가 |

JSON 스키마로 값의 형태를 검사한 뒤에도 상태와 접근 범위 확인이 남는다. 예를 들어 `R42`가 시험 ID 형식에 맞아도 다른 팀의 자료라면 현재 요청에서 조회할 수 없다. 결과에 출처 ID가 붙어 있어도, 해당 문서가 보고서의 원인 판단을 지지하는지는 별도로 확인한다. [도구 호출과 상태별 실행 조건 실습](/agentic-ai/agent-loop/)

### ReAct에서 관찰을 쓰는 방식

ReAct에서 모델의 판단과 행동은 번갈아 진행된다. 검색이나 조회가 끝나면 환경에서 받은 관찰을 다음 입력으로 넣는다. 이 예제에서는 변경 기록에 비슷한 증상이 있다는 관찰이 “같은 각도의 비교 시험을 찾는다”는 다음 행동으로 이어진다. 추론을 길게 쓰는 것보다 새 자료로 **어떤 조사 단계가 추가되거나 제외됐는지**가 실행 기록에 남는 편이 확인하기 쉽다. [ReAct 원 논문](https://arxiv.org/abs/2210.03629)

```text
목표          R42의 탐지율 하락 원인 조사
완료한 조회    R41·R42 설정 비교, 변경 문서 D23 확인
관찰          펌웨어와 각도가 함께 바뀜
다음 확인      같은 각도에서 펌웨어만 다른 시험
완료 조건      비교 조건을 확인하고 결론에 근거를 연결
종료 한도      남은 조회 2회, 전체 마감까지 15초
```

비슷한 증상의 문서를 찾았다는 관찰은 후보를 좁히는 데 쓰인다. 펌웨어를 원인으로 확정하려면 환경과 장비 조건을 맞춘 비교가 더 필요하다. 근거가 부족한 채 기한이 끝나면, 확인한 변경과 남아 있는 가설을 구분해 결과를 반환할 수 있다.

도구 오류도 다음 판단에 필요한 관찰이다. `no_result`는 정상 조회를 끝내고 후보가 없었다는 뜻이다. `timeout`은 조회 결과를 얻지 못한 상태다. 전자에는 다른 조건으로 찾아볼 수 있고, 후자에는 남은 시간 내에서 같은 읽기를 다시 시도할 수 있다. 성공한 중복 요청을 확인하려면 도구 이름과 정규화된 인자, 결과 상태를 함께 기록한다. 같은 문서라도 버전이 바뀌면 새 관찰이 생길 수 있다. [재계획과 타임아웃 실습](/agentic-ai/replanning/) · [AWS의 타임아웃과 재시도 설계](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

## 3. 메모리는 누가 언제 다시 읽는지에 따라 나눈다

현재 프롬프트에 넣은 관찰, 같은 조사를 재개할 때 필요한 데이터, 다른 조사에서도 쓰는 사용자 선호는 범위가 다르다. R42 건에서 사용자가 정한 정상 시험은 그 조사에 보관한다. 여러 보고서에서 계속 쓸 수 있도록 사용자가 확인한 단위나 양식은 사용자 범위에 둘 수 있다.

| 보관 범위 | R42 조사에서 두는 정보 | 다시 읽는 조건 |
|---|---|---|
| 모델 컨텍스트 | 현재 질문, 다음 판단에 필요한 관찰과 후보 | 이번 모델 호출 |
| 실행 상태 | 확인한 시험 ID, 완료한 도구 호출, 남은 예산 | 같은 조사 실행 중 |
| 체크포인트 | 중단 시점의 상태, 대기 질문, 근거 참조, 재개 위치 | 같은 실행을 다시 이어 갈 때 |
| 장기 메모리 | 보고서의 단위와 양식처럼 확인된 선호 | 같은 사용자의 다른 실행에서 관련 있을 때 |
| 업무 데이터 | 측정 원본, 펌웨어 이력, 현행 판단 기준 | 출처와 버전이 필요한 업무 조회 |

컨텍스트를 새로 조립할 때는 이번 단계에 필요한 기록을 골라 넣는다. 앱이 데이터베이스에 저장한 기록은 프롬프트에 붙이거나 도구로 가져와야 모델이 읽는다. 체크포인트는 모델 응답을 생성할 때마다 통째로 넘기기보다, 실행을 복구하는 앱에서 먼저 읽을 수 있다. [LangGraph의 체크포인터와 스토어](https://docs.langchain.com/oss/python/langgraph/persistence) · [프로세스 재시작에서 상태를 읽는 실습](/agentic-ai/memory-layers/)

### 중단 뒤 같은 조사로 돌아오기

비교 시험을 하나 골라야 하는 시점에 실행이 멈췄다면, 체크포인트에 조사 ID, 소유자, 완료한 단계, 근거 ID, 대기 조건을 둔다. 대화 요약에 “시험 비교를 하고 있었다”가 남아 있으면 사람이 맥락을 읽을 수 있다. 실행을 이어 가려면 “설정 비교는 끝났고, R38과 R41 중 기준을 고르면 측정값 조회를 시작한다”는 상태가 필요하다.

재개할 때는 이미 끝난 작업을 확인하는 것과 그 결과가 지금도 유효한지 확인하는 것을 구분한다. 예를 들어 문서의 버전이 바뀌었다면 기존 결과를 보여 주면서 재조회할 수 있다. 보고서를 이미 다른 시스템에 등록했을 가능성이 있는 경우에는 같은 요청 ID의 처리 여부를 먼저 본다. 타임아웃 뒤 응답이 유실됐어도 서버에 상태 변경이 반영됐을 수 있다. 이때 같은 요청이 동일한 효과를 만드는 멱등성 계약이 필요하다. [동시 요청과 커밋 복구 실습](/agentic-ai/lab-assistant/)

## 4. MCP와 A2A를 어디에 쓰는가

문서 서버에 검색과 본문 읽기 기능이 있다면 앱은 **MCP**로 연결해 해당 기능을 발견하고 사용할 수 있다. MCP 호스트는 AI 애플리케이션이며, 호스트의 클라이언트가 MCP 서버에 연결한다. 서버는 호출할 도구, 읽을 리소스, 재사용할 프롬프트를 제공할 수 있다. 이 구조에서 사용자의 접근 권한과 도구 실행 조건은 앱과 서비스에서 따로 확인한다. [MCP 아키텍처 개요](https://modelcontextprotocol.io/docs/learn/architecture)

별도 팀의 장비 진단 시스템이 자체 도구와 실행 상태를 가진 에이전트라면 **A2A**로 조사 과제를 넘길 수 있다. 서버가 즉시 메시지를 보내거나 장시간 추적할 작업을 반환할 수 있고, 작업 ID로 상태를 확인한다. 상대가 추가 입력을 요청할 때는 같은 작업에 조건을 전달한다. 결과는 산출물로 받아 원래 조사와 연결한다. [A2A 공식 사양](https://a2a-protocol.org/latest/specification/)

| 경계 | R42 조사에서 맡기는 일 | 반환값에서 확인할 것 |
|---|---|---|
| 앱 ↔ 도구 서버 | 허용된 시험 ID나 문서를 조회한다. | 조회 상태, 원본 ID, 버전, 필요한 필드 |
| 감독자 ↔ 별도 진단 에이전트 | 펌웨어 변경과 비교 조건을 함께 조사한다. | 과제 ID, 상태, 입력 조건, 출처가 붙은 분석 결과 |

감독자가 상대 에이전트에게 전달하는 값에는 조사 목표, 시험 ID, 사용할 수 있는 자료의 범위, 기대 산출물이 들어간다. 여러 작업자가 결과를 돌려주면 감독자는 원래 요청의 시험과 비교 조건이 유지됐는지 먼저 확인한다. A2A로 과제를 위임받은 진단 에이전트가 자기 쪽 문서 서버에 MCP로 연결하는 구성도 가능하다.

## 5. 지식 그래프로 관계를 따라가기

“변경 C17과 연결된 펌웨어를 사용한 시험을 모두 찾고, 변경 내용을 설명해 줘”라는 요청에는 두 종류의 데이터가 필요하다. 어떤 시험을 포함할지는 시험·펌웨어·변경의 관계로 정한다. 변경한 이유와 부작용은 연결된 문서에서 읽는다.

```text
R42 ──사용함──▶ FW-2.3 ──포함함──▶ C17 ──문서화됨──▶ D23
R43 ──사용함──▶ FW-2.3
R38 ──사용함──▶ FW-2.2
C17 ──수정함──▶ CFAR 설정
```

변경 C17을 포함하는 펌웨어에서 역방향으로 따라가면 기록상 R42와 R43을 찾는다. D23을 읽으면 변경 이유와 적용 범위를 설명할 수 있다. RDF에서는 개별 관계를 주어, 술어, 목적어로 표현한다. 관계가 일정하고 이미 구조화된 데이터베이스에 들어 있다면 SQL 조인으로도 조회할 수 있다. 여러 종류의 관계를 자주 이어서 읽을 때 그래프 형태가 자연스럽다. [W3C RDF 데이터 모델](https://www.w3.org/TR/rdf11-concepts/#section-triples)

임베딩 검색은 D23과 내용이 비슷한 문서를 찾을 때 쓸 수 있다. 시험 목록을 완전하게 구해야 할 때는 등록된 관계와 원본 수집 범위를 확인한다. 펌웨어 필드가 빠진 시험이 있다면 조회 결과는 “현재 기록으로 확인한 시험”까지 답할 수 있다. 그래프에서 관계가 보이지 않을 때는 사실이 없다는 판단을 내리기 전에 수집 누락을 확인한다. [W3C RDF 의미론](https://www.w3.org/TR/rdf11-mt/) · [문서 검색과 출처 실습](/agentic-ai/rag/)

## 6. 사람 확인을 화면과 실행 상태에 연결하기

R42에 대한 비교 후보가 둘 있다고 하자. 사용자에게 “기준 시험을 선택해 주세요”라고만 표시하는 것보다, “R41은 장비가 같고 R38은 안테나 각도가 같다”는 판단 조건을 보여 주는 편이 선택하기 쉽다. 앱은 대기 질문과 후보, 완료한 조회, 재개 위치를 같은 조사 ID에 남긴다.

{{< mermaid >}}
stateDiagram-v2
    [*] --> Investigating
    Investigating --> WaitingInput: 비교 기준 필요
    WaitingInput --> Investigating: 같은 조사에 조건 입력
    Investigating --> Partial: 근거 또는 예산 부족
    Investigating --> DraftReady: 근거 확보
    DraftReady --> WaitingApproval: 사용자가 등록 요청
    WaitingApproval --> Registered: 내용과 대상 확인 후 등록
    WaitingApproval --> DraftReady: 내용 변경 또는 승인 만료
{{< /mermaid >}}

**조사 조건을 묻는 것**과 **외부에 결과를 반영해도 되는지 묻는 것**을 나눴다. 앞 단계에서 사용자가 R38을 기준으로 선택하면 측정 비교가 이어진다. 보고서 등록 단계에는 어느 시스템으로 어떤 버전을 보낼지 표시한다. 승인 기록도 실행 ID, 대상, 보고서 버전, 만료 조건에 연결한다. 오래 대기한 요청을 재개할 때는 현재 권한, 자료 버전, 등록할 내용이 여전히 일치하는지 확인한다. [확인한 값과 실행할 요청을 대조하는 실습](/agentic-ai/approval/)

## 7. 확장할 때 병목을 찾는 순서

### 독립 단계만 병렬로 보내기

가상의 지연으로 설정 비교 250ms, 변경 기록 조회 300ms, 측정 데이터 조회 500ms, 결과 종합 200ms를 넣었다. 두 조회는 모두 설정 비교 결과가 필요하다. 그 뒤에는 서로 독립적으로 시작할 수 있다.

| 경로 | 계산 | 걸리는 시간 |
|---|---|---:|
| 순차 | `250 + 300 + 500 + 200` | 1,250ms |
| 설정 비교 뒤 병렬 조회 | `250 + max(300, 500) + 200` | 950ms |

이 조건에서는 측정 데이터 조회가 임계 경로에 들어간다. 변경 기록 조회를 300ms에서 100ms로 줄여도 전체 시간은 950ms다. 실제 환경에서는 공유 저장소의 큐, 동시 호출 제한, 결과 병합 시간까지 측정한다. 장비 목록처럼 선택적인 자료와, 합격 판단에 필요한 기준표처럼 필수인 자료를 구분하면 일부 도구가 느릴 때 어느 결과를 먼저 보여 줄 수 있는지 판단하기 쉽다. [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/) · [동시성에 따른 실측 비교](/agentic-ai/orchestration/#병렬-실행-시간을-정하는-임계-경로)

### 긴 조사에서 줄일 것과 보존할 것

모델을 N번 부르면서 이전 도구 응답을 매번 모두 보낸다고 가정한다. 각 관찰이 비슷한 크기라면 누적 전달량은 `0 + 1 + … + (N−1)`에 비례한다. 현재 프롬프트에는 다음 단계에 필요한 사실을 짧게 두고, 원본은 근거 ID로 읽을 수 있게 하면 반복 전송량을 줄일 수 있다. 비교 조건의 예외, 버전, 단위처럼 결과를 바꿀 값은 요약에서 빠지지 않는지 따로 확인한다. [컨텍스트 토큰 예산과 체크포인트](/agentic-ai/memory-layers/)

적응성을 확인할 때는 바뀐 부분을 특정한다. 검색 서비스 API가 바뀌면 도구 어댑터와 반환 계약을 확인한다. 모델이 바뀌면 같은 입력과 관찰을 주고 선택한 도구·인자를 비교한다. 승인 정책이 바뀌면 실행기의 규칙과 재개 중 검사에 반영한다. 실행 로그의 모델과 도구 계약 버전은 이런 차이를 추적할 때 쓰인다.

## 8. 설계안을 검토할 때 남긴 기준

정기 보고는 세 자료가 **같은 시험과 유효한 기준 버전**을 가리키는지, 수치의 단위가 바뀌지 않았는지를 본다. 원인 조사는 **새 관찰이 다음 조회를 어떻게 바꿨는지**, 비교 조건과 근거를 확보했는지, 보류해야 할 부분은 보류했는지를 본다. 에이전트 위임과 사용자 확인이 들어가면 **부분 실패가 최종 결과에 표시되는지**, **같은 조사로 돌아오는지**, **이미 완료한 외부 작업이 반복되는지**도 확인한다.

한 번의 실행을 다시 읽을 때는 `run_id`, 도구와 인자, 출처 ID와 버전, 상태 전환, 종료 이유를 연결한다. 정답 문장에 14%라는 숫자가 맞게 들어갔더라도 잘못된 시험에서 가져온 값이면 실패다. 반대로 비교 조건이 부족한 상태에서 확인한 사실만 반환했다면, 중단 사유까지 포함해 요구된 동작인지 평가할 수 있다. [도구 경로, 근거, 성공 조건을 나눠 평가한 실습](/agentic-ai/evaluation/)
