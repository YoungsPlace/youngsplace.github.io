“R41을 기준으로 R42가 얼마나 달라졌는지 보여 줘.” 이 요청에서 필요한 것은 대상 시험 R42, 기준 시험 R41, 비교 연산이다. 두 식별자는 문장에 나타난 순서와 역할이 다를 수 있다. 화면 캡처에 기준 시험 항목이 없다면 비교할 값을 다시 받아야 한다. 도구가 보낸 결과와 타임아웃도 구분해서 처리해야 한다.

1장에서 정기 보고와 원인 조사의 실행 경로를 나눴다. 이번에는 문장에서 추출한 정보를 검사해 두 시험의 탐지율을 읽는 작은 도구를 붙였다. 이미지에서는 화면의 시험 ID를 구조화된 필드로 추출했다. 시험 ID와 측정값은 실습을 위한 합성 데이터다. [1장 에이전트 아키텍처와 설계](/ncp-aai/chapter-01-agent-architecture/)

## 1. 프롬프트와 실행 단계를 연결하기

모델에 두 시험의 결과를 비교하라고 바로 요청하면, 모델은 먼저 비교 방향을 이해하고 자료의 존재를 확인한 뒤 계산해야 한다. 예제에서는 첫 호출에서 요청 의도와 ID만 추출한다. 실행기는 그 값을 검사해 조회하거나 입력을 다시 받는다. 유효한 값이 모이면 앱이 계산하고 조회한 출처를 결과에 붙인다.

{{< mermaid >}}
flowchart TD
    I["질문 또는 시험 화면"] --> P["모델 · 의도와 시험 ID 추출"]
    P --> V["실행기 · 출력과 조회 범위 검사"]
    V -->|필수 ID 없음| Q["누락된 대상이나 기준 입력 요청"]
    V -->|조회 가능| T["등록된 도구로 시험 결과 조회"]
    V -->|지원 범위 밖| X["처리할 수 있는 요청 범위 안내"]
    T -->|일시 타임아웃| R["정해 둔 횟수만 재시도"]
    R --> T
    T -->|측정값과 출처 확보| A["조회 값 또는 비교 결과 반환"]
    T -->|자료 없음 또는 호출 한도 도달| W["구분된 상태와 이유 반환"]
{{< /mermaid >}}

모델에 전달한 스키마에서 `intent`는 조회, 비교, 지원 범위 밖의 요청 중 하나다. `target`은 평가할 시험, `baseline`은 비교 기준이다. 문장에 필요한 ID가 없으면 해당 칸에 `null`을 넣는다.

```json
{
  "intent": "compare",
  "target": "R42",
  "baseline": "R41"
}
```

구조화 출력은 응답에 필요한 키와 형식을 정한다. 위 객체의 키와 값이 전부 스키마에 맞아도, 모델이 대상과 기준을 뒤집었거나 단일 조회를 비교로 분류했을 수 있다. **파싱이 됐는지**, **사용자의 의도를 제대로 읽었는지**, **실행할 수 있는 조건을 갖췄는지**를 따로 확인했다. [Ollama Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)

| 추출된 값 | 실행 경로 |
|---|---|
| `lookup`, R42 | R42의 탐지율과 출처 반환 |
| `compare`, R42와 R41 | 두 값을 읽고 대상에서 기준을 뺀 값 반환 |
| `compare`, R42와 `null` | 기준 시험을 받을 때까지 대기 |
| `unsupported` | 조회 도구를 실행하지 않고 요청 범위 반환 |

프롬프트 체인에서 모든 요청이 같은 단계로 가면 경로를 미리 정할 수 있다. 입력 방식에 따라 이미지 해석을 추가하거나, 누락된 정보가 돌아올 때만 다음 단계를 부르는 경우에는 실행 경로가 입력과 관찰에 따라 바뀐다. 이번 예제는 모델이 의도와 ID를 제안하고 앱의 조건문이 이후 경로를 결정한다. [1장의 라우팅과 프롬프트 체인](/ncp-aai/chapter-01-agent-architecture/) · [Anthropic의 프롬프트 체인과 라우팅](https://www.anthropic.com/research/building-effective-agents)

## 2. 이미지와 음성도 같은 업무 입력으로 받기

텍스트 질문과 캡처는 표현 방식이 다르지만, 비교 도구에는 대상과 기준 ID가 필요하다. 이미지에서 읽은 값도 같은 필드에 담으면 두 입력 방식에 동일한 검사를 적용할 수 있다. 다만 입력을 해석한 값의 출처가 달라지므로, 어느 화면의 어느 항목에서 읽었는지와 원본 파일을 연결해 두면 재검토하기 쉽다.

| 입력 | 전처리에서 만드는 값 | 실행 전 확인할 것 |
|---|---|---|
| 텍스트 | 의도, 대상 ID, 기준 ID | 두 ID의 역할과 필수 항목 |
| 이미지 | 화면에 표시된 라벨과 ID | 항목 누락과 오독, 원본 화면의 정보 |
| 음성 | 전사문과 필요한 경우 언어·구간 정보 | 고유명사, 숫자, 단위와 사용자가 정정한 값 |

### 보이는 항목만 읽게 하기

Gemma 3 4B에 두 가지 합성 화면을 넣었다. 하나에는 `TARGET RUN`과 `BASELINE RUN`이 있고, 다른 화면에는 `TARGET RUN`만 있다. Ollama REST API에는 이미지를 base64로 인코딩해 사용자 메시지의 `images`에 넣었다. 출력 스키마는 `target`과 `baseline`을 각각 문자열이나 `null`로 받는다. [Gemma 3 모델 카드](https://ai.google.dev/gemma/docs/core/model_card_3) · [Ollama Vision](https://docs.ollama.com/capabilities/vision)

두 입력을 각각 한 번 실행했다. [기준 항목이 없는 두 번째 합성 화면](run-panel-target-only.png)에서는 모델이 빈 항목을 `null`로 반환했다. 이 추출 결과로 곧바로 비교를 시작할지 여부는 앱에서 정한다. 위 코드의 `--image`는 식별자 추출까지 수행한다.

이미지 판독은 값의 원래 위치를 파악하는 단계다. 앱이 R42의 현재 결과를 알려 줄 때는 시험 ID를 받아 원본 시험 자료를 다시 읽는다. 모델이 이미지에서 84를 읽었더라도, 그 화면이 어떤 시점에 만들어졌는지와 현재 조회 값은 각각 다룰 수 있다.

음성 입력은 전사 단계에서 오차가 들어올 수 있다. 예전에 MLX Whisper를 사용한 합성 WAV 실습에서는 잡음이 섞인 문장의 ‘인식’이 한 모델에서 ‘민식’으로 전사됐다. 시험 ID와 단위를 읽을 때도 음성이 비슷한 값이 나올 수 있다. 전사문을 확인하거나 수정할 수 있게 하고, 검증을 통과한 값을 도구에 넘기는 흐름으로 연결한다. [합성 WAV와 MLX Whisper 실습](/local-ai-models-on-a-mac/week-03/)

## 3. 도구가 맡는 범위와 반환값 정하기

예제의 조회 도구는 시험 ID를 받아 탐지율과 출처 ID를 반환한다. 합성 데이터에서 R41은 92.0%, R42는 84.0%다. 비교에서는 `대상 − 기준`을 계산한다. R42를 R41 기준으로 비교하면 **−8.0퍼센트포인트**다. 상대 변화율이 필요하면 `(84−92)/92`로 계산하며 약 −8.7%가 된다. 같은 두 숫자에서도 요구된 단위에 따라 표시 값이 달라진다.

| 도구 계약 | 예제의 값 |
|---|---|
| 입력 | 시험 ID 한 개 |
| 정상 결과 | 탐지율, 출처 ID |
| 정상 조회에서 결과 없음 | `not_found` |
| 일시 실패 | `timeout` |
| 등록 또는 외부 발송 | 예제의 조회 경로에서 지원 범위 밖으로 분류 |

[실행 코드](report_agent.py)는 Ollama의 `format`으로 모델이 제안하는 객체의 구조를 맞춘다. Python은 의도와 ID를 확인한 뒤 등록된 조회를 실행하고, 결과를 받아 수치를 계산한다. Ollama의 네이티브 도구 호출에서는 모델이 `tool_calls`로 도구 이름과 인자를 제안할 수 있다. 실행기가 함수를 실행하고 그 결과를 `tool` 메시지로 다시 넘기는 구조다. 이 글의 코드에서는 간단한 구조화된 제안을 실행기에서 직접 해석했다. [Ollama Tool Calling](https://docs.ollama.com/capabilities/tool-calling)

운영 서비스에서는 스키마 검사 뒤 사용자 권한을 다시 확인한다. 형식에 맞는 시험 ID라도 다른 팀의 자료일 수 있다. 검색된 문서나 이미지에서 읽은 문장에 발송이나 등록 요청이 들어 있어도, 그 내용은 모델이 읽은 입력이다. 사용자가 승인한 동작과 접근 범위는 실행기가 관리하는 별도 상태로 다룬다. [승인과 실행 범위를 나누는 실습](/agentic-ai/approval/)

## 4. 실패 원인에 따라 복구 경로를 나누기

입력이 비어 있으면 사용자에게 필요한 값을 받아야 한다. 결과가 없는 시험은 같은 조회를 다시 해도 자료를 얻기 어렵다. 타임아웃 같은 일시 문제에서만 같은 읽기를 제한된 횟수로 다시 시도했다.

| 상태 | 다음 동작 |
|---|---|
| `needs_input` | 어느 값이 필요한지 표시하고 다음 입력을 기다린다. |
| `not_found` | 조회한 ID를 보여 주고 올바른 ID를 확인한다. |
| 첫 `timeout` | 읽기 도구를 한 번 더 시도한다. |
| 연속 `timeout` | `tool_unavailable` 상태로 반환한다. |
| 지원 범위 밖 | 등록이나 발송을 실행할 수 있는 다른 경로가 필요하다고 안내한다. |

합성 타임아웃을 한 번 넣었을 때 R41 조회는 `timeout → ok`로 끝났다. 두 번 넣었을 때 R42 조회는 `timeout → timeout` 뒤 `tool_unavailable`로 중단됐다. R99는 첫 조회에서 `not_found`로 끝났다. 타임아웃은 모의 도구가 반환한 상태이며, 네트워크 대기 시간은 측정하지 않았다.

재시도 외에 서비스 전체의 접근을 잠시 제한하는 **서킷 브레이커**도 있다. 연속 실패가 쌓이면 호출을 잠시 차단하고, 대기 뒤 제한된 호출을 보내 회복 여부를 본다. 하나의 읽기 시도에서 할 수 있는 재시도와, 여러 요청에 걸쳐 실패하는 서비스에 접근할 수 있는지는 다른 범위다. 실패한 요청이 쌓일 때는 백오프, 지터, 전체 마감 시간을 함께 적용한다. 쓰기에서 응답을 놓쳤다면 같은 요청이 이미 반영됐는지 확인하고, 서버가 동일한 요청을 중복 반영하지 않도록 멱등성 키를 쓸 수 있다. [Circuit Breaker · Microsoft Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker) · [AWS의 타임아웃과 재시도](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

## 5. 스트리밍 응답과 실행 상태를 따로 표시하기

채팅 화면의 스트리밍에는 다른 종류의 정보가 섞일 수 있다. 모델이 생성 중인 답변 조각을 표시하는 것과, 도구의 조회 시작·종료·실패를 사용자에게 알리는 것은 별도의 이벤트로 다룰 수 있다.

```jsonl
{"type":"status","run_id":"q17","state":"validating_request"}
{"type":"status","run_id":"q17","state":"waiting_for_baseline"}
{"type":"needs_input","run_id":"q17","field":"baseline"}
```

위 예시는 앱에서 정의할 수 있는 이벤트 형식이다. 사용자가 R41을 입력하면 같은 `run_id`에서 비교를 재개한다. 일반 텍스트 조각, 상태 변경, 사용자 입력 요청을 구분하면 “기준 입력이 필요하다”는 말을 최종 보고서 일부로 저장하는 일을 줄일 수 있다.

Ollama에서 스트리밍을 켜면 엔드포인트에 따라 줄 단위 JSON(NDJSON)으로 응답을 보낸다. 각 줄을 읽어 텍스트 조각을 연결하고 마지막 이벤트에서 생성 완료를 판단한다. 구조화된 계획이나 도구 인자는 객체 전체가 준비된 뒤 파싱하고 실행한다. UI에 출력 중인 글자가 보인다고 아직 수신 중인 JSON을 바로 도구에 전달할 필요는 없다. 이번 비교 코드는 계획 전체를 받은 뒤 처리했고, 로컬 모델의 첫 조각과 최종 응답을 나누어 잰 실험은 앞선 서빙 글에 정리했다. [Ollama Streaming](https://docs.ollama.com/api/streaming) · [로컬 스트리밍 지연 측정](/agentic-ai/serving/)

사용자가 “기준과 대상이 바뀌었음”을 표시했다면, 피드백에는 의도, 기존 계획, 수정한 필드, 어떤 결과를 보여 줬는지를 연결한다. 승인 클릭은 해당 실행에 대한 상태 변화다. 답변 만족도와 승인 신호는 각각 품질 평가와 실행 검사에 사용한다. 이후 프롬프트 평가에 쓰면서도 실제 대화의 보존 범위를 업무 요구에 맞출 수 있다.

## 6. 프롬프트를 바꿔도 같은 입력으로 결과 대조하기

같은 합성 요청 아홉 개를 Gemma 3 4B에 넣었다. 환경은 Apple M5 Pro, Python 3.13.18, Ollama 0.40.11이었다. 로컬 모델 ID는 `68ceab7e468a`다. 입력 스키마와 도구 코드를 고정하고 `temperature=0`, `seed=42`, `num_ctx=4096`, 최대 출력 96토큰을 적용했다. [실행 코드 다운로드](report_agent.py)

```bash
ollama pull gemma3:4b
python3 report_agent.py --prompt v1
python3 report_agent.py --prompt v2
python3 report_agent.py --prompt v3
```

같은 문장이더라도 의도, 대상, 기준이 모두 맞아야 **계획 일치**로 센다. 최종 실행 상태는 따로 비교했다. 대상과 기준을 뒤집고 두 값을 모두 읽어도 최종 상태는 `ok`일 수 있다. 이 경우 실행 상태는 일치하지만 계획과 차이의 부호는 틀린다.

| 버전 | 바꾼 지시 | 계획 일치 | 실행 상태 일치 |
|---|---|---:|---:|
| v1 | 비교 문장 속 두 ID를 등장 순서로 해석 | 8/9 | 8/9 |
| v2 | ‘대상’, ‘기준’ 역할을 표현한 단어를 우선 | 8/9 | 8/9 |
| v3 | 의도를 먼저 고르고 단일 조회와 기준 없는 비교의 예시를 추가 | 9/9 | 9/9 |

v1과 v2는 “Show the result of R42.”에 `{"intent":"compare","target":"R42","baseline":null}`을 반환했다. 모델 출력은 파싱됐지만 실행기는 기준 ID가 없어서 `needs_input`을 반환했다. 비교 방향에 관한 지시를 바꿔도 단일 조회와 비교를 구분하는 문제는 그대로였다.

v3에는 “시험 하나의 결과를 읽어 달라”와 “기준이 빠졌지만 비교할 것을 요청했다”를 구분하는 예시를 넣었다. 같은 문장을 다시 실행하니 `lookup`으로 분류됐고 R42의 **84.0%**와 출처 `synthetic:R42@1`이 반환됐다. 처음부터 비교 목적이 분명했던 “Compare R42 with the baseline.”에서는 기준을 추측하지 않고 `needs_input`을 유지했다. R42와 R41을 각각 기준으로 바꿔 비교한 두 경우에는 −8.0과 +8.0퍼센트포인트가 나왔다.

설정 변경의 효과를 볼 때는 세 단계에 기대값을 둔다.

1. **계획**에서 대상과 기준을 올바르게 구분했다.
2. **실행**에서 입력이 빠진 경우 조회를 멈추고, 타임아웃만 재시도했다.
3. **결과**에서 올바른 시험과 단위로 값과 출처를 반환했다.

이번 아홉 요청은 변경 전후를 비교하는 작은 진단 묶음이다. 실제 사용에서는 새 표현과 다른 언어, 여러 의도가 섞인 요청, 모호한 이미지, 현재 볼 수 없는 자료를 따로 모아 비교한다. 그래야 한 오류를 줄였을 때 다른 경로가 나빠졌는지, 모델 판단에 드는 추가 호출이 가치가 있는지를 함께 볼 수 있다. [검색, 실행, 정확도를 나눠 평가한 실습](/agentic-ai/evaluation/)
