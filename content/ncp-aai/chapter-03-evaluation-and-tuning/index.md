R42와 R41을 비교해 달라는 요청에 도우미가 두 시험을 모두 조회하고도 차이를 거꾸로 계산할 수 있다. 숫자가 맞아도 R42의 출처를 찾지 못한 상태에서 답을 추측했을 수 있다. 비교 기준이 없는 요청이라면 다시 묻는 것이 목표를 충족한다. 평가할 때는 최종 문장과 함께 실행 경로를 읽어야 어떤 단계가 결과를 바꿨는지 알 수 있다. [2장의 도구 실행 결과](/ncp-aai/chapter-02-agent-development/)

NCP-AAI의 Evaluation and Tuning은 공식 웹 출제표에서 13%다. 학습 가이드 3.1–3.5는 평가 파이프라인과 과업 벤치마크, 과업·데이터셋 비교, 구조화된 사용자 피드백, 성능 튜닝, 결과 분석을 다룬다. ## 1. 평가 파이프라인에 무엇을 저장할까

평가 입력에는 요청 문장, 데이터의 상태, 가능하면 시행 당시의 버전과 허용한 도구를 둔다. 정답은 문자열 하나로 고정하기보다 관찰할 수 있는 성공 조건을 적는다. 검증 도우미의 비교 과업에는 대상과 기준의 ID, 차이의 부호와 단위, 양쪽에 사용한 출처 ID가 들어간다. 조회 불가 과업에는 잘못된 답을 출력하지 않고 보류하는 조건을 둔다.

    D --> E["유형과 실패 단계별로 비교"]

| 평가 단위 | 검증 도우미에서 보는 값 |
|---|---|
| 경로 | 조회, 비교, 추가 질문 중 맞는 동작을 골랐는가 |
| 도구 호출 | 알맞은 시험 ID를 전달했고 결과 상태를 제대로 해석했는가 |
| 결과 | 수치, 부호, 단위와 출처가 요청에 맞는가 |
| 보류 | 근거 없는 경우를 구분하고, 답할 수 있는 요청을 지나치게 막지 않았는가 |
| 운영 비용 | 모델 호출 수, 입력·출력 토큰, 도구 수, 완료 시간은 얼마인가 |

숫자와 ID처럼 확실한 값은 코드로 비교할 수 있다. 답변이 출처의 주장을 지지하는지는 정답 문서나 사람의 검토 기준이 필요할 수 있다. 모델 평가자를 쓰면 판단 기준, 평가 모델 버전과 예시를 기록한다. 정답 형식만 다른 경우나 답이 여러 개 있는 경우를 사람과 대조해 평가자가 어느 유형에서 흔들리는지도 확인한다. 모델 한 번의 출력과 도구 실행 전체를 다른 단위로 평가하는 이유다. [AI Agents That Matter · Kapoor 외](https://arxiv.org/abs/2407.01502)

## 2. 과업과 데이터셋을 나눠 비교하기

단일 조회와 비교는 호출 수부터 다르다. 조회를 잘 맞혀도, 비교 기준이 빠졌을 때 계속 답을 만드는 정책은 현장에서 문제가 될 수 있다. 조회, 비교, 모호한 요청, 근거가 없는 요청을 유형별로 나눴다. 같은 템플릿에서 시험 ID만 바꾼 입력이 개발·평가에 섞이면, 평가가 실제로 새 문제를 보는지 판단하기 어렵다. 과업 종류나 원본 문서 버전 단위로 나눌 수 있다.

응답률은 전체 요청 중 답한 비율이다. 답변 정확도는 **답한 것 중 올바른 답**의 비율이다. 과업 성공률은 정답이 있는 입력에서의 올바른 답과, 정답이 없거나 조건이 부족한 입력에서의 올바른 보류를 함께 센다. 모두 보류하는 정책은 잘못 답한 건이 적지만 실제로 답해야 할 요청을 놓친다. 결과표에는 전체 표본 수와 응답을 낸 수를 같이 둔다. [블로그의 회귀 평가와 답변 근거 검증](/agentic-ai/evaluation/)

## 3. 피드백으로 실패 유형을 좁히기

사용자가 “비교 기준이 뒤집혔음”을 표시했다면 요청과 실제 출력에 이어 **수정한 필드**가 남아야 한다. “도움이 안 됨”이라는 평가만 있으면 도구 선택과 근거 부족, 표시 문제를 가르기 어렵다. 실행 ID, 언제 본 답변인지, 오류 유형, 사용자 수정 값, 이미 사용한 출처를 함께 남긴다.

예를 들어 지원 범위에 있는 `compare`를 잘못 분류했다면 분류 프롬프트를 볼 수 있다. 정답 경로를 골랐지만 R42와 R41을 바꿨다면 인자 추출과 교차 검증이 대상이다. 도구가 정확한 값을 반환했는데 결과의 부호가 틀렸다면 계산 단계를 고친다. 수정한 사례는 회귀 집합에 넣고, 같은 유형의 새 예제로 다시 비교한다. 실제 대화 원문이 필요 없는 지표에는 유형과 결과만 남겨도 된다.

## 4. 보류 임계값 두 개를 실행해 보기

[evaluation_lab.py](evaluation_lab.py)에는 요청 유형, 후보 점수, 응답을 기대하는지, 응답을 채택하면 맞는지가 들어 있다. 점수는 판단 로직을 비교하기 위해 미리 적은 합성 값이다. 임계값 이상이면 답하고, 낮으면 보류한다. 개발용 6개와 별도 평가용 8개에 0.60과 0.80을 각각 적용했다. 아래 수치는 Python 3.13.18에서 같은 입력을 실행한 결과다.

```bash
python3 evaluation_lab.py
```

| 데이터 | 임계값 | 낸 답 | 과업 성공 | 답한 것 중 정답 | 답하면 안 되는 요청에 답함 |
|---|---:|---:|---:|---:|---:|
| 개발용 | 0.60 | 5/6 | 4/6 | 3/5 | 1 |
| 개발용 | 0.80 | 3/6 | 4/6 | 2/3 | 0 |
| 평가용 | 0.60 | 7/8 | 4/8 | 3/7 | 3 |
| 평가용 | 0.80 | 4/8 | 5/8 | 2/4 | 1 |

개발용에서는 임계값을 올려도 과업 성공이 4건이었다. 모호한 요청 하나를 올바르게 보류했지만 답할 수 있던 비교 하나도 함께 보류했다. 평가용에서는 0.91점으로 표시된 모호한 요청이 0.80을 통과했다. 검증 도우미가 비교 전에 대상과 기준을 모두 갖췄는지 확인하는 검사를 추가할 이유다. 후보 점수를 조절해 잡는 오류와 필수 조건으로 막는 오류를 구분했다.

## 5. 튜닝할 때 바꾸는 조건과 남기는 증거

프롬프트 문구와 모델을 한꺼번에 바꾸면 좋아진 이유를 좁히기 어렵다. 설정 비교에서는 같은 데이터, 같은 도구·권한 조건에서 한 변수를 먼저 바꾼다. 온도나 모델 크기를 바꿀 때는 과업 성공뿐 아니라 요청당 입력·출력 토큰, 도구 호출 수, 지연 분포도 비교한다. 비용과 성공률은 서로 다른 단위라 두 값의 요구 조건을 먼저 정한다. 같은 정확도를 유지하면서 호출 수를 줄일 수 있는지, 호출을 늘렸다면 어떤 유형에서 성공이 추가됐는지를 본다. [AI Agents That Matter의 비용 비교](https://arxiv.org/abs/2407.01502)

측정 조건에는 입력 길이, 시간 제한, 모델 버전, 실패 재시도 수, 보류 기준을 적는다. 모호한 요청이 많은 평가에서 기준을 바꿨다면, 보고서에서 그 유형의 성능을 따로 표시한다. 이번 실험은 합성 점수에 두 임계값을 적용한 정책 비교다. 실제 모델에 적용하려면 고정한 평가셋에서 점수와 정답의 관계부터 확인할 수 있다.
