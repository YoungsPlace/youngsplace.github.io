R42 시험 보고서를 만드는 에이전트에 조회와 게시 도구를 연결하면, 같은 채팅에서 내부 기록을 읽고 외부에 영향을 주는 행동도 요청할 수 있다. 읽기 권한은 팀과 기록을 확인하고, 게시 권한은 승인한 판본과 실제 실행할 판본이 같은지까지 확인한다. 자료를 모델에 넘길 때, 로그를 남길 때, 결과를 전달할 때에는 각 단계에 필요한 정보만 공개한다.

공식 학습 가이드 9.1–9.5는 보안과 추적성, 개인정보와 기업 정책, 편향·유해성 평가, 계층별 안전장치와 사람 검토, 모델·데이터의 라이선스와 규정 준수를 다룬다. 웹 출제표에서 비중은 5%다. [공식 출제표](https://www.nvidia.com/en-us/learn/certification/agentic-ai-professional/#exam-blueprint) · [공식 학습 가이드 9장](https://dam-cdn.nvd.orangelogic.com/AssetLink/64tei188l3tt132l265u1ipjoexdl1p5.pdf#page=12)

## 1. 읽기와 게시 권한을 확인하는 곳

요청 본문에 팀이 적혀 있더라도 권한을 판단할 때는 서버가 확인한 계정과 소속을 사용한다. 모델이 제안한 도구 호출에서는 작업 종류, 레코드 ID, 판본처럼 필요한 인자를 읽는다. 애플리케이션은 허용된 도구 목록과 입력 스키마를 관리하고, 조회용과 게시용 서비스 자격 증명에 각 작업에 필요한 범위만 부여한다.

| 동작 | 실행 전에 확인할 정보 |
|---|---|
| 시험 원본 조회 | 요청자에게 해당 시험과 필드의 조회 권한이 있는가 |
| 비교 보고서 초안 생성 | 사용할 근거가 요청자의 조회 범위 안에 있는가 |
| 승인 등록 | 권한이 있는 사람이 특정 작업과 판본을 검토했는가 |
| 보고서 게시 | 게시 권한, 승인 범위, 현재 판본, 승인 상태가 일치하는가 |

초안을 수정하면 승인 당시 판본과 달라진다. 게시 도구를 실행하기 전에 현재 판본을 확인하고, 가능하면 쓰기 조건에도 같은 판본을 넣는다. 중복 요청에 대응하려면 같은 실행 ID에 해당하는 완료 결과를 조회할 수 있어야 한다. [5장의 체크포인트와 재개](/ncp-aai/chapter-05-cognition-planning-memory/) · [10장의 판본별 승인](/ncp-aai/chapter-10-human-ai-oversight/)

검색 결과나 외부 도구의 본문에는 자료 작성자가 넣은 지시도 들어 있을 수 있다. 이 텍스트는 근거로 취급하고, 도구 권한은 인증 결과와 애플리케이션 정책에서 판단한다. 검색 단계의 권한 필터는 모델이 볼 수 있는 자료를 제한한다. 실행 단계에서는 도구의 대상과 인자를 재검사하고, 승인 범위를 벗어난 작업은 검토 대기 상태로 돌린다. [OWASP의 LLM 프롬프트 인젝션 방어 지침](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) · [NeMo Guardrails의 검사 구간](/ncp-aai/chapter-07-nvidia-platform/)

입력, 인덱스, 모델 제공자, 실행 로그가 서로 다른 곳에 있다면 개인정보가 거치는 위치부터 적는다. 목적에 필요한 필드만 전송하고, 저장 범위와 보관 기한을 정한다. 감사 레코드에는 정책 버전, 요청 식별용 참조, 작업 종류, 결과와 시각을 둘 수 있다. 원본 요청이나 검색 문서의 보관에는 별도의 목적과 접근 권한을 적용한다.

## 3. 권한과 승인 판본을 확인한 결과

[policy_lab.py](policy_lab.py)는 팀 A가 R42를 읽을 수 있다는 모의 권한과 R42 3판에 대한 승인을 준비한다. 스크립트는 도구 실행 전에 반환할 정책 결정과 감사 레코드를 출력한다.

```bash
python3 policy_lab.py
```

| 요청 | 정책 결정 | 감사 기록의 시험 ID |
|---|---|---|
| 팀 A가 R42 조회 | `allow` | R42 |
| 팀 A가 다른 팀 R41 조회 | `deny_scope` | `null` |
| 3판 승인으로 R42 4판 게시 요청 | `hold_for_approval` | R42 |
| 승인과 같은 R42 3판 게시 요청 | `allow` | R42 |

예제에서 승인은 팀, 시험 ID, 판본을 비교한다. 배포하는 서비스에서는 승인자의 권한과 유효 기간, 작업 종류와 대상도 승인 기록에 연결한다.

## 4. 필터의 오류를 유형별로 세기

안전 필터를 평가할 때에는 적절한 입력을 잘못 막은 비율과 차단해야 할 출력이 통과한 비율을 각각 센다. 문의 언어, 표현 방식, 과업 종류를 기록하면 전체 평균에 묻힌 차이를 찾을 수 있다. 같은 의도를 직접 말한 사례와 돌려 말한 사례를 비교하려면 의도를 고정한 문장 쌍을 쓴다. 유해성 평가에서는 업무에 필요한 인용이나 분석을 막은 사례와, 사용 맥락상 허용되지 않은 출력이 통과한 사례에 서로 다른 라벨을 붙인다.

같은 스크립트의 모의 데이터에서 허용 대상만 집계했다. 직접 표현은 4건 중 1건, 간접 표현은 4건 중 2건이 차단된 것으로 입력해 각각 25%, 50%가 나왔다. 실제 필터를 평가할 때는 표본을 늘리고 평가 기준과 라벨을 따로 관리한다. 평가 담당자 간에 판정이 갈린 이유도 기록할 수 있다. [NIST AI Risk Management Framework](https://airc.nist.gov/airmf-resources/airmf/)

## 5. 사용 조건과 운영 책임을 기록하기

모델 가중치, 실행 코드와 컨테이너, 학습 데이터와 검색 자료에는 각각 사용·재배포 조건이 붙을 수 있다. 모델을 API로 쓴다면 제공자의 데이터 처리 조건도 확인한다. 아티팩트의 이름, 버전, 출처, 사용 조건, 확인 이력을 남기면 새 버전을 들일 때 바뀐 부분을 찾기 쉽다. 소프트웨어 구성과 라이선스 식별자를 기록하는 데에는 SPDX 같은 표준을 쓸 수 있다. [SPDX 개요](https://spdx.dev/learn/overview/)

기술 설정과 정책 요구는 대응 관계를 남긴다. 보관 기한이 있다면 어떤 저장소에서 삭제되고 백업에는 얼마 동안 남는지 적는다. 사람의 승인 절차가 필요하다면 누가 무엇을 보고 결정하며 어떤 이벤트가 남는지 설명한다. 개별 실행의 긴급 검토와 제품 수준의 지표 검토에는 서로 다른 담당과 권한을 배정할 수 있다.
