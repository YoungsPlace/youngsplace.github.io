사용자가 선호 장소를 Amber에서 Cobalt로 바꿨다. 다음 대화에서 Cobalt를 찾고, Amber는 현행 값으로 검색되지 않아야 한다. 사용자가 선호를 삭제하면 새 답변을 조립할 때 Cobalt도 빠져야 한다. 원본 표에서 한 줄을 지우는 일과 이미 만들어 둔 검색 항목을 지우는 일을 묶었다. [5편의 사용자와 날짜 필터](/agentic-ai/memory-retrieval/)

## 바꾸는 단위에 검색 인덱스 포함하기

이번 예제에는 현재 값, 별도 FTS5 인덱스, 변경 이벤트가 있다. FTS 인덱스도 텍스트 사본을 갖는다. 내용을 변경할 때 해당 사용자의 인덱스 행부터 없애고, 새 값이 있으면 원본과 인덱스를 다시 입력한다. 이벤트에는 시퀀스 ID와 사용자, 항목 이름, 변경 동작만 남긴다. 샘플 데이터에서는 절대 시각이나 이전 값을 보존하지 않는다. [SQLite FTS5 · SQLite 프로젝트, 2026-11-16 확인](https://www.sqlite.org/fts5.html) · [SQLite Transaction · 2026-11-16 확인](https://www.sqlite.org/lang_transaction.html)

원본과 인덱스가 서로 다른 서비스에 있다면 여기처럼 같은 트랜잭션으로 바꾸기 어렵다. 그때는 변경 이벤트를 전달하고 인덱스 작업을 재시도할 수 있게 둔다. 인덱스가 느리게 따라오는 동안에도 읽을 때 원본 권한과 현재 버전을 확인하면 오래된 검색 결과를 답변에서 제외할 수 있다. 예제의 검색은 인덱스로 후보를 찾더라도 원본에서 같은 사용자와 항목의 현재 값을 가져온다.

## 정정, 중간 실패, 삭제 뒤 확인

[실행 코드](lifecycle.py)는 임시 SQLite 파일을 만든다. 합성 값 `amber`, `cobalt`, `silver`, `cedar`를 썼다. Python 3.13.18과 SQLite 3.54.1에서 실행했다. 답변 함수는 첫 검색 결과 한 건을 반환한다. 외부 모델로 새 문장을 생성하는 과정은 없다.

```bash
python3 lifecycle.py
```

| 동작 | 검색·답변에서 확인한 결과 |
|---|---|
| u1의 Amber를 Cobalt로 정정 | Amber는 0건, Cobalt는 `cobalt` |
| Silver를 저장하다가 커밋 전에 예외 | Silver는 0건, Cobalt는 `cobalt` |
| u1이 u2의 Cedar를 조회 | `no_evidence` |
| u1 선호 삭제 후 DB 연결을 닫았다가 다시 엶 | u1의 Amber, Cobalt, Silver 모두 `no_evidence` |
| 같은 연결에서 u2의 Cedar를 조회 | `cedar` |
| u1 변경 이벤트를 순서대로 조회 | `put`, `put`, `delete` |

롤백에서 Silver의 원본 및 인덱스 쓰기를 모두 취소했다. 실패 이벤트는 기록되지 않았고, Cobalt의 검색 결과가 그대로였다. 새 세션에서 읽는 경로뿐 아니라, 이전 검색 결과를 캐시에 넣거나 이미 대화 입력에 붙인 경로도 별도로 찾아야 한다. 다음 답변을 만들 때 삭제 전에 조립한 문서를 다시 쓰면 DB를 지운 뒤에도 그 값이 나올 수 있다.

논리적으로 검색 결과에서 빠지는 것과 파일에 남은 흔적까지 없애는 것은 다른 범위다. SQLite의 `secure_delete` 설명에는 가상 테이블의 섀도 테이블에 내용이 남을 수 있다고 되어 있다. 이 실습은 파일 내부, 백업, 로그에 남은 데이터를 검사하지 않았다. 서비스에서는 원본, 인덱스, 캐시, 백업마다 보존 기간과 삭제 범위를 정의할 수 있다. [PRAGMA secure_delete · SQLite 프로젝트, 2026-11-16 확인](https://www.sqlite.org/pragma.html#pragma_secure_delete)

LongMemEval은 여러 대화에서 바뀐 정보를 읽는지와 근거가 없을 때 보류하는지를 따로 평가한다. 이 예제에서는 삭제 후 검색 자체가 비었는지와, 근거 없이 이전 값을 돌려주지 않는지를 두 조건으로 봤다. [LongMemEval · Di Wu 외, ICLR 2025, arXiv v2 2025-03-04](https://arxiv.org/abs/2410.10813)

## 삭제가 끝난 시점에 진행 중이던 읽기

SQLite의 WAL 모드에서 한 연결이 읽기 트랜잭션을 열면, 그 연결은 읽기를 시작했을 때의 스냅샷을 유지한다. 다른 연결에서 삭제를 커밋할 수 있어도 먼저 시작한 읽기는 이전 버전을 볼 수 있다. [wal_snapshot.py](wal_snapshot.py)는 [lifecycle.py](lifecycle.py)와 같은 폴더에 두고 두 연결을 분리해 확인하는 예제다. [Isolation In SQLite · SQLite](https://www.sqlite.org/isolation.html) · [Write-Ahead Logging · SQLite](https://www.sqlite.org/wal.html)

```bash
python3 wal_snapshot.py
```

| 조회 시점 | u1의 Cobalt 검색 |
|---|---|
| 읽기 트랜잭션 시작 직후 | `["cobalt"]` |
| 별도 연결에서 삭제 후, 기존 트랜잭션 | `["cobalt"]` |
| 삭제 후 새 연결의 조회 | `[]` |
| 기존 연결을 롤백하고 시작한 새 읽기 | `[]` |

삭제 이전 스냅샷에 있던 연결로 쓰기를 시도하니 `SQLITE_BUSY_SNAPSHOT`이 반환됐다. 오류 뒤에는 기존 트랜잭션을 종료하고 새로운 상태를 읽었다. 위 결과는 WAL에 원본·검색 인덱스를 함께 바꿔도 진행 중인 읽기까지 새 데이터로 갱신되는 것은 아니라는 사례다. 조회 시작 시점의 일관성과 삭제 직후 실행되는 답에 적용할 정책을 따로 정할 수 있다.

## 캐시와 비동기 인덱스에서 옛 값이 돌아오는 순서

원본 저장소에서 버전 8 삭제를 커밋했는데 벡터 인덱서가 아직 버전 7의 갱신 이벤트를 처리하고 있을 수 있다. 뒤늦은 갱신을 그대로 적용하면 삭제가 끝난 뒤 같은 항목이 검색된다. 각 항목의 마지막 처리 버전과 삭제 표시를 비교하면 순서가 역전된 이벤트를 무시할 수 있다. 삭제 표시를 너무 일찍 제거하면 뒤늦게 온 옛 이벤트를 최신 것으로 볼 수 있으므로, 처리 지연 상한과 재생·백업 복원 정책에 따라 유지할 범위를 정한다.

```text
정정 이벤트 v7 → 인덱스 작업 지연
삭제 이벤트 v8 → 삭제 표시와 마지막 적용 버전 8
지연된 v7 도착 → v7 <= 8, 적용 보류
```

검색 경로에서 권한과 최신 버전을 원본과 맞춰 보면 인덱스 반영 전에도 오래된 항목을 결과에서 제외할 수 있다. 다만 프롬프트에 이미 붙인 근거까지 변경되지는 않는다. 답을 아직 생성 중이라면 최종 출력 전에 근거 ID의 삭제 여부를 다시 검사하는 정책을 둘 수 있다. 이미 출력된 대화나 외부 효과의 처리 범위는 별도로 관리한다. 원본 기억의 변경 기록에 값을 남길지, 식별자와 변경 종류만 남길지도 이런 읽기 경로와 보존 목적에 맞춰 정한다.

삭제 시나리오를 평가할 때는 ① 새 세션 읽기, ② 이전에 생성된 캐시, ③ 순서가 바뀐 인덱스 이벤트, ④ 백업 복원 뒤 새 인덱스 생성 각각에서 삭제된 ID가 나타나는지를 본다. 이번 데모는 ①과 진행 중인 SQL 스냅샷의 차이를 확인했다. 같은 사용자의 여러 기억이 들어오는 실제 검색에서는 정정된 근거의 내용까지 일치하는지 확인할 수 있다.
