빈 시간 조회에는 현재 운영 상태를 읽는 권한이 있으면 된다. 실제 예약은 다른 사람도 보는 일정을 바꾼다. 한 사용자가 ‘B, 14:00’을 확인했다면 그 확인으로 15:00을 예약할 수 없다. 도구 호출 제안이 도착했을 때 허용된 행동과 승인된 내용을 실행기에서 맞춰 봤다. [8편의 도구 계약](/agentic-ai/orchestration/)

## 모델이 읽는 데이터와 런타임의 권한

| 입력 | 어디에서 읽는가 | 실행기에 주는 권한 |
|---|---|---|
| 검색한 운영 문서 | 모델이 읽는 자료 | 예약에 필요한 조건을 설명할 수 있다. |
| 모델의 행동 제안 | 입력 스키마가 있는 요청 | 실행기가 검증할 이름과 인자를 제공한다. |
| 인증된 사용자 범위 | 실행기와 서비스의 신원 정보 | 어떤 실험실을 사용하는지 제한한다. |
| 확인 화면에서 승인한 내용 | 실행기가 가져온 승인 레코드 | 사용자, 요청 ID, 장소와 시간이 일치할 때 이 예약을 허용한다. |

검색 문서와 도구 결과에 사용자를 대신해 행동을 지시하는 문장이 들어올 수 있다. 앱에서는 입력 출처를 표시하고 서비스 권한을 코드로 확인한다. OWASP는 외부 입력의 분리, 최소 권한, 민감한 작업의 사람 확인을 완화책으로 제시한다. NVIDIA NeMo Guardrails의 retrieval rail은 검색 결과, execution rail은 도구 이름·인자·응답을 검사하는 위치다. 여기에 쓰인 결정은 Python 함수로 구현했다. ## 가상 예약에서 승인과 재호출 비교

[approval.py](approval.py)의 데이터는 실행 중 메모리에 둔다. 입력과 승인에는 요청 ID, 사용자, 장소, 시간이 들어간다. 예제에서는 인증된 사용자 ID와 승인 레코드를 테스트 코드에서 따로 전달했다. Python 3.13.18에서 합성 사례 일곱 개를 한 번의 프로세스에 순서대로 넣었다.

```bash
python3 approval.py
```

| 입력 | 결과 |
|---|---|
| 승인 없이 B 14:00 요청 | `needs_matching_approval` |
| B 14:00 승인 뒤 요청을 15:00으로 변경 | `needs_matching_approval` |
| 목록에 없는 시간 입력 | `invalid_slot` |
| B만 허용된 u2가 A 요청 | `denied` |
| u1의 승인과 요청을 B 14:00으로 맞춤 | `committed` |
| 같은 ID와 내용으로 다시 요청 | `same_request` |
| 이미 쓴 ID를 다른 시간에 재사용 | `request_conflict` |

예약은 한 건 남았다. 이벤트에는 합성 요청 ID, 도구 이름, 상태만 저장됐다. 장소·시간·사용자나 문서 본문은 이벤트에 담지 않았다. 운영 로그에서는 요청 ID로도 사용자를 추적할 수 있으므로 열람 범위와 보존 기간을 함께 본다.

## 승인 레코드에 어떤 값을 고정할까

승인 화면에는 행동 이름과 대상, 변경될 값을 표시한다. 서버는 화면과 같은 자료를 승인 레코드에 저장한다. 이 예제에서 실제로 변경되는 값은 ‘실험실 B의 14:00 예약’이다. 서비스를 여러 팀이 쓴다면 사용자와 소속 범위, 도구 이름, 장소, 시작 시각, 정책 버전, 만료 시각, 요청 ID가 승인과 함께 묶일 수 있다. 입력을 다듬는 과정에서 `14:00 KST`를 UTC로 바꾼다면 확인 화면과 서버가 같은 정규화 규칙으로 의미를 비교할 수 있어야 한다.

| 시점 | 검사할 데이터 |
|---|---|
| 도구를 모델에 보여 줄 때 | 서비스가 그 사용자와 요청 범위에 공개하는 도구 목록 |
| 모델이 제안할 때 | 허용된 도구 이름, 인자 형식, 알려진 값의 범위 |
| 승인할 때 | 사용자에게 표시한 행동과 전체 변경값 |
| 예약을 실행할 때 | 현재 권한, 유효한 승인, 동일한 요청 ID와 값, 슬롯의 현재 상태 |
| 사용자가 결과를 받을 때 | 실제 커밋된 요청과 결과 ID |

승인에 ‘예약 허용=true’만 저장하면 어떤 슬롯을 확인했는지 알 수 없다. 앱에서 사용자가 승인했다고 주장하는 모델 출력은 증거로 쓰지 않는다. 승인 정보는 애플리케이션이 관리하는 역할·요청·유효기간에서 가져온다. 실제 쓰기와 떨어진 곳에서 검사만 먼저 하면, 그사이에 권한이나 일정이 바뀔 수 있다. 같은 저장소에서 현재 상태 확인과 쓰기를 함께 하거나, 슬롯 버전을 쓰기 요청의 조건에 넣는다. [12편의 SQLite 동시 예약](/agentic-ai/lab-assistant/)

## 읽어도 되는 정보와 쓰기 가능한 작업을 각각 확인

문서 검색에 권한 검사를 먼저 쓰면 사용자에게 검색 점수나 딱 맞는 문구가 있어도, 읽을 수 없는 출처는 모델 입력에 오르지 않는다. 예약 도구에는 승인 조건을 별도로 걸어 검색 문서 안의 안내문, 요청 텍스트, 도구 응답이 권한을 변경하지 못하게 한다. 한 모델에게 읽기와 쓰기를 모두 노출할 때도 앱의 인증 정보는 모델이 수정할 수 없는 자리에 둔다. 도구 설명과 출력 스키마는 사용 범위를 설명하고, 인가와 서버의 서비스 계정 권한은 실행 가능한 범위를 정한다. [Tools · MCP 사양](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) · [LLM01:2025 Prompt Injection · OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

실행기에서 사용할 수 있는 입력 검사 위치는 네 곳으로 구분된다. 사용자 입력에서 과업 대상과 데이터 처리 범위, 검색에서 문서 권한과 버전, 도구 경계에서 승인과 어댑터 인자, 최종 응답에서 공개할 수 있는 결과 필드를 확인한다. 예를 들어 읽기 단계에서 이미 다른 사용자 데이터를 모델에 보냈다면 응답 필터가 유출의 일부는 막더라도 앞선 조회 자체는 되돌리지 못한다. [Guardrail Types · NVIDIA NeMo Guardrails](https://docs.nvidia.com/nemo/guardrails/about-nemo-guardrails-library/rail-types)

## 승인 거부도 정상 경로로 평가하기

이 글의 단일 프로세스 예제에서는 사용자 u2의 `denied`나 변경 슬롯의 `needs_matching_approval`가 올바른 결과다. 평가 상태를 ‘커밋됐다’ 하나로 두면 이런 경로가 모두 실패로 계산된다. 사용자 입장에서는 왜 멈췄는지, 값을 수정해서 다시 확인할 수 있는지가 필요하다. 운영 쪽에서는 승인 없이 커밋된 수, 정상 승인 뒤 커밋되지 않은 수, 동일 요청의 중복 효과 수, 민감한 데이터가 로그에 남았는지를 따로 집계한다.

‘조건은 만족했는데 요청을 끝내지 못했다’와 ‘만족하지 않은 조건 때문에 멈췄다’를 실행 기록으로 분리한다. 이번 테스트에는 잘못된 자료에서 나온 권한을 모델이 판단하는 행위가 없다. 사람과 실행기를 잇는 레코드에 무엇을 묶고, 어떤 상태에서 쓰기를 거부하는지를 살폈다.

## 실제 서비스에서 달라지는 부분

예제는 쓰기 한 건을 사전으로 기록한다. 여러 프로세스에서 동시에 들어오는 요청에는 예약 가능 상태 확인, 요청 ID 유일성, 슬롯 선점을 트랜잭션이나 예약 서비스의 원자적 연산으로 옮겨야 한다. 승인에도 유효 기간이나 취소 상태를 넣을 수 있다. 승인 기록의 생성과 조회를 모델의 도구 입력과 분리하고, 사용자가 본 장소·시간을 실행 직전 다시 대조한다. MCP는 도구 공개, 호출 시각 표시, 사람이 거절할 수 있는 흐름을 권고한다. 승인 화면과 실제 권한 검사는 애플리케이션에서 구현할 부분이다.
