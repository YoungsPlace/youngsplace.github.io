방문 안내에는 운영 시간과 출입 조건, 장비가 들어간다. 서로 다른 정보원에서 가져오지만 장비를 찾기 위해 출입 조건을 먼저 읽을 필요는 없다. 세 조회를 나눠 동시에 요청했다. 운영 시간만 묻는 날에는 그 도구 하나만 불렀다. [1편의 실행 경로 선택](/agentic-ai/agent-loop/)

## 도구 계약부터 정하기

`get_hours(room_id)`는 운영 시간과 출처를 반환한다. `get_access(room_id)`는 출입 조건, `get_equipment(room_id)`는 장비 목록을 맡는다. 모두 읽기 도구다. 도구 이름, 허용 인자, 출력 형식, 타임아웃 구분이 있으면 결과를 합칠 때 ‘장비 없음’과 ‘장비 응답 없음’을 따로 유지할 수 있다. 예제에서 각 도구는 가상의 한 장소를 읽는다. 모든 결과에 상태를, 성공한 결과에는 출처를 보존했다.

MCP 도구 사양에 따르면 서버는 이름과 입력 스키마 등을 통해 도구를 공개한다. 구조화된 결과의 스키마도 적을 수 있다. `tools/call`이 실행됐지만 도구 내부에서 실패한 경우와, JSON-RPC 요청 자체의 오류는 응답 모양이 다르다. MCP를 연결할 때는 어떤 오류를 실행기가 재시도하거나 사용자에게 보낼지도 정한다. 이번 코드는 표준 라이브러리의 함수 호출을 이용했다. 모델이 도구 목록을 제안하는 경우에는 Ollama에 JSON 스키마를 전달했다. [Tools · Model Context Protocol 사양 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

## 순서가 정해진 병렬 실행과 동적 분해

요청이 들어오기 전에 도구 세 개를 정할 수 있으면 순차 호출을 병렬로 바꾸는 것만으로 충분할 수 있다. 작업을 사전에 알기 어렵다면 감독자가 이번 목표를 하위 과제로 나누고 작업자에게 할당한 뒤 결과를 합친다. Anthropic은 미리 정해진 병렬 분기와 실행 중에 하위 과제를 고르는 orchestrator-workers를 별도 패턴으로 설명한다. 순차·병렬 비교에서는 `hours`와 `visit`의 도구 목록을 표로 고정했다. 별도의 `dispatch` 모드에서는 모델이 같은 도구 목록 안에서 자연어 요청에 필요한 호출을 고른다. [Building effective agents · Anthropic Engineering, 2024-12-19](https://www.anthropic.com/research/building-effective-agents)

작업자에게는 전체 대화 대신 맡은 목표와 필요한 입력만 줄 수 있다. 감독자가 출처와 누락을 확인하지 않으면 작업자 셋을 두고도 최종 답변에서 일부 결과가 사라질 수 있다. A가 닫혔을 때 대체 B부터 알아야 하는 [2편의 조회](/agentic-ai/replanning/)에는 선행 결과가 필요하다. 그런 의존성이 없는 것만 동시에 실행했다.

## 같은 세 조회를 순차와 병렬로 실행

[workers.py](workers.py)는 운영 시간 40ms, 출입 조건 70ms, 장비 90ms를 기다리도록 만든 합성 읽기 도구를 쓴다. Python 3.13.18에서 `ThreadPoolExecutor`의 최대 스레드는 3이다. 같은 조건을 각 7회 실행한 뒤 `perf_counter`로 잰 시간의 중앙값을 구했다. 네트워크나 LLM 호출은 없다.

```bash
python3 workers.py hours serial
python3 workers.py visit parallel
python3 workers.py visit parallel --fault
```

| 입력 | 호출 수 | 순차 중앙값 | 병렬 중앙값 | 상태 |
|---|---:|---:|---:|---|
| 운영 시간만 | 1 | 44.1ms | 50.0ms | 완료 |
| 방문 안내 | 3 | 218.5ms | 95.9ms | 완료 |
| 방문 안내, 장비 타임아웃 조건 | 3 | 218.8ms | 91.9ms | 부분 완료 |

병렬 방문 안내는 기다리는 시간을 겹쳐 썼고, 호출 수는 3회로 같았다. 타임아웃 조건에서는 운영 시간과 출입 조건에 출처가 남고 장비에는 `timeout`만 기록됐다. 이 코드의 타임아웃은 합성 응답이다. 서비스에 적용할 때는 도구별 타임아웃과 전체 응답 시한, 취소 가능한 작업인지, 외부 서비스의 동시 호출 제한을 함께 본다. Python 스레드 풀을 종료할 때 이미 실행 중인 작업까지 즉시 취소할 수 있는 것은 아니다.

## 모델에게 필요한 조회만 선택하게 하기

`dispatch`에서는 Gemma 3 4B가 원문에서 필요한 도구 이름을 배열로 제안한다. 앱은 이름과 중복을 검사하고 개별 도구를 병렬로 실행한다. Ollama 0.40.11에서 `temperature=0`, `seed=42`, 출력 상한 80토큰으로 호출했고, 영어 질문 세 개를 한 번씩 넣었다.

```bash
ollama pull gemma3:4b
python3 workers.py hours dispatch
python3 workers.py visit dispatch
python3 workers.py equipment_and_access dispatch
```

| 질문 | 실행한 도구 | 요구 범위 |
|---|---|---|
| 언제 여는지 | `hours` | 1/1 |
| 운영 시간, 출입 조건, 장비 | `hours`, `access`, `equipment` | 3/3 |
| 운영 시간은 알고 있으며 장비와 필요한 신분증을 물음 | `equipment` | 1/2 |

세 번째 질문에서는 장비 조회만 성공했고 출입 확인이 빠졌다. 코드의 `complete`는 제출된 호출이 모두 성공했다는 뜻으로, 질문의 요구가 다 채워졌는지는 검사하지 않는다. 요구 범위가 미리 정의된 상황에서는 예상한 출처 유형이 모두 돌아왔는지를 따로 확인할 수 있다. 병렬 표에는 모델 판단 시간이 없으며 `dispatch`의 `ms`도 조회 구간만 잰다.

## 병렬 실행 시간을 정하는 임계 경로

앞 단계의 결과를 받아야 다음 단계가 시작되는 경로에서는 각 구간의 시간이 누적된다. 세 도구가 독립적이고 동시에 시작할 수 있으면 사용자 응답에 필요한 시간은 대략 가장 늦게 오는 도구의 시간에 모으는 시간을 더한 값이다. 이 경로가 전체 처리 시간을 결정하므로 임계 경로라고 한다. 병렬로 요청을 많이 내도 필요한 도구 중 하나가 늦으면 온전한 답변은 같이 늦어진다.

```text
순차:      hours(40) → access(70) → equipment(90)       ≈ 200ms
동시성 2: hours(40) → equipment(90)
           access(70)                                   ≈ 130ms
동시성 3: hours(40), access(70), equipment(90)           ≈  90ms
```

같은 코드의 `--max-workers`를 1, 2, 3으로 바꿔 방문 안내를 각 7회 실행했다. 세 설정 모두 조회 3회, 상태 `complete`였다. 대기와 스레드 실행 비용이 포함된 중앙값은 220.8ms, 141.7ms, 97.4ms였다.

```bash
python3 workers.py visit parallel --max-workers 1
python3 workers.py visit parallel --max-workers 2
python3 workers.py visit parallel --max-workers 3
```

꼬리 지연도 도구마다 따로 본다. 각 도구가 100ms 안에 응답할 확률이 95%이고 독립이라면, 세 도구가 모두 100ms 안에 끝날 확률은 `0.95³≈85.7%`다. 여덟 개로 늘면 `0.95⁸≈66.3%`다. 같은 저장소나 연결 풀을 쓰는 도구들이 느려지는 시점은 서로 독립적이지 않을 수 있다. 실제 분포는 각 도구의 시간과 전체 요청의 분포를 같이 잰다. 필수 자료와 선택 자료를 구분해 필요한 결과만 기다리는 방식도 있다. [The Tail at Scale · Jeffrey Dean, Luiz André Barroso, CACM 2013](https://research.google/pubs/the-tail-at-scale/)

## 감독자가 확인할 것은 호출 완료와 요청 범위

작업자에 ‘출입 확인’을 넘긴다면 작업 입력에는 장소 ID, 방문 예정일, 원하는 결과 형식을 적는다. 각 작업자가 같은 대화를 처음부터 해석하게 두면 공통 조건이 달리 해석될 수 있고 입력 토큰도 늘어난다. 출력에는 구조화한 사실과 출처 ID, 관찰 시각을 둔다. 감독자는 장비 목록과 출입 조건을 합치면서 각 값의 출처를 유지한다. 장비 서비스를 못 읽었으면 장비를 모른다는 상태를 남긴다.

| 단계 | 검증할 조건 | 조건이 빠졌을 때 |
|---|---|---|
| 분해 | 요청에서 요구한 운영 시간·출입·장비가 모두 하위 과제에 들어갔나 | 성공 상태여도 질문의 일부가 비어 있다. |
| 할당 | 같은 절을 두 작업자가 중복으로 읽고 있나 | 모델과 도구 비용이 늘고 답변에 같은 내용이 반복된다. |
| 수집 | 각 결과에 같은 장소와 날짜가 쓰였나 | A의 출입 조건을 B의 장비에 붙일 수 있다. |
| 합치기 | 누락, 출처 충돌, 최신 버전 여부를 구분했나 | 가장 늦게 돌아온 응답이 근거 없이 다른 값을 덮을 수 있다. |

동일한 질문을 단일 모델과 여러 작업자 구조에 주려면 입력과 성공 조건이 같아야 한다. 다중 작업자의 장점이 작업 분담에서 나왔는지, 더 많은 토큰과 검색 결과를 썼기 때문인지 알려면 예산이 같은 조건도 같이 본다. 이 글의 합성 도구는 하나의 Python 프로세스에서 독립적으로 잠깐 대기한다. 분산 작업자에서는 도구마다 별도 연결과 속도 제한이 있어 스레드 수를 그대로 적용하기 어렵다. [9편의 예산과 성공률](/agentic-ai/evaluation/)
