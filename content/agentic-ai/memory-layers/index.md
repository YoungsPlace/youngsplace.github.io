A가 닫혀 있고 B를 확인할 차례에 프로그램을 종료했다고 해 보자. 같은 대화를 다시 열면 B부터 이어가면 된다. 다음 날 새 대화를 시작하면 어제의 조회를 이어 갈 이유는 없다. 그때도 사용자가 평소 A를 선호한다는 설정은 쓸 수 있다. 어디에 저장하는지보다 먼저 어느 범위에서 다시 읽을지를 정했다. [2편에서 쓴 대체 장소 규칙](/agentic-ai/replanning/)

## 한 번의 모델 입력과 세 가지 저장 범위

| 범위 | 예제에서 들어갈 값 | 언제 다시 읽는가 |
|---|---|---|
| 컨텍스트 창 | 현재 질문, 필요한 규칙, 이번 도구 결과 일부 | 모델을 호출할 때 입력을 조립한다. |
| 실행 중 상태 | 확인한 장소, 남은 호출 수, 다음 조회 대상 | 같은 실행의 각 단계에서 읽는다. |
| 스레드 체크포인트 | 중단 시점의 상태와 재개 지점 | 같은 사용자와 스레드가 다시 올 때 읽는다. |
| 사용자 기억 | 선호하는 실험실 | 사용자의 새 스레드에서도 필요한 경우에 읽는다. |

컨텍스트는 모델이 이번 추론에 받는 토큰 범위다. 애플리케이션에 더 많은 상태가 있어도, 필요한 도구 결과나 기억을 가져와 입력에 넣어야 모델이 참조할 수 있다. MemGPT는 시스템 지시, 편집 가능한 작업 컨텍스트, 메시지 큐를 모델 입력 안에 두고, 밖의 보관·회상 저장소와 함수 호출로 정보를 주고받는다. 그 논문의 메모리 계층은 모델 입력에서 무엇을 빼고 다시 올릴지 설명할 때 도움이 됐다. [MemGPT: Towards LLMs as Operating Systems · Charles Packer 외, arXiv v2 2024-02-12, §2](https://arxiv.org/html/2310.08560#S2)

LangGraph의 체크포인터는 그래프 상태를 스레드 단위로 저장한다. Store는 사용자 선호처럼 여러 스레드에서 읽을 값을 맡는다. 문서의 예제에는 프로세스 내 메모리 구현도 있다. 재시작 후에도 값을 남기려면 파일이나 데이터베이스에 저장하는 구현을 골라야 한다. [Persistence · LangChain, 2026-11-16 확인](https://docs.langchain.com/oss/python/langgraph/persistence)

## 프로세스를 다시 띄워 읽어 보기

[checkpoint.py](checkpoint.py)는 Python 표준 라이브러리와 SQLite만 쓴다. `pause`는 닫힌 A와 다음 조회 대상 B를 `(owner, thread)` 키로 저장한다. 선호하는 실험실 A는 별도로 `owner`를 키로 저장한다. `inspect`는 현재 두 값을 각각 읽는다.

```bash
study_db_dir=$(mktemp -d)
python3 checkpoint.py pause "$study_db_dir/lab.sqlite" u1 t1
python3 checkpoint.py inspect "$study_db_dir/lab.sqlite" u1 t1
python3 checkpoint.py inspect "$study_db_dir/lab.sqlite" u1 t2
python3 checkpoint.py inspect "$study_db_dir/lab.sqlite" u2 t1
```

Python 3.13.18과 SQLite 3.54.1에서 각 명령을 별도 프로세스로 실행했다. 새 파일에 처음 `inspect`를 실행했을 때는 두 값이 모두 `null`이었다. 값을 저장하고 프로세스를 새로 띄웠을 때는 다음과 같았다.

| 프로세스가 읽은 범위 | 체크포인트 | 기본 선호 |
|---|---|---|
| 사용자 u1, 원래 스레드 t1 | A 닫힘, B 상태 조회 대기 | LAB-A |
| 사용자 u1, 새 스레드 t2 | `null` | LAB-A |
| 사용자 u2, 같은 이름의 스레드 t1 | `null` | `null` |

재시작한 프로세스에서 다음 행동 값을 읽는 것까지 확인했다. 함수 호출을 실제로 재개시키는 실행기는 이 예제에 들어 있지 않다. 서비스를 이어 가려면 어떤 지점까지 완료했는지, 데이터 형식 버전, 외부 호출이 반영됐는지도 저장해야 한다. 체크포인트 뒤에 외부 쓰기가 성공하고 그 결과를 남기기 전에 종료될 수 있다. 같은 요청 ID를 다시 보냈을 때 중복을 막는지는 저장소와 별도로 외부 시스템에서 처리한다.

## 모델 입력의 토큰 예산과 KV 캐시

컨텍스트 길이는 그 호출에서 모델이 함께 처리할 토큰 수의 범위다. 문자가 토큰으로 바뀌는 과정은 모델의 토크나이저에 따라 다르다. 한국어와 기술 표기의 토큰 수를 영어 단어 수로 예상하면 오차가 커질 수 있다. 8,192토큰 예산에서 최대 생성량을 1,024토큰, 시스템 지시와 도구 정의를 1,600토큰, 현재 질문을 200토큰으로 잡으면 이력과 검색 결과에는 5,368토큰이 남는다. 채팅 템플릿이 붙이는 구분 토큰과 안전 여유가 필요하면 여기서 더 줄인다. 검색 문서 수를 정할 때에는 항목 수와 별도로 이 합을 확인한다.

트랜스포머의 자기 어텐션에서는 디코딩할 때 이미 처리한 토큰의 K와 V를 보관해 이후 생성에서 다시 쓸 수 있다. 일반적인 디코더 모델에서 KV 캐시 크기를 가늠하는 식은 `2 × 레이어 수 × 토큰 수 × KV 헤드 수 × 헤드 차원 × 요소당 바이트`다. 32층, KV 헤드 8개, 헤드 차원 128, BF16, 8,192토큰인 가상의 모델이라면 약 1GiB다. 여기에는 모델 가중치, 계산 버퍼, 할당기 여유가 빠져 있다. 쿼리 헤드가 KV를 공유하는 GQA에서는 쿼리 헤드 수 대신 실제 KV 헤드 수로 셈한다. 여러 요청을 동시에 받으면 각 요청의 시퀀스 길이만큼 공간을 마련한다. [PagedAttention · Woosuk Kwon 외, 2023](https://arxiv.org/abs/2309.06180) · [11편의 서빙 실측](/agentic-ai/serving/)

KV 캐시는 현재 입력에서 계산한 중간 표현을 재사용하는 장치다. 데이터베이스에 저장한 장소 선호는 다음 요청의 입력을 조립하는 자료다. 서버가 혼잡해서 캐시를 비웠을 때는 기존 프롬프트를 다시 계산할 수 있고, 사용자가 선호를 삭제했을 때는 프롬프트를 새로 조립해야 한다. 누가 어떤 범위에서 정보를 다시 읽는지가 다르다.

## 많이 넣는 것과 필요한 근거를 배치하는 것

*Lost in the Middle* 연구에서는 여러 문서 질의응답에서 같은 관련 문서의 위치를 바꿨다. 실험 모델 중 여러 경우에서 시작이나 끝의 근거를 더 잘 활용하고, 중간에 있을 때 정확도가 떨어졌다. 길이 제한 안에 들어간다는 정보로 답변 품질까지 판단하기 어려운 이유다. 예약 예제라면 확정된 장소와 최신 일정처럼 바로 써야 할 값은 표나 짧은 최신 상태에 두고, 자세한 조회 이력은 필요할 때 찾는 쪽으로 나눌 수 있다. 평가할 때는 근거 텍스트를 그대로 두고 위치나 잡음 문서의 수만 바꿔 영향을 본다. [Lost in the Middle · Nelson F. Liu 외, TACL 2024](https://aclanthology.org/2024.tacl-1.9/)

| 보관 방법 | 살리는 정보 | 잃거나 추가로 확인할 정보 |
|---|---|---|
| 최근 메시지 N개 | 직전 흐름과 현재 질문 | 오래된 사용자 선호, 이전 분기의 결정 이유 |
| 진행 요약 | 지금까지의 목표와 주요 조건 | 부정, 예외, 정확한 수치와 원 출처 |
| 구조화 상태 | 다음 도구, 상태, 버전, 근거 ID | 자유 문장 안에 있던 설명과 복합 조건 |
| 검색으로 가져온 기억 | 먼 과거에서 관련 있는 조각 | 찾지 못한 항목, 잘못된 검색 순위 |

## 중단 지점에서 어떤 코드를 다시 실행할까

복구를 위해 저장하는 값에는 실행의 소유자, 스레드 ID, 단계 ID, 상태 스키마 버전, 보호해야 할 외부 요청 ID가 들어갈 수 있다. 같은 스레드가 두 곳에서 진행되면 예전 상태가 새로운 체크포인트를 덮지 않도록 `generation`을 둔다. 예를 들어 버전 7을 읽은 실행은 `UPDATE … WHERE generation = 7`이 한 행을 바꾼 경우에만 버전 8 저장에 성공한다. 변경된 행이 0개면 새 버전을 읽어 충돌을 처리한다.

식별자와 데이터 형식이 같아도 부수 효과가 들어가는 순간 복구 조건이 달라진다. ‘B 14:00 예약을 서버에 보낸 뒤 응답 기록 전에 프로그램 종료’라면 체크포인트만 보고는 예약 반영 여부를 모른다. 외부 예약 요청에 실행 단위로 고정된 ID를 주고, 복구 때 같은 ID의 결과를 조회하거나 해당 키로 재요청한다. 상당한 비용을 쓰는 모델 응답도 외부 효과 대신 재현 조건이 달라지는 단계라, 실행 별 생성 결과를 저장할 수 있다. 단계 실행을 저장하는 프레임워크에서도 체크포인트 앞뒤로 되풀이될 수 있는 효과는 서비스의 멱등성 계약을 따로 확인한다. [Interrupts · LangGraph](https://docs.langchain.com/oss/python/langgraph/interrupts) · [12편의 커밋과 재호출](/agentic-ai/lab-assistant/)

## 원래 대화를 얼마나 다시 보낼까

메시지 전체를 다시 보내면 맥락이 손실되는 시점은 늦춰지지만 매 요청의 입력이 커진다. 요약은 길이를 줄이고 주요 결정만 남긴다. 반대로 이후에 필요해진 세부 근거가 요약에서 빠질 수 있다. 상태를 구조화하면 ‘B가 대체 장소’와 ‘B가 열림’처럼 다른 관찰을 분리해 복원할 수 있다. 새 스레드에는 A를 선호한다는 값만 전달하고, 과거에 A가 닫혔다는 도구 결과는 필요하면 다시 확인한다. 선호와 운영 상태는 각자 유효 기간이 다르다.
