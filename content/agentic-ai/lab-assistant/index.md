사용자가 B를 선호하고 그곳에 빈 시간이 있다면 B를 먼저 보여 준다. B가 닫혔으면 접근할 수 있는 다음 장소를 확인한다. 예약을 요청하면 현행 안내에 적힌 신청 기한을 확인하고, 사람이 확인한 장소와 시간이 실행할 값과 같은지 대조한다. 실험실 한 곳만 읽는 기준선에 앞에서 만든 규칙을 조금씩 연결했다. [NVIDIA NCP-AAI 공개 시험 범위 · 2026-11-16 확인](https://www.nvidia.com/en-us/learn/certification/agentic-ai-professional/)

## 정보마다 읽어 올 위치 다르게 두기

| 정보 | 이번 입력에서 얻는 위치 | 결정에 쓰이는 곳 |
|---|---|---|
| 사용자의 장소 선호 | 사용자 ID로 찾은 기억 | 장소 후보의 순서 |
| 가능한 장소와 시간 | 현재 일정 응답 | 선호를 적용할 수 있는지 |
| 누가 어느 장소를 쓸 수 있는지 | 실행기의 권한 표 | 후보 조회와 쓰기 범위 |
| 예약 시한 | 현행 예약 안내의 출처와 값 | 예약 요청 검증 |
| 확정한 예약 | 별도 승인 입력 | 쓰기 직전 요청과 대조 |

기억은 오래가지만 장소가 지금 열렸는지는 일정에서 읽는다. 출처가 최신인지와 사용자가 사용할 수 있는 장소인지도 서로 다른 검사다. 예제는 두 버전의 규칙 중 현행 한 건을 선택한다. 검색 모드에서는 현행 문서의 예약 절을 먼저 찾고, 실행기가 그 출처에 이미 연결해 둔 정책 값을 읽는다. [7편의 RAG](/agentic-ai/rag/)에서 문서 검색은 근거 절을 찾는 데 사용했고, 실제 예약 조건은 검증된 구조화 값으로 연결했다. 숫자 48을 모델이 다시 생성하도록 두지 않았다.

## 같은 일곱 요청으로 두 경로 비교

[lab_assistant.py](lab_assistant.py)와 [approval.py](/agentic-ai/approval/approval.py)를 같은 폴더에 두고 Python 3.13.18에서 실행했다. 기준선은 A의 일정만 읽는다. 통합 경로는 u1의 선호, 접근 가능 장소, 일정, 현행 문서 `v2#book`의 48시간 조건을 차례로 적용한다. u2의 사용 가능 장소는 B뿐이다. 예약 서비스 대신 프로세스 안의 사전에 결과를 기록했다.

```bash
python3 lab_assistant.py
```

| 입력 | A만 읽는 기준선 | 통합 경로 |
|---|---|---|
| u1이 조회, 선호 B에 14:00이 있음 | A 10:30 | B 14:00 |
| u1이 조회, B를 사용할 수 없고 A에 10:30 | A 10:30 | A 10:30 |
| u2가 조회, 사용할 수 없는 A에만 빈 시간 | `no_accessible_slot` | `no_accessible_slot` |
| 방문 30시간 전 예약 요청 | `unhandled` | `notice_too_short` |
| 방문 48시간 전 요청, 승인 없음 | `unhandled` | `needs_matching_approval` |
| 방문 48시간 전 요청, B 14:00 승인 | `unhandled` | `committed` |
| 같은 ID와 내용으로 재호출 | `unhandled` | `same_request` |

검색까지 실행할 때는 [rag.py](/agentic-ai/rag/rag.py)와 [retrieve.py](/agentic-ai/memory-retrieval/retrieve.py)도 같은 폴더에 둔다. Ollama 0.40.11과 `all-minilm:22m`으로 예약 질문을 검색하니 `v2#book`이 유사도 0.6111로 나왔다. 검색 경로와 구조화된 정책을 바로 읽는 경로 모두 표와 같은 결과였다.

```bash
ollama pull all-minilm:22m
python3 lab_assistant.py --retrieve-policy
```

쓰기 직전 검사에 도달한 경우는 승인 대기, 승인 완료, 재호출 세 건이었다. 처리된 예약은 한 건이었다. 버전 조건을 체크한 30시간 요청은 쓰기 함수까지 도달하지 않았다. 24시간 기준을 담은 구버전을 참조하면 이 사례의 결과가 달라질 수 있다. 이 예제는 현행 정책의 단일 값, 실험실별 시간 한 개, 동시 쓰기 없는 입력으로 실행했다.

## 동시에 두 사람이 같은 시간을 확정하면

앞 예제의 사전은 요청이 순서대로 들어오는 프로세스 안에서만 중복을 확인한다. 실제 예약에는 서로 다른 두 문제가 있다. 같은 사람이 네트워크 오류 뒤 요청을 다시 보내는 경우에는 기존 결과를 찾아야 한다. 다른 두 사람이 같은 슬롯을 동시에 확정하는 경우에는 한 사람만 예약에 성공해야 한다. 첫 문제는 `(actor, request_id)` 유일성으로, 두 번째는 `(room, slot)` 유일성으로 나눠 제약을 걸었다. 예제의 일정은 하루치 고정 슬롯이다. 여러 날짜나 겹치는 시간 범위를 받는 서비스라면 시작일과 겹침 조건까지 예약 서비스에 포함한다.

[sqlite_reserve.py](sqlite_reserve.py)는 임시 SQLite 파일을 만들어 두 스레드를 배리어에서 동시에 출발시킨다. 승인 레코드에는 사용자, 장소, 시간, 정책 버전과 만료 시각이 있다. 쓰기는 사용자별 요청 ID, 현행 정책 및 승인 확인, 슬롯 삽입, 이벤트 삽입을 같은 트랜잭션 안에서 처리한다. SQLite의 `BEGIN IMMEDIATE`로 쓰기 트랜잭션을 먼저 확보한다. 빈 시간을 화면에서 보여 준 조회가 끝난 뒤에도, 예약 순간 DB의 슬롯 제약이 충돌을 막는다. [Transaction · SQLite](https://www.sqlite.org/lang_transaction.html)

```bash
python3 sqlite_reserve.py
```

| 주입한 상황 | SQLite에서 확인한 결과 |
|---|---|
| 두 사용자 모두 B 14:00을 승인받고 동시에 요청 | 한 건 `committed`, 한 건 `slot_taken` |
| 성공한 요청을 응답이 유실됐다고 가정하고 같은 내용으로 재전송 | 원래 예약 ID 1과 `already_committed` |
| 성공한 요청 ID로 시간만 변경 | `request_conflict` |
| 처음 보는 요청에 만료 시각과 같은 시각 전달 | `approval_expired` |
| 현행 정책 v2에서 v1 승인 전달 | `needs_approval` |
| 예약과 이벤트 삽입 뒤 커밋 전 예외 | 예약 1건, 발송 대기 이벤트 1건으로 롤백 |
| 같은 미커밋 요청을 다시 처리 | 예약 2건, 이벤트 2건 |

두 사람 중 어떤 요청이 먼저 잠금을 얻을지는 실행마다 달라질 수 있다. 테스트에서는 요청자에 상관없이 성공 1건, 충돌 1건인지를 본다. 응답이 유실된 사례는 이미 완료한 요청의 결과를 되돌려 받는 경로다. 완료 전인 새 요청에는 승인 만료를 적용하며, 승인 만료 다음에도 같은 요청 ID에 대해 기존 예약 ID를 확인할 수 있다. 예제에서 새 요청은 과거 정책의 승인을 재사용하지 않았다.

## 예약 커밋과 후속 알림의 경계

예약 서비스가 예약은 커밋했는데, 알림 API를 부르기 전에 종료됐다고 하자. 두 시스템을 한 SQLite 트랜잭션에 넣을 수는 없다. 트랜잭션 아웃박스는 업무 상태와 ‘나중에 보낼 이벤트’를 같은 DB 트랜잭션에 저장한다. 예약이 커밋되면 발송 대기 레코드도 남고, 예약이 롤백되면 이벤트도 없어지는 구조다. 후속 작업자는 그 표를 읽어 외부로 보낸다. 발송 뒤 처리 완료 표시 전에 중단되면 같은 이벤트가 다시 나갈 수 있으므로 수신 측에서도 이벤트 ID를 기준으로 중복을 처리한다. 이 예제에서는 로컬 표까지 검사했고 알림을 실제로 전송하지 않았다. [Transactional outbox pattern · AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

다른 서비스에서 이미 끝낸 변경을 되돌려야 하는 경우에는 업무상의 보상 작업을 실행한다. 예를 들어 예약이 확정됐으나 후속 확인이 거부됐을 때 ‘예약 취소’가 가능한지 정책을 본다. 시간 취소와 이미 전달한 메시지 삭제는 같은 문제가 아니며, 중간에 사람이 다시 확인해야 할 수도 있다. 긴 실행은 무엇을 완료했고 어떤 보상이 가능한 상태인지 보관한다. [Compensating Transaction Pattern · Microsoft Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)

## 새 버전을 비교할 때 상태와 근거를 나란히 두기

구조화한 예약 정책은 출처 ID와 정책 버전을 함께 둔다. RAG가 비슷한 문서를 먼저 가져와도 슬롯의 권한이나 48시간 필드를 바로 바꾸지 않는다. 실제 요청 경로에 적용할 때는 구조화 정책을 배포할 때 읽은 문서 버전과 연결하고, 새 버전 자료가 준비되기 전에는 기존 응답을 다시 확인하거나 보류할 수 있다. 메모리는 사용자의 후보 순서를 바꾸고, 도구의 최신 결과는 그 후보의 실현 가능성을 확인한다. 승인과 쓰기 계층은 이 둘을 다시 검증한다.

실험실 도우미를 평가할 때는 일정 검색의 정확도 외에 승인 없이 예약한 횟수, 같은 예약이 중복된 횟수, 만료된 정책이 실제로 적용된 횟수도 센다. ‘모델이 어느 슬롯을 제안했는가’와 ‘서버에 어느 슬롯이 커밋됐는가’를 같은 요청 ID에서 대조하면, 분류 오류와 쓰기 오류를 각각 찾을 수 있다. 예제로부터 옮길 만한 것은 정답 문자열보다 그 문자열을 뒷받침한 관찰, 검증과 실행 로그다. [9편의 회귀 평가](/agentic-ai/evaluation/) · [10편의 사용자 승인](/agentic-ai/approval/)

## 모델을 붙일 위치

요청 종류와 접근 권한이 이미 정해져 있으면 통합 흐름을 평범한 코드로 실행할 수 있다. 자연어에서 날짜와 요청 범위를 읽거나 여러 부서의 안내 문서를 찾아야 할 때는 모델에 후보를 고르는 일을 줄 수 있다. 모델이 제안한 장소와 시간은 일정 조회에서 확인하고, 예약은 승인 기록과 맞을 때 실행한다. 작업이 복잡해져도 목표 달성, 요청당 호출 수, 근거와 승인 상태를 각각 비교할 수 있다. [Introduction to LLM Agents · Tanay Varshney, NVIDIA, 2023-11-30](https://developer.nvidia.com/blog/introduction-to-llm-agents/) · [Building effective agents · Anthropic Engineering, 2024-12-19](https://www.anthropic.com/research/building-effective-agents)

실제 예약을 연결할 때는 같은 ID의 재처리 여부와 현재 빈 시간을 서버에서 함께 확인한다. 사용자가 확인한 뒤 다른 사람이 그 시간을 예약할 수 있다. 새 시간 후보를 제시하면 그 값도 다시 확인받는다. 네트워크 응답이 끊기면 이미 반영됐는지를 먼저 확인할 수 있어야 한다. [10편의 승인 경계](/agentic-ai/approval/) · [11편의 서빙과 도구 지연](/agentic-ai/serving/)

이 예제에서는 사용자의 선호가 후보 순서만 바꿨다. 접근 권한과 예약 기한, 승인은 그대로 적용했다. A만 조회하는 기준선이 처리하던 요청을 남겨 두고, 필요한 조건을 하나씩 연결해 결과를 비교할 수 있었다.
