“오늘만 B에서 찾아 줘”와 “12월부터는 항상 B를 먼저 봐 줘”에는 라벨이 다르게 붙는다. 두 문장에 같은 실험실 이름이 있어도 앞 문장은 지금 실행에 쓰고, 뒤 문장은 12월 이후 새 대화에서 쓸 수 있다. 모델이 “아마 C를 좋아할 것”이라고 추정했다면 승인된 선호 사이에 끼워 넣지 않는다. [3편의 체크포인트와 기억 범위](/agentic-ai/memory-layers/)

## 기록 단위를 정하기

메모리 서베이는 쓰기, 관리, 읽기를 나눠 설명한다. 쓰기는 관찰 전체에서 필요한 정보를 고르고, 관리는 여러 항목을 정리하고, 읽기는 이번 질문에 맞는 내용을 가져오는 단계다. 원문은 예외나 근거까지 보존하기 쉽고, 구조화한 사실은 검색과 갱신에 편하다. 구조화한 값에 근거가 남아 있으면 요약에서 빠진 맥락을 다시 확인할 수 있다. [A Survey on the Memory Mechanism of Large Language Model based Agents · Zeyu Zhang 외, 2024-04-21, §3.4 및 §5.3](https://arxiv.org/html/2404.13501#S5.SS3)

| 필드 | 예시 | 쓰임 |
|---|---|---|
| 소유자와 이름 | 사용자 u1, `preferred_lab` | 같은 사용자의 같은 선호를 찾는다. 예제 함수에는 u1의 행만 넣는다. |
| 값 | `LAB-B` | 컨텍스트에 넣을 수 있는 작은 단위다. |
| 출처 | `u1:t1:7` | 어느 대화 항목에서 값을 얻었는지 가리킨다. |
| 적용 범위 | 확인된 선호, 이번 요청, 도구 관찰, 추정 | 장기 보관 여부를 결정한다. |
| 기록 날짜 | 11월 16일 | 그때 앱이 알고 있던 정보만 보는 조회에 쓴다. |
| 유효 기간 | 12월 1일부터 | 실제 대상 날짜에 적용할 값을 고른다. |

## 기록일과 적용일을 나눠 조회하기

[실행 코드](memory_policy.py)는 입력에 출처와 범위를 미리 붙이고 Python 3.13.18에서 저장 분기만 실행한다. 사용자의 자연어를 모델이 분류하는 단계는 이 예제에 없다. 대상 날짜 이전에 유효해진 후보 가운데 가장 최근에 유효해진 값을 고른다. 기록 날짜를 따로 제한하면 미래 적용을 이미 알던 시점과 아직 듣기 전인 시점을 구분할 수 있다.

```bash
python3 memory_policy.py
```

| 미리 라벨을 붙인 입력 | 분기 |
|---|---|
| 11월 16일부터 A를 선호 | 장기 기억 |
| 11월 16일에 들은 ‘12월 1일부터 B 선호’ | 장기 기억 |
| 11월 16일의 A 닫힘 관찰, 17일에 만료 | 실행 상태 |
| 확인하지 않은 C 선호 추정 | 제외 |
| 이번 요청에서만 B 우선 | 실행 상태 |

11월 16일까지 기록된 정보로 조회했을 때 11월 30일의 선호는 A, 12월 1일의 선호는 B였다. 기록 기준을 11월 15일로 바꾸니 12월 1일의 값은 `null`이었다. `valid_until`은 그 날짜를 포함하지 않는다. 이 예제의 장기 후보는 같은 날 같은 우선순위로 중복되지 않는다. 운영에서는 동률 시 처리, 기록 정정, 출처 접근 범위를 별도로 정한다.

LongMemEval은 먼저 무엇을 인덱싱할지, 그중 무엇을 가져올지, 가져온 기록에서 어떻게 답을 만들지를 나눠 실험했다. 시간 관련 질문에서는 사건 날짜를 더해 검색 범위를 좁혔다. 이 편에서는 모델이 날짜를 해석하도록 두지 않고 두 날짜를 그대로 전달했다. 자연어로 “지난주”를 받으면 기준일과 시간대 해석부터 평가해야 한다. [LongMemEval · Di Wu 외, ICLR 2025, arXiv v2 2025-03-04, §5.4](https://arxiv.org/html/2410.10813#S5.SS4)

장기 기억을 많이 남기면 새 세션에서 읽을 단서는 늘어난다. 같은 값의 사본이 여러 군데 생기면 수정할 범위도 늘어난다. 실험실 운영 상태처럼 자주 바뀌는 값은 오래된 관찰을 기억에서 되살리기보다 필요할 때 현재 상태를 조회하는 편이 맞았다.

## 소급 정정은 두 시간 축에서 다르게 보인다

12월 3일에 사용자가 “12월부터 B라고 했는데 C로 정정해 줘”라고 했다. 12월 4일에 묻는 ‘12월 2일의 선호’는 C다. 12월 2일 당시 앱이 보고 있었던 값은 B다. 앞의 질문은 실제 적용일 기준이고, 뒤의 질문은 당시 앱이 어떤 기록을 알고 있었는지 재현한다. 저장 행에 적용 기간과 기록이 유효하다고 알고 있던 기간을 별도로 두면 둘 다 조회할 수 있다. Fowler는 이 두 축을 actual time과 record time으로 설명한다. [Bitemporal History · Martin Fowler, 2021-04-07](https://martinfowler.com/articles/bitemporal-history.html)

| 값 | 규칙이 적용되는 기간 | 앱이 그 버전을 유효하다고 알고 있던 기간 |
|---|---|---|
| A | 11/16부터 12/01 전까지 | 11/16부터 |
| B | 12/01부터 | 11/16부터 12/03 전까지 |
| C | 12/01부터 | 12/03부터 |

모든 기간은 시작일을 포함하고 끝나는 날을 포함하지 않는 반열린 구간이다. 예제는 날짜 단위로 비교한다. 시간이 필요한 서비스에서는 표준 시간대를 정하고, 문장의 ‘내일부터’는 발화 시각과 사용자 시간대에서 절대 시각으로 바꾼다. 사용자가 12월 3일까지 B라고 말한 사실과 12월 3일에 B가 적용되는지는 각각 다른 조건이다.

아래는 SQL 조회의 중심 조건이다. `?1`은 조회하려는 날짜, `?2`는 앱이 알고 있던 기준 날짜를 뜻한다. [temporal.py 다운로드](temporal.py)

```sql
WHERE valid_from <= ?1 AND (valid_until IS NULL OR ?1 < valid_until)
  AND known_from <= ?2 AND (known_until IS NULL OR ?2 < known_until)
```

`python3 temporal.py`로 실행했다. 12월 2일을 12월 2일 기준으로 읽으면 B였고, 같은 날을 12월 4일 기준으로 읽으면 C였다. 12월 3일 경계에는 C만 남았고, 12월 4일 기준으로 본 11월 30일의 값은 A였다. C와 같아야 할 기간에 D를 추가로 넣으니 `conflict`와 두 후보를 반환했다. 마지막에 들어온 행을 무조건 고르면 등록 순서가 같은 두 값이나 동시 업데이트의 충돌을 숨길 수 있다.

## 추출 제안과 장기 기록 사이의 조건

장기 기억 쓰기에는 새 문장 전체, 출처, 적용 범위가 필요하다. “요즘 자주 B를 썼다”는 행동 기록으로 남길 수 있고, 장기 선호 업데이트를 뜻하는지는 확인할 수 있다. 서로 다른 출처에서 같은 값이 도착하면 근거 링크를 합치고, 기존 값과 달라지면 날짜가 다른 변경인지, 소급 정정인지, 동시 충돌인지 먼저 정한다. 새 글이 예전 문장을 인용한 경우에는 인용 날짜를 값의 유효 시작일로 쓰지 않는다.

이 글의 조회는 이미 확정된 행만 받는다. 모델에 추출을 맡긴다면 모델 제안은 `key/value/scope/effective_from/source_message_id` 같은 구조화 값으로 받는다. 앱이 원 발화에 접근할 수 있는지, 허용된 키인지, 기존 기간과 겹치는지를 검사한 뒤 저장한다. 쓰기의 결과는 새 대화에서 얼마나 잘 기억했는지 외에도 저장하면 안 되는 문장을 장기 항목으로 만들었는지 따로 평가한다. 한 세션에서만 쓸 지시나 민감한 내용을 저장한 오탐은 맞는 항목 하나를 빠뜨린 경우와 비용이 다르다.
