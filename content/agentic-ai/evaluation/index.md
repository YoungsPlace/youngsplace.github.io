일정 시스템이 ‘B 14:00’이라고 답했다. 채점할 때는 14:00만 비교하면 A의 시간을 말한 답도 통과한다. B와 시간을 모두 맞혀도, B를 조회하지 않고 값을 짐작했을 수 있다. 과업의 답, 근거, 호출 비용을 따로 기록했다. [2편의 일정 조회](/agentic-ai/replanning/) · [7편의 출처 검증](/agentic-ai/rag/)

## 사례를 만들고 어떤 답을 맞았다고 할지 정하기

| 항목 | 이번 실험에서 비교한 값 |
|---|---|
| 과업 완료 | 기대한 상태, 실험실, 시간이 모두 일치하는가 |
| 근거 | 제시한 실험실과 시간이 그 실행의 일정 도구 결과에 모두 있는가 |
| 보류 | 빈 일정, 시간 초과, 순환에 맞는 상태를 반환했는가 |
| 비용과 지연 | 실제 실행한 도구 수와 경로별 가정 시간, 지연의 p50과 p95 |
| 실패 단계 | 예상과 다른 상태를 받은 첫 사례에서 내역을 확인한다. |

시간을 찾지 못한 입력에서는 장소를 채점하지 않았다. 정상 조회에 값이 없으면 `no_slot`, 두 번 모두 조회가 시간 초과면 `timeout`이 정답이다. 근거 위반은 시간을 제시한 결과만 검사한다. 답을 거의 안 하는 구성도 위반 0건이 나올 수 있어 시간 반환 수를 같이 적었다.

## 7개 일정 사례를 두 번 채점

[evaluate.py](evaluate.py)와 [replan.py](/agentic-ai/replanning/replan.py)를 같은 폴더에 두고 Python 3.13.18로 실행했다. 2편의 합성 입력 7개를 각 정책에 한 번씩 넣었다. 상태 요청 10ms, 일정 요청 20ms, 타임아웃 60ms를 가정해 각 실행 기록을 합산했다. 시간은 대기한 실측값이 아니다. p50은 중앙값, p95는 오름차순 정렬 뒤 `ceil(0.95 × N)`번째 값이다. N이 7이라 p95는 최대값과 같다.

```bash
python3 evaluate.py
```

| 정책 | 정확한 결과 | 시간을 제시함 | 근거 없는 시간 | 도구 호출 | 가정 p50 | 가정 p95 |
|---|---:|---:|---:|---:|---:|---:|
| A만 조회 | 3/7 | 1 | 0 | 12 | 30ms | 70ms |
| 관찰에 따라 변경 | 7/7 | 4 | 0 | 19 | 40ms | 130ms |

첫 타임아웃 뒤 복구되는 경우는 호출을 한 번 더 하고 시간을 찾았다. 두 번 모두 시간 초과인 경우에도 추가 호출이 들어갔고, 두 정책의 응답 상태는 같았다. 지연을 더 쓴 사례에서 실제로 목표 달성이 늘었는지를 따로 보면 어떤 재시도 규칙을 유지할지 결정하기 쉽다.

짧은 과업의 비용도 도구 호출과 모델 호출을 구분할 수 있다. 모델을 붙이면 입력·출력 토큰, 대기 시간, 캐시 여부에 따라 값이 달라진다. 이 예제의 호출 수 19는 외부 요금이나 운영 지연을 추정하기 위한 청구 자료로 쓰지 않았다. [AI Agents That Matter · Sayash Kapoor 외, arXiv 초판 2024-07-01](https://arxiv.org/abs/2407.01502)

## 개선한 사례와 퇴행한 사례를 짝지어 보기

같은 일곱 입력을 두 정책에 실행했으므로 결과는 짝을 이룬다. ‘A만 조회’에서 실패하고 ‘복구’에서 성공한 사례를 b, 반대로 기존에는 맞았는데 새 정책에서 틀린 사례를 c로 둔다. 두 정책이 둘 다 맞히거나 둘 다 틀린 사례는 정확도 차이를 만들지 않는다. 차이는 `(b−c)/N`이다. 정확도만 각각 3/7과 7/7로 적는 것보다 어느 쪽에서 몇 건이 움직였는지가 드러난다.

```bash
python3 evaluate.py --paired
```

실행 출력은 개선 4, 퇴행 0, 동률 3이었다. McNemar의 정확 검정에서는 두 정책의 맞고 틀림이 바뀐 네 쌍만 놓고, 차이가 없다는 가정에서 각 방향의 확률을 1/2로 본다. 네 쌍이 모두 한 방향일 양측 확률은 `2×(1/2)⁴=0.125`다. 이 수치는 작은 표본에서 4승 0패라는 모양을 어떻게 세는지 보여준다. 코드 작성에 쓴 합성 사례이므로 이 값을 실제 사용 요청에 대한 통계적 근거로 해석할 수 없다. 비슷한 템플릿에서 파생된 문제들을 독립 표본으로 셀 때도 불확실성을 과소평가할 수 있다. [McNemar Test · NIST](https://www.itl.nist.gov/div898/software/dataplot/refman1/auxillar/mcnemar.htm)

새 요청에서 비교할 때는 문제 ID를 고정하고 두 정책을 같은 입력에 돌린다. 결과 차이의 불확실성을 보려면 짝을 유지한 상태로 문제 단위 재표본추출을 하고, 같은 문서나 사용자에서 만든 사례가 많다면 그 묶음을 단위로 삼을 수 있다. 모델의 랜덤성을 보려는 반복과 새로운 문제에 대한 성능을 보려는 표본 수를 구분한다. 동일 문제 100회가 서로 다른 문제 100개와 같은 의미를 갖지는 않는다.

## 검색, 인용, 보류를 분리하는 채점표

검색은 `Recall@K = 상위 K에 포함된 관련 문서 수 / 전체 관련 문서 수`로 볼 수 있다. 첫 정답이 빨리 나타나는지 보고 싶으면 첫 관련 문서 순위의 역수(MRR)를 여러 질문에 평균한다. 정답 없는 질문에서는 전체 평균에 어떻게 반영할지 미리 정하고, 보류 정확도는 따로 계산할 수 있다. [7편에서 재정렬 결과에 MRR 적용](/agentic-ai/rag/)

| 상황 | 검색 채점 | 생성 채점 |
|---|---|---|
| 정답 절이 상위 K에 없는데 답함 | 근거 회수 실패 | 인용과 주장 대조 |
| 정답 절이 들어 있었는데 답이 다름 | 회수 성공 | 근거 읽기 실패 |
| 존재하는 ID를 인용했지만 문장이 주장을 지지하지 않음 | 문서가 반환됨 | 인용의 지지 여부 실패 |
| 정답 없는 질문에 보류 | 대상 없음 | 올바른 보류 |
| 정답 있는 질문에 보류 | 회수 결과에 따라 구분 | 답변 범위 감소 |

서비스에 보류가 들어가면 전체 요청 중 얼마나 답했는지(coverage)와 답한 요청의 정확도(selective accuracy)를 같이 본다. 모든 답을 보류하면 틀린 답 개수는 작아지는데 사용자는 필요한 정보를 못 얻는다. 승인이나 예약에서 보류 기준을 정할 때는 맞지 않는 시간을 제안한 비용과 확인을 한 번 더 요청한 비용이 다르다.

실험 비교에서는 요청당 모델 호출 수, 입력·출력·캐시 토큰과 도구 수를 먼저 저장한다. 예산을 고정한 채 성공률을 비교하거나, 성공률이 비슷한 두 설정에서 어느 쪽이 지연이나 비용이 낮은지 본다. 배포 판단에서는 정확도만 올라가면서 도구 호출과 p95가 급격히 늘어난 설정을 따로 확인한다. 과업 성능과 비용을 함께 보고, 개발에서 쓰지 않은 사례를 별도의 단위로 떼어 두자는 근거는 Kapoor 외의 평가 분석에 있다. [AI Agents That Matter · Sayash Kapoor 외](https://arxiv.org/abs/2407.01502)

## 개발 사례와 평가 사례를 분리하기

위 7개 사례는 이미 계획을 만들 때 사용했다. 회귀 비교에는 쓸 수 있고 새 입력에 대한 성능은 보여주지 않는다. 개발할 때 손보지 않은 데이터에서는 닫힌 장소가 여러 곳인 경우, 안내에 후보가 누락된 경우, 사람이 사용을 중단한 경우처럼 경계가 더 다른 요청을 준비할 수 있다. 생성을 추가하면 여러 번 실행하고 같은 근거로도 답이 바뀌는지를 본다.

기억을 평가할 때도 검색 성공과 최종 답변을 나눈다. 현행 기억이 검색됐지만 모델이 오래된 대화의 값을 답했다면 검색과 읽기 단계의 결과가 다르다. LongMemEval은 정보 추출, 다중 세션 추론, 시간 추론, 정보 변경, 답변 보류를 따로 다룬다. NVIDIA의 공개 학습 경로에는 RAG와 의미 검색 평가 과정이 있다. [LongMemEval · Di Wu 외, ICLR 2025, arXiv v2 2025-03-04](https://arxiv.org/abs/2410.10813) · [NVIDIA NCP-AAI 학습 경로 · 2026-11-16 확인](https://www.nvidia.com/en-us/learn/certification/agentic-ai-professional/#certification-learning-path)
