실험실 A의 첫 빈 시간을 찾는 계획에는 두 단계면 된다. A가 열렸는지 확인하고, 열렸으면 일정을 조회한다. A가 닫혔으면 두 번째 단계 자체가 바뀐다. A가 열려 있고 일정 서버가 응답하지 않으면 같은 조회를 한 번 더 해 볼 수 있다. 계획을 세울 때 아는 정보와 도구를 실행한 뒤 얻는 정보가 다르다. [1편의 일정 조회](/agentic-ai/agent-loop/)

## 계획, 행동, 관찰

목표는 ‘사용할 수 있는 첫 시간 확인’으로 둔다. 계획의 각 단계에는 필요한 입력, 성공 조건, 실패 시 분기를 붙인다. A의 일정 조회는 A가 열렸다는 관찰이 선행 조건이다. B의 상태 조회는 A에서 대체 장소 B를 안내받았을 때 계획에 추가된다. NVIDIA의 입문 글은 복합 질문을 하위 과제로 나누는 계획과, 관찰을 보고 당시 계획을 다듬는 과정을 계획 모듈 안에서 설명한다. [Introduction to LLM Agents · Tanay Varshney, NVIDIA, 2023-11-30](https://developer.nvidia.com/blog/introduction-to-llm-agents/#planning_module)

ReAct는 모델이 짧은 추론 텍스트와 행동을 만들고, 환경에서 돌아온 관찰을 다음 입력에 넣는 방식이다. HotpotQA와 FEVER 실험에서는 제한된 위키피디아 환경의 검색·본문 조회와 답변 제출을 사용했다. 저자 코드의 `wikienv.py`와 노트북에서 질의에 대응하는 행동과 환경 응답이 이어지는 구조를 볼 수 있다. 이 글의 예제에서는 모델 대신 Python 규칙이 다음 행동을 고른다. 같은 관찰에 같은 복구가 일어나게 해 어떤 분기가 효과를 냈는지 좁혀 봤다. [ReAct · Shunyu Yao 외, ICLR 2023, arXiv v3 2023-03-10](https://arxiv.org/html/2210.03629) · [저자 예제 코드](https://github.com/ysymyth/ReAct)

## 관찰마다 복구 조건 두기

| 관찰 | 이어서 할 일 | 종료 조건 |
|---|---|---|
| 운영 상태가 닫힘 | 안내된 대체 장소의 상태부터 조회한다. | 대체 안내가 없거나 앞에서 방문한 장소면 종료한다. |
| 일정 조회가 성공했고 값이 비어 있음 | 대체 장소 확인까지 요청된 경우에만 후보를 바꾼다. | 후보가 더 없으면 빈 일정으로 반환한다. |
| 일정 조회가 타임아웃 | 같은 읽기 요청을 한 번 재시도한다. | 두 번 모두 타임아웃이거나 전체 호출 예산이 끝나면 중단한다. |
| 일정 값이 있음 | 해당 도구가 확인한 장소와 시간을 반환한다. | 목표 달성. |

운영 상태는 유효한 응답이고 타임아웃은 일정의 상태를 아직 모른다는 뜻이다. 둘을 같은 `None`으로 받으면 ‘빈 시간이 없다’는 잘못된 결정으로 이어진다. 예제는 타임아웃을 별도의 결과로 기록한다. 실제 HTTP에서 재시도 간격을 결정할 때는 서버의 `Retry-After`와 남은 응답 시간을 함께 본다. 예약 완료 여부가 불명확한 쓰기 요청에는 읽기와 다른 정책이 필요하다. [HTTP Semantics · Fielding, Nottingham, Reschke, IETF, 2022-06, §9.2.2 및 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

## 합성 일정으로 호출 경로 비교

[실행 코드](replan.py)는 외부 API에 접속하지 않는다. Python 3.13.18에서 A만 확인하는 `fixed`와 대체 장소 및 읽기 재시도를 처리하는 `adaptive`를 실행했다. 전체 호출 상한은 6회이며, 운영 상태 조회와 실패한 일정 조회도 한 번씩 센다. 1편의 고정 워크플로에도 대체 분기가 있었다. 여기서 쓰는 `fixed`는 각 복구 규칙의 차이를 확인하기 위해 A만 조회하는 기준선이다.

```bash
python3 replan.py fixed closed
python3 replan.py adaptive closed
python3 replan.py adaptive timeout_once
python3 replan.py adaptive timeout_once --max-calls 2
```

| 입력 | A만 조회 · 호출 수 | 관찰에 따라 변경 · 호출 수 |
|---|---|---|
| A 열림, 10:30 | A 10:30 · 2 | A 10:30 · 2 |
| A 닫힘, 대체 B에 14:00 | `closed` · 1 | B 14:00 · 3 |
| A 열림, 빈 일정, 대체 B에 14:00 | `no_slot` · 2 | B 14:00 · 4 |
| A의 일정 조회 첫 시도 타임아웃 | `timeout` · 2 | A 10:30 · 3 |
| A의 일정 조회 두 번 타임아웃 | `timeout` · 2 | `timeout` · 3 |
| 서로를 대체 장소로 안내하는 A와 B | `closed` · 1 | `cycle` · 2 |
| 대체 장소 없이 A의 일정이 비어 있음 | `no_slot` · 2 | `no_slot` · 2 |

`timeout_once`의 경로는 `status A → open`, `first_slot A → timeout`, `first_slot A → 10:30`이었다. 같은 입력에서 상한을 2회로 줄이니 재시도 전 `call_limit`으로 끝났다. 정상 사례에서는 같은 예산을 쓰고, 실패에서 복구할 때 조회가 추가됐다. 실제 시스템에서 이 비용을 판단하려면 한 번의 외부 호출에 걸리는 지연과 일정 조회 성공률을 같이 재야 한다.

## 어떤 부분을 모델에 맡길까

이 예제의 일정 도구는 상태 값과 대체 장소를 구조화해서 반환한다. 분기 규칙이 작고 명확해 Python으로 표현하기 쉽다. 이후 안내문 종류가 많아지고 어떤 문서에서 대체 장소를 찾을지 요청마다 달라지면, 모델이 후보와 필요한 하위 과제를 제안할 수 있다. 그때도 런타임이 조회 가능 범위, 이미 간 경로, 응답 기한을 관리할 수 있다. Anthropic은 에이전트가 매 단계 환경의 실제 결과를 받아 진행 상황을 판단하고, 반복 횟수나 사람 확인 지점에서 멈추는 구조를 설명한다. [Building effective agents · Anthropic Engineering, 2024-12-19](https://www.anthropic.com/research/building-effective-agents)

ReAct 논문의 PaLM-540B 프롬프트 실험에서 ReAct의 HotpotQA exact match는 27.4, CoT는 29.4였다. FEVER 정확도는 각각 60.9와 56.3이었다. 논문은 이전 행동을 반복하는 경로와 유용한 검색 결과를 못 얻은 경로도 분석했다. 외부 정보를 볼 수 있게 했을 때의 이득은 과업과 검색 품질에 따라 달라진다. 이 글의 합성 실험에서는 복구 조건, 호출 수와 종료 사유를 확인했다. [ReAct §3.3, 표 1·2](https://arxiv.org/html/2210.03629#S3.SS3)

## 계획을 재사용하려면 의존 조건으로 적기

‘상태 조회 → 일정 조회’는 순서가 붙은 문장이다. 실행기는 한 단계가 다음 단계에 무엇을 넘기는지까지 알아야 한다. 예를 들어 `read_schedule(B)`는 ‘B가 열림’이라는 확인, B에 대한 접근 범위, 남은 시간이 필요하다. A가 닫혔다는 응답이 오면 이미 끝난 A의 상태 조회를 다시 할 이유는 없다. 무효가 된 일은 A의 일정 조회와 그 결과를 쓰는 단계이고, B를 확인하는 새 경로만 추가한다. 이렇게 조건이 붙은 계획은 실패한 부분만 다시 계산하거나, 서로 의존하지 않는 단계를 병렬로 실행하기 쉽다.

| 계획에서 표현할 값 | A의 일정 조회에 넣는 값 | 재계획에서 읽는 값 |
|---|---|---|
| 입력 | 장소 A, 현재 요청의 날짜 | 확인된 새 장소와 날짜 제약 |
| 선행 조건 | A가 열려 있음 | 조건이 성립하지 않으면 이 단계 폐기 |
| 완료 조건 | 조회 결과가 확인됨 | 결과가 비어 있어도 조회 자체는 완료 |
| 재시도 조건 | 일시적인 읽기 오류 | 남은 시도 횟수와 응답 기한 |
| 다음 단계 | 근거와 함께 종료 | 대체 장소 확인 또는 사유를 보여 주고 종료 |

읽기만 있는 세 단계는 지시 그래프(DAG) 위에서 실행할 수 있다. 재시도나 새 후보 탐색은 같은 노드가 다시 등장한다. 실행 로그에서는 `step_id`와 `attempt`를 구분해 한 단계의 재호출과 새 계획의 단계를 분리할 수 있다. 실행에 이미 비용이 들었거나 외부 효과가 있었다면 계획을 수정하는 것과 완료한 효과를 되돌리는 것도 각기 다른 연산이다. [12편의 재개와 보상](/agentic-ai/lab-assistant/)

## ReAct와 미리 계획한 실행의 차이

ReAct 논문에서 모델의 텍스트 추론은 필요할 때 다음 질의를 고르거나 관찰을 합치는 데 쓰인다. 위키피디아 과제의 `Search[entity]`는 검색을 시작하고, `Lookup[string]`은 현재 읽고 있는 문서의 특정 표현을 찾고, `Finish[answer]`는 답을 낸다. 도구 이름은 셋으로 정해져 있어도 검색 문자열, 반복 횟수와 최종 근거가 실행 중 달라진다. 본문의 HotpotQA 비교에서 ReAct는 행동만 내는 Act보다 exact match가 25.7에서 27.4로 높았다. 추론만 하는 CoT의 29.4와는 순위가 반대였다. 모델, 도구 환경, 과업에 따라 관찰을 쓰는 이점과 검색 실패의 비용이 다르게 나타난다. [ReAct · Yao 외, §3 및 표 1](https://arxiv.org/html/2210.03629#S3)

실험실의 구조화된 응답에는 다음 조건이 거의 다 들어 있다. 자유롭게 계획을 쓰는 모델을 붙이더라도, 계획 답변에는 하위 목표, 대상과 필요한 증거만 요청하는 편이 테스트하기 쉽다. 모델이 설명을 길게 생성하는 것보다 도구의 반환값에 맞춰 계획이 수정됐는지 관찰한다. 최초의 계획을 저장해 두면 ‘원래 예정이 없던 B가 새 증거 때문에 추가됐는지’와 ‘계획은 그대로인데 같은 요청만 다시 보내는지’를 구분할 수 있다.

## 재시도 예산을 숫자로 계산하기

한 번의 읽기가 일시 오류로 실패할 확률을 p, 실패가 독립이라고 두면 두 번 모두 실패할 확률은 p²이다. 한 번 재시도할 때 평균 호출 수는 `1 + p`다. 예를 들어 p=0.2라면 완료 확률은 80%에서 96%, 평균 호출 수는 1.2회가 된다. 실제 장애에서 두 번의 실패는 같은 과부하나 장애 구간에 묶일 수 있다. 이때 필요한 값은 p가 아니라 첫 실패가 주어졌을 때 두 번째 시도도 실패할 조건부 확률이다. 그 값이 0.9라면 전체 실패가 0.2 × 0.9 = 0.18로만 줄어든다. 성공 이득 2퍼센트포인트와 부하 증가량을 비교하게 된다.

저장소까지 다섯 계층이 있고 각 계층이 최대 세 번 시도한다고 가정하면 마지막 계층에서 요청이 3⁵=243번 발생할 수 있다. 장애 시점에 세 요청이 동시에 재시도되면 다시 부하가 한꺼번에 걸린다. 지수 백오프는 다음 시도를 늦추고, 지터는 그 대기 시간에 분산을 준다. 사용자가 기다릴 수 있는 총 기한보다 대기와 실제 요청 시간이 길어지면 다시 호출할 이유가 없다. 여러 계층 중 하나에서 재시도 예산을 맡기면 외부 호출 횟수를 예측하기 쉽다. [Timeouts, retries, and backoff with jitter · Marc Brooker, AWS Builders’ Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

| 추적 필드 | 사례에서 확인하는 질문 |
|---|---|
| `attempt`, `deadline_remaining_ms` | 재시도를 시작할 시간이 있었나? |
| `failure_class` | 비어 있는 결과, 일시 오류, 권한 오류 중 무엇이었나? |
| `plan_revision`, `evidence_id` | 무슨 새 관찰 때문에 경로가 바뀌었나? |
| `stop_reason` | 빈 결과, 순환, 호출 예산 중 어디서 끝났나? |
