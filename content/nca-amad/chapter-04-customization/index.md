모델의 답변이 만족스럽지 않다고 바로 학습부터 시작할 필요는 없다. 지시가 모호한 것인지, 필요한 자료가 없는 것인지, 자료를 줘도 반복적으로 작업을 수행하지 못하는 것인지부터 구분해야 한다.

시험을 준비하면서 비교한 방법들을 **입력에서 바꾸는 것과 학습에서 바꾸는 것**으로 나누어 정리했다. Prompt·RAG·Fine-tuning의 선택에서 시작해 SFT와 LoRA의 관계, 학습 결과를 평가하고 배포하는 과정까지 연결한다. 아래 사례와 계산은 원리를 설명하기 위한 가정이다.

## 1. 세 방법은 경쟁 관계가 아니다

| 방법 | 주로 바꾸는 것 | 먼저 검토할 상황 |
| --- | --- | --- |
| Prompt engineering | 지시, 예시, 입력 구성 | 요구가 모호하거나 출력 형식이 일정하지 않음 |
| RAG | 응답 시 참고할 외부 근거 | 최신 정보나 접근 가능한 사내 자료가 필요함 |
| Fine-tuning | 학습 가능한 모델 파라미터 | 반복적인 업무 행동과 작업 성능을 맞추고 싶음 |

Prompt와 일반적인 RAG 사용만으로 생성 모델의 가중치가 갱신되지는 않는다. Fine-tuning은 미리 준비한 학습 신호로 파라미터를 조정한다. 다만 “RAG 시스템은 절대 학습하지 않는다”는 뜻은 아니다. 검색기나 생성 모델을 별도로 학습한 뒤 RAG에 사용할 수도 있다.

세 방법은 함께 사용할 수 있다. 학습으로 문서에서 정보를 추출하는 행동을 개선하고, RAG로 최신 문서를 제공하며, Prompt로 이번 요청의 출력 형식을 지정하는 식이다. 이름을 먼저 고르기보다 실패 위치를 정하는 것이 출발점이다.

가령 특정 문서 버전의 수치를 묻는데 모델이 오래된 값을 답한다면, 그 문서가 입력에 있었는지부터 확인한다. 반대로 정확한 문서를 줬는데 조건문을 반복해서 잘못 해석한다면 검색만 개선해도 문제가 남을 수 있다.

## 2. Prompt를 고칠 때는 결과를 비교할 수 있어야 한다

좋은 Prompt의 핵심은 길이가 아니라 작업의 명확성이다. 입력 자료, 해야 할 작업, 출력 형식, 정보가 없을 때의 행동을 구분해 적는다.

예를 들어 가상의 기술 문서 추출 작업을 다음처럼 정의할 수 있다.

> 제공된 문서에서 입력 전압의 최소값과 최대값을 추출한다. 단위는 원문대로 유지한다. 문서에 명시되지 않은 값은 추정하지 말고 `null`로 둔다. 값을 가져온 절 번호도 함께 반환한다.

“정확하게 답해 줘”라고만 쓰는 것보다 무엇을 성공으로 볼지 확인하기 쉽다.

**Zero-shot**은 수행 예시 없이 지시하는 방식이고, **few-shot**은 입력과 바람직한 출력의 예시를 함께 제공하는 방식이다. 예시를 넣는 것은 추가 학습과 다르다. 그 요청의 문맥 안에서 예시를 참고하게 한다.

Few-shot 예시는 정상 사례만 모으기보다 정보 누락, 복수 조건, 단위 차이 같은 경계를 포함하는 편이 유용하다. 단, 예시가 길어지면 입력 비용과 문맥 사용량이 늘어난다. 평가 데이터의 정답을 예시로 넣어 놓고 성능이 올랐다고 판단하면 데이터 누출이 된다.

출력을 JSON으로 제한하더라도 내용의 정답 여부는 별도 문제이다. JSON 스키마 검증은 키와 자료형의 형태를 확인하고, 문서 대조는 값과 근거가 맞는지 확인한다. **형식 적합성과 사실 적합성은 따로 측정한다.**

## 3. RAG는 검색과 생성을 따로 진단한다

RAG(retrieval-augmented generation)는 필요한 자료를 찾아 모델의 문맥에 제공하는 구성이다. 전체 과정에는 문서 수집과 파싱, 분할, 인덱싱, 검색, 선택된 근거의 전달, 답변 생성이 포함된다.

답변 실패를 다음 관찰 지점으로 나눈다.

| 관찰한 현상 | 먼저 확인할 곳 |
| --- | --- |
| 원본에는 있지만 저장된 텍스트에는 값이 없음 | 표·이미지·단위의 파싱과 문서 적재 |
| 인덱스에는 있지만 검색 후보에는 없음 | 질의 표현, 검색 방식, 필터, 후보 수 |
| 후보에는 있지만 최종 문맥에는 없음 | 재정렬, 중복 제거, 문맥 길이 제한 |
| 최종 문맥에 있지만 답을 잘못 만듦 | 지시, 근거 해석, 생성 모델, 출력 검증 |
| 값은 맞지만 출처가 다른 문서를 가리킴 | 인용 매핑과 출처의 일관성 |

[NVIDIA의 RAG 설명](https://developer.nvidia.com/blog/rag-101-retrieval-augmented-generation-questions-answered/)도 RAG를 단일 모델이 아닌 여러 단계의 시스템으로 보고, 파싱·분할·검색·재정렬을 개선 지점으로 다룬다.

### Chunk 크기에는 정답 하나가 없다

작은 Chunk는 관련 구간을 세밀하게 찾기 좋지만, 표 제목이나 조건이 다른 조각으로 떨어질 수 있다. 큰 Chunk는 문맥을 보존하는 대신 불필요한 정보가 함께 들어갈 수 있다. Overlap은 경계를 완화하지만 중복 저장과 검색 결과 중복을 늘릴 수 있다.

가상의 규격 문서에 “최대 전압 12V”라는 행과 “25°C에서 적용”이라는 주석이 있다고 하자. 숫자 행만 검색되면 모델은 조건 없는 12V로 답할 수 있다. 이런 문서는 고정 글자 수만 기준으로 자르기보다 표·절·주석 관계를 보존하는 방식을 검토해야 한다.

Semantic search는 의미 유사성을, keyword search는 정확한 용어의 일치를 활용한다. 제품 코드나 오류 번호처럼 한 글자 차이가 중요한 질의라면 둘을 조합하는 hybrid search를 비교할 수 있다. Reranker는 가져온 후보의 순서를 다시 평가하는 단계이다. 최초 후보에 정답이 전혀 없다면 재정렬만으로 되찾을 수 없다.

### 검색 문서와 출력은 문맥 예산을 나누어 쓴다

검색한 자료를 많이 넣는 것만으로 답변이 좋아지지는 않는다. 입력과 출력이 하나의 문맥 한도를 공유하는 모델에서는 답변을 생성할 공간도 남겨 두어야 한다.

앞서 복습한 계산처럼 공유 한도가 8,192토큰이라고 가정하자. 입력 구성요소를 중복 없이 계산했을 때 시스템 지시에 512토큰, 질문과 대화 기록에 1,536토큰, 검색 문서에 4,096토큰을 사용했다면 남는 예산은 다음과 같다.

$$
N_{remaining}=8192-(512+1536+4096)=2048\ \text{tokens}
$$

이는 **이 가정에서 문맥 한도가 허용하는 출력의 상한**이다. 별도 출력 한도나 설정한 최대 생성 길이가 더 작으면 실제 상한도 낮아진다. 채팅 템플릿·특수 토큰·도구 정의가 있다면 입력 계산에 포함해야 하며, 언어마다 글자 수를 토큰 수로 바꾸는 고정 비율을 적용하지 않는다.

문맥이 부족할 때는 필요한 조건이나 표 주석까지 잘라 내기보다, 중복 문서를 줄이고 질의와 관련 있는 근거를 선택한다. 출력 예산을 확보하는 일과 근거의 완전성을 유지하는 일을 함께 평가해야 한다.

### 검색 성능과 답변 성능의 분모를 고정한다

가정상 평가 질의가 100개이고, 질의마다 정답을 뒷받침하는 문서를 하나 지정했다고 하자. Top-5 검색 결과에 그 문서가 포함된 질의가 80개라면, 이 설정에서의 검색 성공 비율은 80%이다.

그 80개 중 72개에서 최종 답이 정확했다면 “검색에 성공한 경우의 답변 정확도”는 90%이다. 나머지 20개에서는 모두 답변도 실패했다고 가정할 때 전체 정확도는 72%이다. 90%만 보고하면 시스템 전체 성능을 과대평가한다.

실제 문제에는 정답 근거가 여러 개이거나, 일부 근거만으로도 답할 수 있는 경우가 있다. 따라서 문서 단위 Recall, 질의 단위 검색 성공률, 답변 정확도를 같은 이름으로 섞지 않는다. 권한 밖 문서를 잘 찾아오는 것은 좋은 검색 성능이 아니라 접근 통제 실패이다.

## 4. SFT와 PEFT는 분류하는 축이 다르다

SFT(supervised fine-tuning)는 입력과 바람직한 출력 예시를 사용해 학습하는 방법이다. 생성 모델에서는 보통 입력과 앞선 정답 토큰을 조건으로 다음 정답 토큰의 확률을 높이는 손실을 사용한다.

$$
\mathcal{L}_{SFT}
=-\sum_{(x,y)\in\mathcal{D}}\sum_t
\log p_{\theta}(y_t\mid x,y_{<t})
$$

\(x\)는 입력, \(y\)는 목표 응답, \(\theta\)는 모델 파라미터이다. 식은 핵심을 보이기 위해 합으로 썼다. 실제 학습에서는 토큰 평균, 마스킹, 가중치 등의 설정이 추가된다. 특히 Prompt 부분과 응답 부분 중 어디에 손실을 적용하는지 확인해야 한다.

PEFT(parameter-efficient fine-tuning)는 전체 파라미터 대신 제한된 파라미터를 학습하는 접근이다. **SFT는 어떤 학습 신호를 쓰는가에 가깝고, PEFT는 무엇을 얼마나 갱신하는가에 가깝다.**

따라서 SFT를 전체 가중치 갱신으로 수행할 수도 있고, LoRA 같은 PEFT 방식으로 수행할 수도 있다. “SFT와 LoRA 중 하나를 고른다”는 표현은 두 축을 혼동하기 쉽다. 어떤 서비스가 메뉴에서 Full SFT와 LoRA를 나누어 보여 주더라도, 학습 원리상 SFT가 반드시 전체 가중치 갱신을 뜻하지는 않는다. [NVIDIA의 Customization Concepts](https://docs.nvidia.com/nemo-helix/latest/documentation/customizer-reference/customization-concepts)는 맞춤화와 배포의 개념을 함께 설명한다.

학습 데이터에는 실제 운영에서 원하는 행동이 들어 있어야 한다. 항상 답을 만들어 내는 예시만 학습시키고, 운영에서는 근거가 없으면 답변을 보류하기를 기대하면 요구가 어긋난다. 누락과 불확실성을 처리하는 예시도 목표 행동의 일부이다.

## 5. LoRA는 가중치 변화량을 작게 표현한다

LoRA(low-rank adaptation)는 기존 가중치를 고정하고, 변화량을 낮은 랭크의 행렬 곱으로 학습하는 방식이다. [LoRA 원 논문](https://arxiv.org/abs/2106.09685)의 핵심을 한 선형 레이어로 표현하면 다음과 같다.

$$
W'=W_0+\Delta W,\qquad
\Delta W=\frac{\alpha}{r}BA
$$

\(W_0\in\mathbb{R}^{d_{out}\times d_{in}}\)가 기본 가중치라면, \(A\in\mathbb{R}^{r\times d_{in}}\), \(B\in\mathbb{R}^{d_{out}\times r}\)를 학습한다. \(r\)은 랭크이고 \(\alpha\)는 스케일 설정이다. 여기서는 통상적인 \(\alpha/r\) 스케일링을 사용하며 변형 기법에는 다른 방식도 있다.

원래 행렬의 파라미터 수는 \(d_{out}d_{in}\)이고, 추가 행렬은 다음과 같다.

$$
N_{LoRA}=r(d_{in}+d_{out})
$$

예를 들어 \(4096\times4096\) 행렬 하나에 \(r=8\)을 적용한다고 가정하면 다음과 같다.

- 원래 행렬: 16,777,216개
- LoRA 행렬 두 개: \(8\times(4096+4096)=65,536\)개
- 이 레이어에서의 비율: 약 0.391%

이 수치는 **한 레이어의 학습 대상 파라미터 비율**이다. 모델 전체 메모리가 0.391%가 되거나, 학습 시간이 그 비율로 줄어든다는 뜻은 아니다. 기본 모델의 순전파와 역전파 경로, 활성값 저장 등은 여전히 필요하다.

랭크를 늘리면 표현할 수 있는 변화량의 범위가 커지지만, 파라미터·메모리·과적합 가능성도 함께 고려해야 한다. 데이터가 부정확하거나 목표가 일관되지 않은 문제를 랭크 증가만으로 해결할 수는 없다. 어떤 레이어를 학습 대상으로 선택했는지도 성능에 영향을 준다.

## 6. QLoRA는 모든 연산을 4비트로 하는 기술이 아니다

QLoRA는 양자화해 저장한 기본 모델을 고정하고 LoRA 어댑터를 학습하는 접근이다. [QLoRA 원 논문](https://arxiv.org/abs/2305.14314)은 4비트 기본 모델, NF4, double quantization, paged optimizer 등을 제안했다.

여기서 기본 가중치의 **저장 표현**, 연산 시 사용하는 **계산 자료형**, 어댑터와 옵티마이저의 **학습 상태**는 구분해야 한다. 저장된 가중치가 4비트여도 계산 과정에서 더 높은 정밀도를 사용하며, 모든 상태가 4비트로 저장되는 것은 아니다.

가령 80억 개를 정확히 4비트씩만 저장한다는 이상적인 계산은 40억 바이트, 즉 4GB이다. 하지만 실제 파일과 실행 메모리에는 스케일 등 양자화 메타데이터, 양자화하지 않은 부분, 활성값, 학습 상태가 추가된다. “8B 모델이므로 4GB GPU에서 학습할 수 있다”는 결론은 성립하지 않는다.

QLoRA는 학습 메모리 제약을 완화하는 선택지이지 모든 작업에서 최상의 품질이나 가장 짧은 학습 시간을 보장하는 선택지는 아니다. 지원하는 모델 구조, 라이브러리, GPU, 계산 자료형을 확인하고 같은 평가 데이터로 비교해야 한다.

## 7. 선호 학습은 데이터의 형태부터 구분한다

정답 예시를 모으는 일과 두 응답 중 무엇이 더 나은지 판단하는 일은 다르다. 후자에서는 바람직한 답의 문장 전체를 새로 쓰지 않고도 피드백을 얻을 수 있다.

| 접근 | 대표적인 학습 신호 | 구분할 점 |
| --- | --- | --- |
| 전형적인 RLHF 구성 | 인간 선호로 학습한 보상 모델의 점수 | 보상 모델과 정책 최적화 단계가 있음 |
| DPO | 같은 입력의 선호·비선호 응답 쌍 | 별도의 보상 모델 학습 없이 직접 최적화 |
| KTO | 개별 응답의 바람직함·바람직하지 않음 | 반드시 응답 쌍을 구성할 필요는 없음 |
| GRPO | 한 입력에서 생성한 응답 집단의 보상 | 집단 내 상대적인 신호를 활용 |

DPO와 GRPO의 개념은 [NVIDIA의 맞춤화 문서](https://docs.nvidia.com/nemo-helix/latest/documentation/customizer-reference/customization-concepts), KTO의 이진 피드백 구성은 [KTO 원 논문](https://arxiv.org/abs/2402.01306)에서 확인할 수 있다. RLHF는 넓게 인간 피드백 기반 정렬을 가리키기도 하므로, 약어만 보고 특정 알고리즘 구성이 고정되어 있다고 생각하지 않는다.

어떤 방법이든 신호의 품질이 중요하다. 예를 들어 긴 답변을 계속 선호하면 길이가 품질의 대리 지표가 될 수 있다. JSON 파싱 성공만 보상하면 형식은 맞지만 틀린 값을 내는 응답을 강화할 수 있다. DPO가 보상 모델을 별도로 학습하지 않는다는 사실은 부정확한 선호 데이터의 영향을 받지 않는다는 뜻이 아니다.

Distillation도 이들과 구분한다. 교사 모델의 출력이나 분포를 학생 모델이 학습하는 접근으로, 작은 모델에 작업 능력을 옮기는 데 활용할 수 있다. 교사의 답변을 사용했다는 사실만으로 정답이 보장되지는 않으며 데이터 검증과 이용 조건 확인이 필요하다.

## 8. 학습 성공과 운영 성공은 다르다

훈련 손실이 줄었다고 목적을 달성한 것은 아니다. 학습한 사례를 잘 맞히는지와 처음 보는 사례에도 적용되는지를 분리한다.

**Overfitting**은 학습 데이터에 지나치게 맞춰 일반화가 나빠지는 문제이다. **Catastrophic forgetting**은 맞춤화 과정에서 기존에 갖고 있던 능력이 크게 손상되는 문제이다. 두 현상은 함께 생길 수도 있지만 같은 뜻은 아니다.

가상의 문서 추출 모델이라면 다음과 같이 평가를 설계할 수 있다.

1. 같은 문서의 유사 페이지가 학습과 평가에 나뉘지 않도록 문서 단위로 분할한다.
2. Prompt만 사용하는 기본 모델을 기준선으로 남긴다.
3. 형식 적합률, 값의 정확도, 근거의 정확도, 누락 처리 능력을 나누어 측정한다.
4. 새로운 문서 형식, 긴 입력, 단위 변경, 모호한 조건을 별도 집합으로 점검한다.
5. 목표 작업 외에 유지해야 하는 일반 능력과 안전 행동도 확인한다.
6. 최종 선택에 쓰지 않은 테스트 집합에서 결과를 확인한다.

학습률, 반복 횟수, 데이터 혼합 비율, LoRA 랭크를 모두 동시에 바꾸면 개선 원인을 추적하기 어렵다. 한 번의 작은 실험으로 모든 설정을 확정하기보다, 기준선을 고정하고 변화량을 남긴다. 프롬프트 템플릿과 토크나이저도 학습·평가·운영 간 일관되어야 한다.

오프라인 평가에서 좋아진 후보도 실제 사용 환경에서는 별도로 확인한다. **[A/B test](https://docs.aws.amazon.com/sagemaker/latest/dg/model-ab-testing.html)**는 비교 가능한 사용자나 요청 집단을 두 버전에 배정해 업무 성공률·지연·비용의 차이를 보는 실험이고, **[Canary 배포](https://docs.aws.amazon.com/sagemaker/latest/dg/deployment-guardrails-blue-green-canary.html)**는 새 버전의 노출을 작게 시작해 문제 발생 범위를 제한하는 운영 방식이다. 두 방법을 함께 쓸 수 있지만 목적은 같지 않다. 최소 품질 기준을 통과한 후보에 한해 노출하고, 오류율과 품질 저하를 탐지할 기준 및 되돌릴 버전을 준비한다.

## 9. 어댑터 배포와 최종 선택

LoRA 어댑터만으로 원래 모델을 완전히 대체하지는 못한다. 실행에는 기본 모델이 필요하다. 기본 모델과 어댑터를 함께 서빙하거나, 지원되는 구성에서는 변화량을 기본 가중치에 병합해 배포할 수 있다.

어댑터 방식은 작업별 교체와 관리에 유리할 수 있지만 실행 엔진의 지원 범위를 확인해야 한다. 병합은 별도 어댑터 경로를 없애는 데 도움이 될 수 있으나, 양자화된 모델에서는 병합·재양자화 절차에 따라 수치가 달라질 수 있다. 학습 직후 평가뿐 아니라 **실제로 배포할 산출물**을 다시 평가해야 한다.

가상의 기술 문서 도우미를 만든다면 다음과 같이 선택을 정리할 수 있다.

- 출력을 매번 다른 형식으로 만든다 → 명확한 스키마와 Prompt, 파서 검증부터 적용한다.
- 새 문서의 값과 출처를 모른다 → 문서 적재·검색·버전 관리를 포함한 RAG를 검토한다.
- 근거를 줘도 조건별 수치 추출에 반복적으로 실패한다 → 평가 집합을 만든 뒤 SFT를 비교한다.
- 전체 가중치 학습의 비용이 부담된다 → LoRA 또는 QLoRA의 지원 조건과 품질을 비교한다.
- 답변의 유용성을 평가한 피드백이 쌓인다 → 데이터 형태에 맞는 선호 학습을 검토한다.

Fine-tuning으로 사실을 학습할 수는 있지만, 자주 바뀌는 정보의 갱신·출처 제시·문서별 접근 통제를 모두 해결해 주지는 않는다.

## 정리

- Prompt는 작업 지시를, RAG는 필요한 근거를, Fine-tuning은 학습된 행동을 바꾸는 데 초점을 둔다.
- RAG의 실패는 파싱·검색·재정렬·생성·인용 단계로 나누어 진단한다.
- 공유 문맥 한도에서는 입력 자료뿐 아니라 출력 예산도 남겨 두며, 검색 성공률과 최종 답변 정확도를 따로 계산한다.
- SFT와 PEFT는 배타적이지 않다. SFT를 LoRA로 수행할 수 있다.
- LoRA의 작은 학습 파라미터 수와 모델 전체 메모리는 다르다. QLoRA도 모든 계산을 4비트로 수행하지 않는다.
- 학습 손실보다 독립적인 평가 결과를 보고, 배포할 기본 모델·어댑터·양자화 구성을 최종 검증한다.
