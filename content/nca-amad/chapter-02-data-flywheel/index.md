데이터가 많아지면 모델이 좋아질 것이라고 생각하기 쉽다. 하지만 중복된 기록, 잘못된 라벨, 오래된 문서가 늘어나는 것과 새로운 정보를 얻는 것은 다르다. 평가에 쓰일 정보가 학습 과정으로 새어 들어갔다면, 높은 점수도 실제 성능을 설명하지 못한다.

NCA-AMAD 공부에서 이 영역은 **데이터를 어떻게 준비하고, 어떤 기준으로 나누며, 개선됐다는 것을 무엇으로 확인하는가**로 정리했다. 데이터 처리에서 시작해 평가 지표를 계산하고, 운영 결과를 다음 버전으로 연결하는 Data Flywheel까지 살펴본다. 아래 수치와 서비스 사례는 학습용 가정이다.

## 데이터 종류와 용도를 먼저 구분한다

데이터 종류는 저장 형식의 차이이고, 학습·검색·추론에 사용한다는 것은 목적의 차이이다. 두 기준을 섞지 않아야 필요한 처리를 결정할 수 있다.

| 종류 | 예 | 확인할 문제 |
| --- | --- | --- |
| Structured | 행과 열을 가진 측정값, 관계형 테이블 | 자료형, 단위, 결측값, 키의 중복 |
| Semi-structured | JSON 이벤트, XML 문서 | 필드 유무, 중첩 구조, 스키마 버전 |
| Unstructured | 자유 텍스트, 이미지, 음성 | 추출 품질, 문맥, 라벨, 접근 권한 |

JSON에 담겨 있다고 내용까지 정제된 것은 아니다. 자유 텍스트가 들어 있는 필드에는 개인정보나 잘못된 값이 남아 있을 수 있다. 반대로 문서에서 표를 추출했다면 원본 표의 단위와 머리글이 유지되는지 확인해야 한다.

같은 문서라도 학습 데이터로 사용하면 파라미터 업데이트에 영향을 주고, RAG의 검색 자료로 사용하면 추론 시점에 제공할 근거가 된다. 운영 로그는 평가 사례를 찾는 데 사용하거나, 검토 후 다음 학습 데이터로 선별할 수 있다. **저장되어 있다는 사실만으로 자동 학습되는 것은 아니다.**

## ETL과 Batch와 Streaming

ETL은 원천에서 데이터를 가져오는 Extract, 필요한 형태로 정리하는 Transform, 목적지에 적재하는 Load의 흐름이다. 변환에는 자료형·단위 통일, 중복 제거, 개인정보 처리, 품질 검사 등이 포함될 수 있다. 데이터를 먼저 적재하고 변환하는 ELT도 있지만, 처리 순서만으로 어느 방식이 항상 우수하다고 말할 수는 없다.

Batch는 일정량을 모아서 처리하고, Streaming은 들어오는 이벤트를 지속적으로 처리한다. 하루 단위 보고서라면 배치로 충분할 수 있지만, 이상 징후를 빠르게 알려야 한다면 데이터 도착과 처리 지연을 더 엄격히 관리해야 한다. Streaming이라고 지연이 0이 되는 것은 아니며, 늦게 도착하거나 중복된 이벤트를 다루는 정책도 필요하다.

공부했던 제품 이름도 역할로 구분해 둔다.

- **Kafka:** 이벤트를 발행·구독·저장·처리하는 분산 이벤트 스트리밍 플랫폼이다.
- **Spark:** 대규모 데이터의 분산 계산을 지원하며 배치와 스트리밍 처리에 활용된다.
- **Databricks:** 데이터 처리·분석과 AI 작업을 함께 운영하는 플랫폼이다.
- **RAPIDS와 cuDF:** GPU를 활용한 데이터 처리·분석 도구이며, cuDF는 표 형태 데이터의 DataFrame 연산을 제공한다.

이들은 모두 동일한 목적의 대체 제품은 아니다. 이벤트 전달과 계산 엔진, 운영 플랫폼은 서로 다른 역할을 맡을 수 있다. [Kafka](https://kafka.apache.org/), [Spark](https://spark.apache.org/), [Databricks](https://docs.databricks.com/aws/en/introduction/), [cuDF](https://docs.nvidia.com/cudf/latest/)의 공식 설명을 역할별로 읽으면 이름을 외우는 부담을 줄일 수 있다.

GPU 가속도 전체 처리 시간을 나눠 봐야 한다. 전송과 디스크 읽기가 병목인 상황에서 계산만 빨라져도 전체 개선 폭은 작을 수 있다. 지원 연산, 데이터 크기, 메모리 용량, 장치 간 이동을 함께 확인한다.

## 데이터 품질은 라벨보다 넓은 문제다

데이터 정제는 이상한 행을 삭제하는 작업만을 뜻하지 않는다. 무엇을 정상으로 볼지, 어떤 변환이 의미를 보존하는지 판단해야 한다. 예를 들어 결측값을 전부 0으로 채우면 “측정하지 못함”과 “실제로 0”을 구분할 수 없게 된다.

품질 점검에서는 누락, 중복, 최신성, 단위 불일치, 라벨 오류, 클래스 불균형을 함께 살펴본다. 이상치도 무조건 제거하지 않는다. 잘못 기록된 값일 수도 있지만, 서비스가 놓치면 안 되는 드문 상황일 수도 있기 때문이다.

EDA(Exploratory Data Analysis)는 분포와 관계를 살펴보며 이런 문제를 찾는 단계이다. Feature engineering은 문제 해결에 유용한 입력 표현을 설계하는 일이다. Feature store는 특징의 정의와 값, 활용 경로를 관리해 학습과 서비스에서 재사용하고 일관성을 유지하는 데 도움을 준다.

다만 특징을 저장하는 시스템이 있다고 과거 시점의 정보만 정확히 사용하게 되는 것은 아니다. 미래에 확정된 값을 과거의 예측 입력에 넣는다면 데이터 누수가 발생한다. 특징이 언제 관측되었고 언제 사용 가능해졌는지도 기록해야 한다.

PII(Personally Identifiable Information)는 목적에 필요한 범위로 최소 수집하고, 불필요한 값은 제거하거나 마스킹한다. 가명 처리한 데이터도 다른 정보와 결합해 개인이 드러날 수 있으므로 “이름을 지웠으니 안전하다”고 끝내지 않는다. 접근 권한, 보존 기간, 삭제 범위, 저장 위치 요구를 데이터 흐름에 함께 반영한다.

## 출처와 변환 경로를 남기는 이유

Provenance는 데이터의 출처와 생성 맥락을, Lineage는 이동·변환·사용의 경로를 이해하는 데 초점을 둔다. 실제 도구에서 두 용어의 범위는 겹칠 수 있지만, 왜 기록하는지는 분명하다. 결과가 달라졌을 때 어떤 입력과 변환이 영향을 주었는지 추적하기 위해서이다.

문서 검색 결과가 갑자기 나빠졌다면 원본 변경, OCR 오류, chunking 설정, embedding 모델, 색인 버전 중 어디가 달라졌는지 구분해야 한다. 파일 이름 하나만 남겨 두면 동일한 이름으로 덮어쓴 다른 버전을 구별하기 어렵다.

학습 데이터 버전, 전처리 설정, 라벨 기준, 분할 목록을 모델 버전과 연결해 두면 비교 결과를 다시 확인할 수 있다. 운영 데이터로 개선할 때도 원문, 수정된 정답, 검토 여부를 분리해야 “모델이 처음 만든 답변”을 “사람이 검증한 정답”으로 오인하지 않는다.

## Train과 Validation과 Test

세 데이터셋은 단순히 파일을 세 개로 나누기 위한 것이 아니다. 어떤 결정에 사용했는지가 핵심이다.

| 데이터셋 | 주요 용도 | 피해야 할 사용 |
| --- | --- | --- |
| Train | 모델 파라미터와 전처리 통계 학습 | 평가 정답이나 미래 정보를 섞기 |
| Validation | 모델·설정·임계값 선택 | 선택에 사용하고도 독립 최종 평가라고 부르기 |
| Test | 선택이 끝난 시스템의 일반화 성능 평가 | 결과를 반복 확인하며 설정을 맞추기 |

[scikit-learn의 검증 설명](https://scikit-learn.org/stable/modules/cross_validation.html)처럼 테스트 결과를 보면서 설정을 계속 바꾸면, 파라미터를 직접 학습하지 않았더라도 테스트 정보가 선택 과정에 영향을 준다. 그런 점수는 더 이상 완전히 독립적인 최종 평가로 해석하기 어렵다.

분할 방법은 실제로 일반화하려는 대상을 반영해야 한다. 같은 문서에서 잘라 낸 문장들이 Train과 Test에 섞이면 새로운 문서에 대한 성능보다 이미 본 내용의 재인식에 가까워질 수 있다. 같은 사람이나 장비의 관련 샘플도 새로운 사람·장비에 대한 성능을 보려는 경우 그룹 단위 분할을 고려한다.

시간에 따라 미래를 예측하는 문제라면, 과거로 학습하고 이후의 데이터로 평가하는 방식이 필요하다. 영상에서 가까운 프레임이 거의 같은 장면이라면 단순 무작위 분할이 점수를 부풀릴 수 있다. **비율을 8 대 2로 나누었다는 사실만으로 올바른 평가가 되지는 않는다.**

## 전처리에서도 Data leakage가 생긴다

Data leakage는 예측할 때 알 수 없어야 할 정보가 모델 학습이나 선택 과정에 들어가, 평가를 지나치게 낙관적으로 만드는 현상이다. 정답 열을 실수로 입력에 넣는 경우만 해당하지 않는다.

가령 표준화를 위해 전체 데이터의 평균과 표준편차를 먼저 계산한 뒤 Train과 Test를 나누면, 테스트 데이터의 분포가 전처리에 반영된다. [scikit-learn의 데이터 누수 방지 원칙](https://scikit-learn.org/stable/common_pitfalls.html)에 따라 먼저 분할하고, 학습이 필요한 변환은 훈련 데이터에서 맞춘 뒤 같은 변환을 평가 데이터에 적용한다.

$$
z = \frac{x - \mu_{\text{train}}}{\sigma_{\text{train}}}
$$

여기서 평균과 표준편차는 Train에서 구한 값이며, 위 식은 표준편차가 0이 아닌 경우이다. Test에 별도로 맞춘 다른 평균과 표준편차를 적용하면 학습 때의 입력 공간과 달라질 수 있다. 교차 검증에서도 각 훈련 fold 안에서 변환을 학습해야 하므로 Pipeline을 함께 사용하는 것이 도움이 된다.

결측값 대체, 특징 선택, 차원 축소도 같은 점검이 필요하다. 평가 데이터를 단순히 변환하는 것과, 그 데이터로 변환 규칙을 학습하는 것은 다른 행동이다.

## Precision과 Recall과 F1 계산

이진 분류에서 먼저 무엇을 Positive로 부를지 정한다. 여기서는 가상의 “결함 있음”을 Positive라고 하자.

- TP(True Positive): 결함이 있는 샘플을 결함이라고 판정했다.
- FP(False Positive): 정상 샘플을 결함이라고 잘못 판정했다.
- FN(False Negative): 결함이 있는 샘플을 정상이라고 놓쳤다.
- TN(True Negative): 정상 샘플을 정상이라고 판정했다.

Precision은 결함이라고 알린 것 중 실제 결함의 비율이고, Recall은 실제 결함 중 찾아낸 비율이다. [평가 지표 문서](https://scikit-learn.org/stable/modules/model_evaluation.html#precision-recall-f-measure-metrics)의 정의에 따라 다음처럼 계산한다.

$$
\text{Precision} = \frac{TP}{TP+FP},\qquad
\text{Recall} = \frac{TP}{TP+FN}
$$

$$
F_1 = \frac{2\,\text{Precision}\,\text{Recall}}
{\text{Precision}+\text{Recall}}
= \frac{2TP}{2TP+FP+FN}
$$

시험 직전 정리에서 사용했던 가정인 TP=60, FP=20, FN=40을 대입하면 다음과 같다.

- Precision: \(60/(60+20)=0.75\), 즉 75%
- Recall: \(60/(60+40)=0.60\), 즉 60%
- F1: \(120/(120+20+40)\approx0.667\), 약 66.7%

Precision과 Recall을 더해서 2로 나눈 67.5%가 F1은 아니다. F1은 조화평균이므로 두 값 중 낮은 쪽의 영향을 크게 받는다. 계산은 간단한 코드로도 확인할 수 있다.

```python
tp, fp, fn = 60, 20, 40
precision = tp / (tp + fp)
recall = tp / (tp + fn)
f1 = 2 * tp / (2 * tp + fp + fn)
print(f"P={precision:.3f}, R={recall:.3f}, F1={f1:.3f}")
# P=0.750, R=0.600, F1=0.667
```

위 예제는 분모가 0이 아닌 경우이다. 실제 평가 구현에서는 Positive 예측이나 실제 Positive가 없는 경우의 처리 규칙도 정해야 한다.

Accuracy는 전체 샘플 중 맞은 비율이다. 정상 990개와 결함 10개가 있는 데이터에서 전부 정상이라고 예측하면 Accuracy는 99%이지만, 결함 Recall은 0%이다. 이 때문에 지표는 업무에서 어떤 오류가 더 중요한지를 기준으로 골라야 한다. 다중 클래스에서는 클래스별 지표를 평균하는 방식도 함께 명시한다.

## RAG에서는 검색 품질과 답변 품질을 나눈다

검색 결과가 좋아졌다고 답변까지 자동으로 정확해지는 것은 아니다. 반대로 근거가 누락된 상황에서 생성 모델만 바꾸면 문제의 원인을 놓칠 수 있다.

검색 평가는 정답 근거가 후보에 들어왔는지, 관련 자료가 앞에 배치되었는지 확인한다. 답변 평가는 질문을 해결했는지, 제공된 근거에 충실한지, 형식과 안전 조건을 지켰는지 확인한다. Groundedness가 높다는 것은 제공한 근거에 잘 부합한다는 의미이지, 그 근거가 언제나 최신이고 사실이라는 뜻은 아니다.

예를 들어 관련 문서가 총 4개인 질문에 대해 상위 5개 검색 결과 중 관련 문서가 3개라면, 이 가정에서 Precision@5는 3/5, Recall@5는 3/4이다. 그러나 질문 하나당 정답 근거가 하나 이상 포함되었는지만 세는 Hit rate와는 계산 단위가 다르다. 평가 도구가 같은 이름을 쓰더라도 분모와 정답 정의를 확인해야 한다.

문서별 접근 권한과 최신성도 검색 품질의 조건이다. 의미가 매우 비슷한 문서라도 사용자가 볼 수 없는 자료이거나 폐기된 규격이라면 좋은 근거가 될 수 없다. 이 구분은 [4장의 RAG와 맞춤화](/nca-amad/chapter-04-customization/)에서 이어서 다룬다.

## Data Flywheel은 검증된 개선의 순환이다

[NVIDIA의 Data Flywheel 설명](https://www.nvidia.com/en-us/glossary/data-flywheel/)은 운영 과정에서 얻은 데이터와 피드백을 정제하고, 모델과 시스템을 개선해 다시 배포하는 순환을 다룬다. 여기서 주의할 점은 로그가 쌓인다는 사실만으로 성능이 좋아지지는 않는다는 것이다.

가상의 문서 질문 서비스를 기준으로 한 순환은 다음과 같이 정리할 수 있다.

1. **관측:** 질문, 검색 자료 버전, 응답, 실패 유형을 필요한 범위에서 기록한다.
2. **선별:** 중복과 개인정보를 처리하고, 개선할 가치가 있는 사례를 고른다.
3. **검토:** 피드백과 실제 정답을 구분하고 원인을 확인한다.
4. **개선:** 문서·색인·프롬프트·모델 등 원인에 해당하는 부분을 수정한다.
5. **평가:** 독립된 평가 데이터와 기존 회귀 사례로 개선과 부작용을 확인한다.
6. **배포와 감시:** 검증된 버전을 적용하고 운영 지표와 롤백 조건을 확인한다.

사용자의 싫어요는 오류를 찾는 신호이지 곧바로 올바른 정답은 아니다. 답변이 사실과 달라서일 수도 있지만, 너무 길거나 원하는 형식이 아니어서일 수도 있다. 모델이 자기 답변에 높은 점수를 주었다는 이유만으로 검증된 라벨이 되지도 않는다.

개선 방법 역시 항상 재학습일 필요는 없다. 최신 문서가 색인에 없었다면 먼저 수집과 검색을 고쳐야 한다. 출력 형식이 반복해서 흔들린다면 지시와 구조 검증을 점검한다. 특정 업무 수행 능력이 부족하고 적절한 데이터가 있다면 모델 맞춤화를 검토한다.

배포 전에는 수정한 유형의 점수만 보지 않는다. 새 문서에 대한 정확도가 올랐어도 기존 질문에서 회귀가 생기거나, 응답시간과 비용이 요구를 벗어날 수 있다. 운영 피드백으로 다음 버전을 개선하되, 계속 들여다본 평가셋을 새로운 미지의 성능처럼 보고하지 않는 것도 중요하다.

## 핵심 정리

- 데이터의 저장 형식과 학습·검색·운영에서의 용도를 구분한다.
- 품질은 누락·중복·라벨뿐 아니라 최신성, 단위, 권한, 출처를 포함한다.
- 데이터 분할은 비율보다 독립성, 그룹 관계, 시간 순서를 먼저 본다.
- 학습이 필요한 전처리는 Train에서 맞추고 평가 데이터에 같은 규칙을 적용한다.
- Precision은 예측한 Positive 기준, Recall은 실제 Positive 기준이며 F1은 조화평균이다.
- Data Flywheel은 피드백 수집에서 끝나지 않고 검토·개선·평가·배포까지 이어진다.

다음 장에서는 준비된 데이터를 모델에 넣어 실행할 때, 지연시간과 처리량·메모리를 어떻게 구분해 해석하는지 정리한다.
