모델을 고를 때는 이름이나 파라미터 수부터 보기 쉽다. 하지만 “작은 모델인가?”, “지시를 따르는 모델인가?”, “이미지를 처리하는가?”는 서로 다른 질문이다. 같은 모델이 작은 규모의 Instruct 모델이면서 멀티모달 모델일 수 있고, 큰 언어 모델이면서 MoE 구조일 수도 있다.

이번 장은 시험을 준비하며 구분했던 모델 유형을 **분류 기준, 작업의 입출력, 실제 운영 조건**으로 묶은 학습 노트다. 핵심은 모델을 하나의 서열로 나열하지 않는 것이다. 모델 이름이 바뀌어도 이 기준은 다음 후보를 검토할 때 다시 사용할 수 있다.

## 1. 모델의 종류는 여러 축으로 나뉜다

먼저 어떤 기준으로 분류하고 있는지 구분한다.

| 분류 기준 | 대표 구분 | 확인하려는 질문 |
| --- | --- | --- |
| 상대적 규모 | LLM / SLM | 제한된 연산·메모리에서 실행 가능한가? |
| 추가 학습 목적 | Base / Instruct | 문장을 이어 쓰는가, 사용자의 요청을 따르도록 학습했는가? |
| 계산 구조 | Dense / MoE | 토큰을 처리할 때 어떤 부분을 사용하는가? |
| 적용 범위 | Foundation / Task-specific | 여러 작업에 적응시키는 기반인가, 특정 작업에 특화했는가? |
| 입출력 모달리티 | Text / Vision / Audio / Multimodal | 무엇을 입력받고 무엇을 출력하는가? |
| 공개·이용 조건 | 공개 가중치 / API 제공 등 | 직접 실행·수정·배포할 수 있는 범위는 어디까지인가? |

LLM과 SLM을 나누는 파라미터 수에는 모든 제품에 통용되는 고정 경계가 없다. 작은 모델이라도 해당 업무에 적합하게 학습되어 있다면 큰 범용 모델보다 좋은 선택이 될 수 있다. 반대로 모델이 작다는 사실만으로 지연시간이나 전체 서비스 비용이 항상 작다고 단정할 수도 없다. 입력 길이, 생성 길이, 실행 방식과 동시 요청 수가 함께 영향을 준다.

Foundation model도 “모든 일을 바로 잘하는 완성 모델”이라는 뜻은 아니다. 여러 작업으로 적응시킬 수 있는 기반이라는 의미에 가깝다. 실제로 지원하는 언어와 입력 형식, 학습 목적, 평가 범위는 개별 모델 카드에서 확인해야 한다.

## 2. 모든 문제를 생성형 AI로 바꿀 필요는 없다

머신러닝은 데이터에서 규칙이나 관계를 학습하는 방법을 포괄한다. 신경망은 그 안의 한 부류이고, 딥러닝은 여러 층의 신경망을 활용한다. 선형 모델, 의사결정나무, Gradient Boosting 같은 방법도 여전히 비교 대상이다.

예를 들어 수십 개의 정형 변수로 특정 상태를 분류하는 문제라면, 먼저 단순한 기준 모델을 만들 수 있다. 데이터 규모가 작고 설명 가능성이 중요하다면 복잡한 생성 모델을 도입하기 전에 이 기준 모델이 요구사항을 충족하는지 확인하는 편이 합리적이다. 반면 긴 자연어 문서를 이해하거나 이미지와 텍스트를 함께 해석해야 한다면 다른 모델 계열이 필요해진다.

생성형 모델은 문장·이미지 같은 내용을 생성하는 데 초점을 두고, 판별형 모델은 입력의 분류나 목표값 판별에 초점을 둔다. 다만 작업과 모델 계열이 일대일로 대응하는 것은 아니다. 생성형 LLM에 정해진 라벨 중 하나를 출력하게 해서 분류에 사용할 수도 있다. 이때는 라벨 정확도뿐 아니라 출력 형식 준수율, 지연시간, 비용까지 기존 분류기와 비교한다.

GPU가 신경망에 많이 쓰이는 이유도 이와 연결된다. 신경망의 행렬 연산에는 병렬로 수행할 계산이 많다. 그러나 전처리·데이터 이동·작은 배치의 실행 비용까지 고려하면 GPU를 붙이는 것만으로 전체 애플리케이션이 빨라지지는 않는다. **모델 선택과 실행 장치 선택은 연결되어 있지만 같은 결정은 아니다.**

## 3. Base와 Instruct: 배운 지식보다 사용 방식의 차이

Base 언어 모델은 일반적으로 사전학습을 통해 언어의 패턴을 학습한 모델을 가리킨다. 사용자의 요청을 받았을 때 바로 친절한 답변을 하는 대신, 입력과 비슷한 문장을 이어 쓰는 반응을 보일 수 있다.

Instruct 모델은 지시와 응답의 관계를 따르도록 추가 학습한 모델이다. 지도 미세조정, 선호도 기반 학습 등 구체적인 방법은 모델마다 다르다. [InstructGPT 연구](https://arxiv.org/abs/2203.02155)는 사전학습과 지시를 따르도록 만드는 후속 학습을 구분해 이해하는 데 도움이 된다.

가령 “다음 문서를 세 문장으로 요약하라”는 기능을 만들려면, 같은 계열의 Base보다 지시 수행을 목적으로 준비된 모델이 보통 더 직접적인 출발점이다. 그렇다고 Instruct라는 이름이 붙으면 반드시 세 문장만 출력하거나, JSON 규격을 지키거나, 사실만 말한다는 의미는 아니다. 필요한 형식은 별도 검증을 거쳐야 한다.

채팅 템플릿도 중요하다. 시스템·사용자·도구 메시지를 모델이 기대하는 형식으로 구성해야 한다. 단순 문자열을 붙이는 것과 학습 때 사용한 대화 형식에 맞춰 입력하는 것은 다를 수 있다. 모델을 바꾸면서 가중치만 교체하고 입력 템플릿을 그대로 두면 성능 차이를 잘못 해석할 수 있다.

또한 **Inference와 Reasoning은 다른 개념**이다. Inference는 학습된 모델을 실행하는 과정이고, Reasoning은 문제 해결이나 다단계 판단 능력을 가리킨다. Reasoning 모델도 추론 시점에 실행되며, 긴 사고 과정을 출력한다는 이유만으로 그 내용의 정확성이 보장되는 것은 아니다.

## 4. Dense와 MoE: 활성 파라미터와 전체 파라미터

Dense 모델은 일반적으로 각 입력에 대해 공통된 밀집 계산 경로를 사용한다. MoE, 즉 Mixture of Experts는 여러 expert와 router를 두고 토큰별로 일부 expert를 선택한다. Transformer의 FFN 부분에 MoE를 적용하는 구조가 대표적이다. [NeMo의 MoE 설명](https://docs.nvidia.com/nemo-framework/user-guide/24.07/nemotoolkit/features/moe.html)은 expert 수와 선택할 expert 수를 별도로 다룬다.

여기서 expert를 “수학 담당자, 법률 담당자”처럼 사람이 미리 정한 직무로 이해할 필요는 없다. 어떤 전문화가 생기는지는 구조와 학습에 따라 달라진다. 토큰이 한 expert에 배정된 뒤 모든 층에서 같은 expert만 거치는 구조라고 단정해서도 안 된다.

MoE에서 중요한 숫자는 두 가지이다.

- **전체 파라미터**: 모든 expert와 공통으로 사용하는 층을 포함한 전체 가중치 규모이다.
- **활성 파라미터**: 한 토큰의 처리에 참여하는 파라미터 규모를 나타낸다.

활성 파라미터가 작으면 토큰당 계산을 줄이는 데 유리할 수 있다. 하지만 선택되지 않은 expert의 가중치가 모델에서 사라지는 것은 아니다. [NVIDIA의 MoE 최적화 문서](https://docs.nvidia.com/nemo/megatron-bridge/0.7.0/training/moe-optimization.html)도 저장 메모리, expert 간 통신, 계산 효율을 별도의 제약으로 설명한다.

가중치 저장량만 단순 계산하면 다음과 같다.

$$
M_{\text{weights}} \approx N_{\text{total}} \times b
$$

여기서 \(N_{\text{total}}\)은 전체 파라미터 수이고, \(b\)는 파라미터당 바이트 수이다. 가상의 300억 파라미터 모델을 2바이트로 저장하면 가중치만 약 60GB이다. 이때 GB는 \(10^9\)바이트 기준이며 약 55.9GiB에 해당한다. 일부 파라미터만 활성화된다는 이유로 저장량을 활성 파라미터 수만으로 계산하면 안 된다. 분산 배치나 offload는 저장 위치를 바꾸는 방식이지 가중치 자체를 없애는 방식은 아니다.

이 계산에는 KV cache, 중간 텐서, 런타임 버퍼가 빠져 있다. 양자화 시에도 scale 등 부가 정보가 생길 수 있다. 따라서 실제 GPU 메모리 요구량을 그대로 뜻하지 않으며, Dense와 MoE의 우열도 이름만으로 결정할 수 없다.

## 5. 입력과 출력부터 보면 필요한 모델이 좁혀진다

영상 문제만 보더라도 요구 출력이 다르다.

| 작업 | 원하는 출력 | 간단한 예 |
| --- | --- | --- |
| Classification | 이미지나 대상의 클래스 | 사진이 정상 제품인지 분류 |
| Object detection | 객체의 종류와 위치 | 부품마다 bounding box 표시 |
| Segmentation | 픽셀 단위 영역 | 결함 영역의 면적 계산 |
| OCR | 이미지 속 문자 | 스캔 문서에서 문장 추출 |

“이미지를 이해한다”는 표현만으로 이 요구사항을 모두 만족했다고 볼 수 없다. 예를 들어 제품 결함을 자연어로 설명하는 기능과 픽셀 단위 결함 면적을 계산하는 기능은 서로 다른 평가가 필요하다.

VLM은 시각 정보와 언어를 함께 다루는 모델이다. 문서 이미지에 질문하거나 장면을 설명하는 데 활용할 수 있다. Multimodal은 여러 모달리티를 처리한다는 더 넓은 표현이며, 이미지 입력을 받는 모델이라고 해서 이미지 생성도 가능하다는 뜻은 아니다. Omni라는 이름도 실제 지원 입출력과 실시간 처리 조건을 대신하지 않는다.

World model은 환경의 상태나 변화에 대한 표현을 학습하고, 이를 바탕으로 미래 상태를 예측하거나 생성하는 방향의 모델이다. [NVIDIA Cosmos](https://docs.nvidia.com/cosmos/)는 Physical AI를 위한 world foundation model과 관련 데이터 처리 도구를 제공한다. 다만 그럴듯한 미래 영상을 만들 수 있다는 사실만으로, 특정 로봇의 안전한 제어 정책이나 검증된 물리 시뮬레이터가 완성되는 것은 아니다. 행동 입력·출력 지원, 시간 일관성, 대상 환경에서의 유효성은 따로 확인해야 한다.

## 6. 검색에서는 Embedding, Reranker, Generator가 다르다

RAG 시스템 안에서도 하나의 모델이 모든 역할을 맡는 것은 아니다.

| 구성요소 | 주요 역할 | 출력 |
| --- | --- | --- |
| Embedding model | 검색 가능한 표현 생성 | 텍스트·이미지 등의 벡터 |
| Reranker | 검색 후보의 관련성 재평가 | 후보별 점수 또는 순위 |
| Generator | 제공된 문맥으로 답변 구성 | 문장·구조화된 응답 |

예를 들어 문서 10만 개를 대상으로 질문한다고 하자. 문서 표현을 미리 계산해 후보를 검색하고, 좁혀진 후보를 질문과 함께 다시 평가한 뒤, 선택된 문서를 생성 모델에 전달하는 구성이 가능하다. 모든 문서를 매번 정교하게 비교하지 않고 단계별로 계산량을 배분하는 것이다.

[NeMo의 Reranking 문서](https://docs.nvidia.com/nemo/automodel/model-coverage/reranking-models/overview)는 검색 후보를 얻은 뒤 query-document 쌍을 함께 평가하는 cross-encoder 방식을 설명한다. 다만 모든 reranker가 동일한 구조나 점수 해석을 사용하는 것은 아니므로 해당 모델의 사용법을 따른다.

이 구분은 장애 원인을 찾을 때도 유용하다. 정답 문서가 처음부터 검색되지 않았다면 생성 모델을 키워도 빠진 근거가 생기지는 않는다. 후보 안에는 있지만 뒤로 밀린다면 재순위화나 검색 설정을 살펴본다. 근거가 충분한데 답변이 왜곡된다면 프롬프트, 생성 모델, 답변 검증을 검토한다.

벡터 유사도가 높다는 사실도 곧 사실성이 높다는 뜻은 아니다. 오래된 문서와 최신 문서는 의미상 비슷할 수 있다. 검색에는 의미뿐 아니라 접근 권한, 문서 날짜, 버전 같은 조건도 필요하다.

## 7. Token과 Context는 모델을 고르는 운영 조건이다

Token은 모델이 처리하는 단위이며 항상 단어 하나와 일치하지 않는다. 언어, 기호, 코드, tokenizer에 따라 같은 내용의 토큰 수가 달라진다. [Hugging Face의 토큰화 문서](https://huggingface.co/docs/transformers/en/tokenizer_summary)는 BPE, WordPiece, Unigram처럼 서로 다른 분할 방식을 설명한다.

Autoregressive 언어 생성은 앞선 토큰들을 조건으로 다음 토큰을 생성하고 그 결과를 다시 문맥에 붙이는 방식이다. 따라서 답변이 길어지면 생성 단계의 작업량도 커진다. 같은 모델을 비교하더라도 입력·출력 길이가 다르면 단순한 응답시간 비교가 공정하지 않을 수 있다.

Context window는 현재 요청에서 다룰 수 있는 문맥 범위이다. 시스템 지시, 대화 기록, 검색 문서, 출력 예산이 이 한도를 어떻게 공유하는지는 모델과 API에 따라 확인한다. 긴 context를 지원한다고 해서 필요한 근거를 항상 정확히 찾는 것도 아니다. 문서를 많이 넣는 것과 적절한 근거를 넣는 것은 다르다.

문맥에 문서를 넣는 행위는 영구 학습과도 구분한다. 일반적인 추론 요청에서 문서가 사용되었다고 해서 가중치가 자동으로 업데이트되는 것은 아니다. 대화 기록 저장, 검색 색인 갱신, 모델 학습은 서로 다른 상태 변경이다.

## 8. 공개 모델은 모델 카드와 라이선스까지 읽는다

Open-weight는 가중치를 이용할 수 있다는 의미이지, 모든 학습 데이터와 학습 코드가 공개되었거나 이용 제한이 전혀 없다는 뜻이 아니다. 모델, 코드, 데이터, 실행 컨테이너에 각각 다른 조건이 적용될 수도 있다.

예를 들어 [NVIDIA Nemotron Nano 9B v2 모델 카드](https://huggingface.co/nvidia/NVIDIA-Nemotron-Nano-9B-v2)는 아키텍처와 사용법 외에 라이선스를 명시한다. 모델 가중치와 이를 실행하는 컨테이너는 별도 배포 단위이므로, 각각의 이용 조건과 지원 상태를 확인해야 한다. 중요한 것은 특정 약관을 암기하는 일이 아니라, 다운로드한 파일만 보고 이용 가능 범위를 추정하지 않는 태도이다.

모델 카드에서는 최소한 다음 항목을 확인한다.

- 지원 언어와 입력·출력 형식, 권장 사용 목적
- context 한도와 tokenizer·chat template
- 평가 데이터, 평가 조건, 알려진 한계
- 상업적 이용·재배포·파생 모델에 적용되는 조건
- 필요한 런타임과 지원 정밀도, 하드웨어 제약

## 9. 최종 선택은 대표 업무에서 확인한다

모델 비교에는 정확도만이 아니라 업무 달성도(Efficacy), 견고성(Robustness), 해석 가능성(Interpretability)을 함께 사용한다. 업무 달성도는 원하는 결과를 만드는가, 견고성은 입력의 변화나 노이즈에도 성능을 유지하는가, 해석 가능성은 판단에 영향을 준 요인을 이해할 수 있는가에 관한 기준이다. 모델이 길고 그럴듯한 이유를 생성한다고 해서 내부 판단 과정에 대한 충실한 설명이 확보되는 것은 아니다.

가상의 문서 분류 서비스를 생각하면, 정상적인 문장뿐 아니라 짧은 문장, 오탈자, 혼합 언어, 처음 보는 유형을 평가에 포함할 수 있다. 분류 정확도가 비슷하다면 작은 모델의 운영 부담이 더 낮을 수 있다. 반대로 긴 문서의 여러 조건을 함께 판단해야 하는 업무라면 더 높은 성능의 모델이 필요할 수 있다. 어느 쪽도 실제 평가 없이 결론 내리지 않는다.

비교할 때는 모델 버전, 프롬프트, 정밀도, context 길이, 동시 요청 조건을 기록한다. 공개 순위는 후보를 고르는 출발점이고, 실제 채택 기준은 **내 업무의 품질 요구를 만족하면서 운영 제약을 감당하는가**이다.

## 핵심 정리

- LLM·SLM, Base·Instruct, Dense·MoE는 서로 다른 분류축이다.
- 활성 파라미터는 전체 가중치 저장량을 대신하지 않는다.
- Embedding은 표현, Reranker는 후보 정렬, Generator는 응답 생성을 담당한다.
- 멀티모달 지원 여부보다 구체적인 입력·출력과 평가 조건을 확인한다.
- 모델의 크기뿐 아니라 품질, 지연, 메모리, 데이터 처리 조건과 라이선스로 선택한다.
