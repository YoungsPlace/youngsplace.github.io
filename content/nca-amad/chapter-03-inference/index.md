같은 모델을 실행하더라도 어떤 서비스는 첫 문장이 빨리 나오고, 어떤 서비스는 여러 사용자의 요청을 더 많이 처리한다. 두 서비스 중 무엇이 더 빠른지는 지표와 사용 목적을 정한 뒤에야 판단할 수 있다.

시험을 준비하며 정리한 핵심은 추론을 **입력을 읽는 단계, 출력을 만드는 단계, 요청을 운영하는 단계**로 나누어 보는 것이었다. 이 장에서는 그 구분을 지표와 계산으로 연결한다. 계산에 사용하는 수치는 원리를 설명하기 위한 가정이며, 특정 GPU나 모델의 측정 결과는 아니다.

## 1. 추론에서는 무엇을 계산하는가

추론(inference)은 준비된 모델로 입력의 결과를 계산하는 과정이다. 일반적인 추론에서는 가중치를 갱신하지 않는다. 대화가 이어져 이전 문장을 참고하는 것과, 그 대화를 학습해 가중치를 바꾸는 것은 다른 일이다.

자동회귀 LLM의 작업은 크게 두 부분이다.

- **Prefill:** 이미 주어진 입력 토큰을 처리하고, 다음 생성에 필요한 중간 상태를 계산한다.
- **Decode:** 앞에서 주어진 문맥과 생성한 토큰을 참고해 다음 토큰을 반복해서 만든다.

입력 전체는 처음부터 주어져 있어 Prefill에서 병렬 계산을 활용할 수 있다. 반면 Decode는 앞선 출력에 다음 출력이 의존한다. 긴 문서를 읽는 요청과 짧은 질문에 긴 답변을 쓰는 요청의 병목이 같지 않은 이유이다. 일반적인 작은 배치의 Decode는 메모리 대역폭의 영향을 크게 받지만, 모든 모델·배치·문맥 길이에서 항상 같은 병목이 생기는 것은 아니다. [NVIDIA의 추론 최적화 설명](https://developer.nvidia.com/blog/mastering-llm-techniques-inference-optimization/)이 두 단계의 계산 특성을 다룬다.

서비스 전체에는 검색, 토큰화, 요청 대기, 네트워크 전송, 결과 후처리도 들어간다. 따라서 “LLM 호출이 2초 걸렸다”는 기록만으로 GPU 연산이 2초 걸렸다고 해석하면 안 된다.

## 2. TTFT와 TPOT를 분리해서 읽는다

사용자가 처음 느끼는 대기와 응답이 완성될 때까지의 대기는 서로 다르다.

| 지표 | 이 글에서 사용하는 의미 | 살펴볼 문제 |
| --- | --- | --- |
| TTFT | 요청 전송부터 첫 출력 토큰 수신까지 | 첫 응답이 늦는가 |
| TPOT | 첫 토큰 이후의 평균 출력 토큰 간 시간 | 생성이 계속 느린가 |
| ITL | 연속 출력 토큰 사이의 간격 또는 그 집계 | 생성 간격을 어떻게 집계하는가 |
| End-to-end latency | 요청 전송부터 마지막 출력 토큰 수신까지 | 언제 작업이 끝나는가 |
| Throughput | 일정 시간에 처리한 요청 수 또는 토큰 수 | 시스템이 얼마나 처리하는가 |

TTFT에는 큐 대기와 네트워크 시간도 들어갈 수 있다. ITL과 TPOT라는 이름을 쓰더라도 도구별 계산식이 다를 수 있으므로 정의를 먼저 확인한다. 특히 스트리밍 응답 한 조각에 토큰 여러 개가 담길 수 있어, 네트워크 메시지 간격과 토큰 간격을 그대로 동일시하지 않는다. [NVIDIA의 벤치마킹 지표 문서](https://developer.nvidia.com/blog/llm-benchmarking-fundamental-concepts/)도 측정 방식의 차이를 설명한다.

### 첫 토큰을 두 번 세지 않는 계산

하나의 요청에 대해 다음과 같이 정의하자.

- \(N_{out}\): 출력 토큰 수, 2개 이상
- \(t_0\): 요청을 보낸 시각
- \(t_1\): 첫 출력 토큰을 받은 시각
- \(t_N\): 마지막 출력 토큰을 받은 시각

$$
TTFT = t_1 - t_0
$$

$$
TPOT = \frac{t_N-t_1}{N_{out}-1}
$$

같은 수신 시각 기준을 사용한다면 다음 관계가 성립한다.

$$
T_{last\ token} = TTFT + (N_{out}-1)\,TPOT
$$

가령 TTFT가 0.8초이고, 이후 TPOT가 평균 0.025초이며, 출력이 201토큰인 가상의 요청을 생각해 보자.

$$
T_{last\ token}=0.8+200\times0.025=5.8\ \text{초}
$$

첫 토큰은 이미 0.8초 안에 포함되어 있다. 따라서 뒤에 201을 곱하지 않는다. 출력이 1토큰이라면 이 방식의 TPOT는 정의할 수 없고, 마지막 토큰 수신 시간은 TTFT와 같다. 응답 종료 신호, 별도 검증, UI 표시까지 완료 시간에 포함한다면 그 이후 비용은 따로 더해야 한다.

### 같은 완료 시간이어도 경험은 다르다

가상의 서비스 A는 TTFT 0.5초, TPOT 35ms이고, B는 TTFT 1.5초, TPOT 30ms라고 하자. 201토큰을 생성하면 둘 다 7.5초에 끝난다. A는 더 빨리 시작하고, B는 시작한 뒤 더 빠르게 쓴다.

대화형 서비스는 첫 반응을, 일괄 문서 처리 서비스는 전체 완료 시간과 처리량을 더 중요하게 볼 수 있다. 스트리밍은 부분 결과를 먼저 보여 주지만, 그 자체가 모델 계산을 줄였다는 뜻은 아니다.

### TPOT의 역수와 시스템 처리량은 다르다

위의 5.8초 예시에서 \(1/0.025=40\)토큰/초는 첫 토큰 이후 한 요청의 평균 생성 속도에 대응한다. 첫 대기까지 포함한 요청 전체의 출력 속도는 \(201/5.8\approx34.7\)토큰/초이다. 시작점과 분모가 달라 두 숫자가 같지 않다.

시스템 처리량은 여러 요청이 함께 실행되는 측정 구간에서 계산한다. 예를 들어 10초 동안 완료한 요청들이 모두 합해 출력 4,000토큰을 만들었다면, 그 측정 구간의 출력 처리량은 400토큰/초이다.

$$
Throughput_{output}=\frac{N_{out,total}}{\Delta t}
$$

여기서 \(N_{out,total}\)은 전체 출력 토큰 수, \(\Delta t\)는 측정 시간이다. 이 값이 높아져도 개별 요청의 대기가 길어질 수 있다. 따라서 **시스템 전체 처리량을 \(1/TPOT\)로 대신하지 않는다.** 입력 토큰 포함 여부, 측정 구간의 경계, 완료 요청만 집계하는지까지 고정해야 비교가 가능하다. [NVIDIA NIM의 지표 정의](https://docs.nvidia.com/nim/benchmarking/llm/2.0.0/metrics)도 사용자 단위 속도와 시스템 단위 처리량을 구분한다.

## 3. 캐시는 세 가지를 구분한다

“캐시를 사용한다”는 말만으로 무엇이 빨라지는지 알 수 없다.

| 종류 | 재사용하는 것 | 주의할 점 |
| --- | --- | --- |
| KV cache | 이전 토큰의 Key·Value 상태 | 문맥과 활성 요청이 늘면 메모리도 증가 |
| Prefix cache | 여러 요청에 공통인 입력 접두부의 상태 | 의미가 비슷한 문장만으로는 부족 |
| Response cache | 이전에 완성한 응답 | 최신성·권한·개인화 조건 확인 |

KV 캐시는 같은 요청의 다음 토큰을 계산할 때 과거의 Key·Value를 매번 다시 만들지 않도록 돕는다. 그렇다고 과거 문맥을 읽는 모든 연산이 사라지지는 않는다. 긴 문맥은 여전히 비용을 가진다.

Prefix cache는 동일한 모델과 호환되는 설정에서 일치하는 접두부 상태를 요청 사이에 재사용한다. 고정된 시스템 지시문은 앞부분에 두고, 자주 바뀌는 정보는 뒤에 두는 구성이 유리할 수 있다. 다만 실제 재사용은 엔진의 블록 크기, 캐시 퇴거, 요청 실행 시점 등에 영향을 받는다. [TensorRT-LLM의 KV cache reuse 문서](https://nvidia.github.io/TensorRT-LLM/advanced/kv-cache-reuse.html)는 이러한 조건을 명시한다.

응답 캐시는 계산 결과 전체를 되돌려주는 별도 계층이다. 예를 들어 “현재 담당자”를 묻는 답변을 장기간 저장하면 조직 정보가 바뀐 뒤 틀린 답을 재사용할 수 있다. 문서 접근 권한이 다른 사용자가 같은 질문을 했다고 해서 같은 응답을 공유해서도 안 된다. 캐시 설계에는 속도뿐 아니라 키 구성, 만료, 권한 분리가 필요하다.

어느 방식도 모델의 영구 학습과 같지 않다. 캐시를 지워 응답이 느려졌다는 사실은 모델이 지식을 잊었다는 뜻이 아니다.

## 4. 가중치가 들어간다고 서비스가 실행되는 것은 아니다

가중치만의 이상적인 저장량은 다음처럼 계산한다.

$$
M_{weights}=P\times b
$$

\(P\)는 파라미터 수, \(b\)는 파라미터당 바이트 수이다. 80억 파라미터를 16비트로 저장한다면 \(8\times10^9\times2=16\times10^9\)바이트, 약 16GB 또는 14.9GiB이다. GB와 GiB는 단위가 다르다.

이 값은 모델 실행에 필요한 전체 메모리가 아니다. KV 캐시, 임시 활성값, 실행 엔진의 작업 공간, 메모리 관리 오버헤드가 더 필요하다. 학습이라면 기울기와 옵티마이저 상태 등도 별도로 고려해야 한다.

### KV 캐시 크기를 직접 계산해 보기

모든 레이어가 같은 구조이고, 전체 문맥의 KV를 저장하는 단순한 Transformer를 가정하면 다음 근사식을 쓸 수 있다.

$$
M_{KV}\approx 2LBSH_{KV}d_hb_{KV}
$$

- \(L\): 레이어 수
- \(B\): 동시에 활성화된 시퀀스 수
- \(S\): 각 시퀀스에 저장된 토큰 수
- \(H_{KV}\): 레이어당 KV head 수
- \(d_h\): head 하나의 차원
- \(b_{KV}\): KV 원소당 바이트 수

앞의 2는 Key와 Value 두 종류를 뜻한다. 모든 요청의 길이가 다르면 \(BS\) 대신 각 요청의 저장 토큰 수를 합산한다. GQA 구조에서는 Query head 수가 아니라 **KV head 수**를 넣어야 한다.

가정값을 \(L=32\), \(B=4\), \(S=4096\), \(H_{KV}=8\), \(d_h=128\), \(b_{KV}=2\)로 두면 다음과 같다.

$$
M_{KV}\approx2\times32\times4\times4096\times8\times128\times2
=2{,}147{,}483{,}648\ \text{bytes}=2\ \text{GiB}
$$

같은 조건에서 동시 시퀀스 수를 8개로 바꾸면 4GiB이다. 문맥 길이까지 두 배로 늘리면 8GiB가 된다. 긴 문맥과 동시성을 함께 늘리는 설정이 메모리에 부담을 주는 이유를 알 수 있다.

이 계산은 블록 단위 할당과 메타데이터를 제외한다. Sliding-window attention, 압축된 KV 표현, 레이어별 다른 구조에는 그대로 적용할 수 없다. 가중치를 4비트로 줄였다고 KV 캐시까지 자동으로 4비트가 되는 것도 아니다.

## 5. 배칭과 병렬화는 서로 다른 문제를 푼다

배칭은 여러 요청을 함께 계산해 하드웨어를 더 잘 활용하는 방법이다. 하지만 배치를 채우려고 기다리면 요청 지연이 늘 수 있다. 처리량 최대화와 사용자 대기 최소화가 항상 같은 설정을 가리키지는 않는다.

고정 배치에서는 출력 길이가 다른 요청을 효율적으로 처리하기 어렵다. Continuous 또는 in-flight batching은 실행 도중 끝난 요청을 빼고 새 요청을 넣는 방식으로 자원 사용을 개선한다. 그래도 긴 입력이 몰리거나 메모리가 포화되면 지연이 발생한다. “배치가 동적이다”라는 설명만으로 일정한 응답 시간을 보장할 수는 없다.

여러 GPU를 쓰는 방식도 구분한다.

| 방식 | 나누는 대상 | 먼저 고려할 조건 |
| --- | --- | --- |
| 데이터 병렬 서빙 | 요청을 여러 모델 복제본에 분산 | 복제본마다 모델이 들어가는가 |
| Tensor parallelism | 레이어 내부 계산·텐서 | GPU 간 통신 비용이 감당되는가 |
| Pipeline parallelism | 모델의 레이어 구간 | 구간별 부하와 대기 구간은 어떤가 |

모델이 GPU 하나에 들어가지 않는 상황과, 이미 들어가지만 사용자가 많은 상황은 다른 문제이다. 전자는 모델 분할이 필요할 수 있고, 후자는 복제본을 늘려 요청을 분산하는 편이 단순할 수 있다. GPU 수를 두 배로 늘린다고 단일 요청의 지연이 반드시 절반이 되지는 않는다.

Prefill과 Decode를 별도 자원에 배치하는 설계도 있다. 각각의 부하를 따로 조절할 수 있지만 KV 상태를 넘기는 비용과 운영 복잡성이 생긴다. 먼저 단계별 시간이 실제로 어디에서 소비되는지 확인해야 할 선택이다.

## 6. 양자화와 Speculative decoding의 조건

### 양자화는 메모리와 품질을 함께 본다

양자화(quantization)는 수치 표현의 정밀도를 낮추는 방법이다. 가중치 크기를 줄이고 메모리 이동량을 낮출 수 있지만, 지원되는 연산 커널과 하드웨어가 필요하다. 더 작은 파일이라는 사실만으로 더 빠른 실행을 보장하지 않는다.

가령 두 설정이 같은 문답 정확도를 보이더라도 숫자 추출이나 긴 문서 처리에서는 차이가 날 수 있다. 따라서 실제 업무 입력에 대한 품질, 메모리, TTFT, TPOT를 함께 비교한다. 캘리브레이션 데이터를 쓰는 방식이라면 그 데이터가 운영 입력을 대표하는지도 확인한다.

### Speculative decoding은 초안을 검증한다

Speculative decoding은 저렴한 초안 생성기가 여러 토큰을 제안하고, 목표 모델이 이를 검증하도록 구성한다. 적절한 수용·거절과 보정 절차를 사용하면 목표 모델의 샘플링 분포를 유지할 수 있다. 이는 작은 모델의 답변을 무조건 채택하는 방법과 다르다. [Leviathan 등의 원 논문](https://proceedings.mlr.press/v202/leviathan23a.html)이 정확한 분포 보존을 다룬다.

가속 여부는 초안의 수용률, 검증 비용, 초안 생성 비용에 달린다. 초안을 길게 만들었는데 계속 거절된다면 추가 계산만 늘 수 있다. “분포를 보존한다”는 조건과 “어떤 환경에서나 빨라진다”는 주장을 구분해야 한다.

## 7. 느린 서비스를 진단하는 순서

다음은 실제 측정값이 아닌, 진단 사고방식을 위한 세 가지 가상 상황이다.

### 상황 A: 문서 검색을 붙인 뒤 첫 응답만 느려졌다

전체 요청의 TTFT를 검색 시간과 LLM 호출 이후 시간으로 나눈다. 검색 자체가 느린지, 입력 문서가 길어져 Prefill이 늘었는지 구분한다. 검색은 1초 늘었는데 모델만 교체한다면 핵심 원인을 놓칠 수 있다. 근거를 무조건 줄이면 답변 품질이 손상될 수 있으므로 검색 결과의 관련성도 함께 평가한다.

### 상황 B: 사용자 수가 늘자 시스템 처리량은 늘었지만 불만도 늘었다

전체 토큰/초와 사용자별 대기는 다른 지표이다. 평균뿐 아니라 p95 TTFT와 p95 완료 시간을 본다. 요청별 출력 길이가 바뀌었다면 그 영향부터 분리한다. 배치 크기만 계속 키우기보다 큐 한도, 최대 활성 요청 수, 복제본 수를 비교한다.

### 상황 C: 유휴 시간 뒤 첫 요청만 매우 느리다

모델 로딩, 엔진 초기화, 연결 준비 같은 cold start를 확인한다. 정상 상태의 Decode 최적화와 준비되지 않은 서버의 초기화 문제는 구분한다. 자동 확장도 새 인스턴스의 준비 시간을 없애 주지는 않는다. 워밍업과 여유 용량의 비용을 서비스 요구와 함께 판단한다.

이 과정에서 GPU 사용률 하나만 보고 결론내리지 않는다. 사용률이 낮아도 CPU 전처리, 메모리 대역폭, 네트워크, 요청 스케줄링이 병목일 수 있다. 중요한 것은 요청의 어느 구간이 늘어났는지이다.

## 8. 비교 실험에는 조건표가 필요하다

최적화 전후에는 적어도 다음 조건을 기록한다.

1. 모델·토크나이저·실행 엔진의 버전
2. 입력과 출력 토큰 길이의 분포
3. 동시 요청 수와 요청 도착률
4. 정밀도, 배치 설정, GPU 구성
5. 캐시 사용 여부와 워밍업 상태
6. 스트리밍·샘플링·종료 조건
7. 정확도와 지연의 허용 기준

입력 100토큰·출력 20토큰인 테스트와 입력 8,000토큰·출력 1,000토큰인 테스트를 토큰/초 하나로 비교하면 사용 목적을 놓친다. 서로 다른 토크나이저라면 같은 문장도 토큰 수가 다를 수 있다.

비용 역시 GPU 가격만으로 끝나지 않는다. 가령 같은 시간과 비용으로 설정 A는 요청 1,000개를 처리하고, 설정 B는 1,200개를 처리했다고 하자. 품질과 지연 기준을 동시에 만족한 비율이 각각 95%, 70%라면 유효한 결과는 950개와 840개이다. 이 가정에서는 원시 처리량이 큰 B가 유효 결과당 비용도 낮다고 말할 수 없다.

실험 목표를 “최대 토큰/초”로 둘지, “정해진 품질과 지연 기준 안에서 가장 많은 요청”으로 둘지 먼저 정해야 한다.

## 정리

- Prefill과 Decode를 나누어야 입력 처리와 출력 생성의 병목을 구분할 수 있다.
- TTFT와 TPOT는 별개이며, 첫 토큰을 제외한 간격의 개수는 \(N_{out}-1\)이다.
- 한 요청의 생성 속도와 여러 요청을 합친 시스템 처리량을 구분한다.
- 가중치 저장량만으로 필요한 GPU 메모리를 판단하지 않는다. KV 캐시는 문맥과 활성 요청 수의 영향을 받는다.
- 캐시, 배칭, 양자화, 병렬화는 서로 다른 비용을 줄이며 각자의 제약이 있다.
- 최적화의 성공은 동일한 부하에서 품질·지연·처리량·비용을 함께 비교해 판단한다.
